# Ace 多智能体协同重构设计稿

**状态：** 讨论稿  
**日期：** 2026-11-02  
**范围：** 智能组队、任务接入、任务拆分、分配、执行、补员、交付与恢复

## 1. 背景与目标

当前验收中出现了复杂任务未按预期拆分、用户指定职责与实际分配不一致、任务追问反复出现等问题。静态审计还发现：规划模式采用不同的分配路径，职责匹配部分依赖原文片段，能力画像与职责归属相互影响，部分缺省依赖可能将可并行工作串行化。具体某次任务未拆分的原因仍需结合当次运行记录确认。

本设计的目标是建立一条可理解、可执行、可追踪的协作链路：

1. 普通用户只输入团队名称、不选成员，也能由 AI 自动组队并开始使用。
2. 专业用户可以指定成员、职责、工具和协作约束；系统能识别并遵循这些要求。
3. 根据实际任务判断是否拆分；简单任务可以由一个工作单元完成，复杂任务能形成有意义的工作单元和依赖。
4. 所有规划方式共用一套分配规则，并能解释实际负责人、原因和调整过程。
5. 执行过程中支持能力缺口补员、并行提速或质量补员，并保留用户控制。
6. 用户可查看任务进展、等待事项、结果及实际执行记录；出现中断时可在当前版本内恢复。

### 1.1 范围边界

- 项目仍处于开发阶段：**不要求迁移旧任务、兼容旧任务恢复或同时维护旧执行链路**。开发数据是否重置，在实施切换时根据实际情况处理；本设计不会直接删除现有数据。
- 保留并接入有价值的已有能力，包括可用 Agent 和模型接入、工具调用、桌面端和网页端入口、适用的持久化基础；逐项验证接口，不假定现有模块整体可直接复用。
- 以新协作内核作为新任务的唯一决策和执行入口。旧规划和执行分支在新链路接管后删除或退役，不长期并存。
- 本文是目标设计，不代表这些行为已经实现，也不将推荐的资源默认值视为实测结果。

### 1.2 参考思路

[DeepSeek superagent prototype](https://github.com/deepseek-ai/dsh-superagent-prototype) 的任务模型将持续跟进的 Ticket 与一次具体 Assignment 分开；其执行设计关注任务状态、人工介入和恢复。Ace 借鉴任务身份、执行尝试和持续跟进的思路，结合可配置团队、多成员和 DAG 重新设计，不直接套用其面向代码仓库的场景。该项目为研究原型，不能直接视为生产就绪实现。

## 2. 架构总览

```text
团队配置与自动组队
  ↓ 团队版本快照
任务接入与归属
  ↓ 任务目标、输入与约束
任务理解与拆分
  ↓ 工作单元与依赖
统一负责人分配
  ↓ 分配依据与可执行计划
调度执行、动态调整与补员
  ↓ 执行尝试、产物和状态
交付、用户反馈与持续跟进
```

持久化、用户决策、状态投影贯穿全链路。DAG 描述工作单元之间的依赖；普通用户不需要理解 DAG 才能使用团队。

### 2.1 不变量

1. 每次用户任务有稳定 ID；计划变更、追问、执行和产物都归属于该任务。
2. 工作单元描述具体可交付的工作；不能为了让每个成员参与而制造泛化节点。
3. 所有规划入口共用同一套分配和约束校验；模型给出的负责人只是候选，最终由统一分配器决定。
4. 本次任务的明确指令优先于团队长期职责；用户明确排除的行为不能由系统推测覆盖。
5. 职责归属、能力证据和运行可用性分开记录；未知能力不等同于缺失能力。
6. 没有依据的顺序不构成依赖；资源并发限制与业务依赖分别表达。
7. 工作单元状态、实际执行尝试及其结果必须一致；模型返回文本不自动等于成功交付。
8. 临时补员默认只属于当前任务，不自动改变长期团队。
9. 一项工作只有在必需输入或决策确实缺失时才阻塞；其他无依赖工作可以继续。

## 3. 团队配置与自动组队

### 3.1 产品入口

默认填写团队名称，团队目标和高级设置均为选填。用户不选择任何成员时，代表由系统自动选择，不代表空团队或拒绝使用成员。

```text
团队名称：[比赛材料团队]
团队目标：[选填]
[智能组队]

更多设置：必选成员 / 排除成员 / 成员职责 / 工具能力 / 调配偏好
```

| 用户输入 | 系统行为 |
| --- | --- |
| 只填名称 | 从用户可用候选中推荐精简初始团队和建议职责；名称有含义时可作为弱线索 |
| 名称含义不明确 | 推荐通用协作阵容；具体任务出现后再按任务分工或补员 |
| 填写团队目标 | 围绕目标匹配成员和建议职责，保留用户目标原文 |
| 指定必选成员 | 满足可用性前提下保留；未指定的部分可由 AI 补充 |
| 指定成员职责 | 保留原文及来源；润色需可回看原文，不得覆盖用户约束 |
| 没有可用候选 | 明确提示无法完成自动组队及缺少的配置，不展示虚假成功 |

名称推断出的用途和系统建议职责都标记为建议，不保存成用户明确填写的目标。不可用的必选成员不悄悄移除：保留用户选择，解释原因并提供可用选项。

### 3.2 候选成员与职责

候选优先来自用户当前允许使用的 Agent；是否能基于已有模型或运行环境实例化成员，由现有产品能力和用户配置决定。选择依据包含用户约束、任务或团队目标、工具可用性及能力证据；工具实际可用与模型推测的能力分开记录。

组队输出 `FormationPlan`，至少包含团队配置版本、成员 ID、选择原因、职责原文、结构化职责、职责来源、必选/排除约束、未知项和调配策略。结构化职责可含使命、典型工作、交付物和排除事项；模型整理无法可靠确定时保留原文，不凭空创造限制。

用户编辑职责后更新来源及版本；重新评估能力覆盖不等于重新生成并覆盖职责。更改职责后仍停留在当前编辑/结果页面。

**必选入队**表示成员属于团队，不要求每次任务都派活。若用户本次明确要求某成员参与或承担某项工作，则属于该任务约束，无法满足时须说明。

### 3.3 成员选择优先级

本次任务明确指令 > 用户填写的团队职责与明确排除项 > 用户确认过的建议 > AI 推断。不同约束存在真正冲突且无法依据上下文确定时，展示冲突并请用户决定；禁止将推测升级为用户指定。

团队配置是长期设置；任务创建时生成快照。以后用户编辑团队，不追溯改变已启动任务的原始依据；用户可以对当前任务明确提出变更。

## 4. 任务接入与归属

接入层区分：新任务、已有任务补充、任务状态查询、普通对话及针对现有任务的变更。明确指向任务或节点的消息直接关联；无法可靠判断属于哪项任务且关联错误会影响执行时，提供候选并询问。

每个任务持久化 `task_id`、用户目标原文、团队快照版本、输入资料引用、明确约束、补充信息、状态和资源策略。用户回答保存为结构化决策，关联任务、问题、相关工作单元及适用范围，不依赖将答案拼接到目标文本后再次猜测。

补充信息导致目标、约束或依赖变化时，评估对未执行和正在执行的工作的影响；需要改变计划时创建新版本，并说明已完成成果是否仍适用。

## 5. 任务理解与拆分

### 5.1 统一输出

任务规划输出目标、交付物、输入、约束、工作单元、显式依赖和真正阻塞的信息。不同规划强度可使用不同推理预算，但必须输出同一模型并经过同一校验和分配路径；不再保留可以绕过统一分配器的独立 DAG 指派路径。

工作单元至少包含：稳定 ID、工作目标、必要输入、预期输出、完成条件、依赖、能力/工具要求及其来源。模型可提出成员建议，但不能直接作为最终分配结果。

### 5.2 是否拆分

- 简单工作允许只有一个工作单元；单节点本身不是失败。
- 综合判断交付物、不同工作目标、独立审阅要求、可并行性、前置关系和协调成本。
- 当用户明确要求独立的工作或审阅时，计划应体现；不能为成员数量或节点数量凑数。
- 检查计划是否覆盖关键交付、节点是否具体可执行、依赖是否合法、是否存在明显重复或遗漏。规则校验可以发现结构问题，语义覆盖判断需要模型或人工复核，不能保证自动判断完全正确。

### 5.3 依赖与并行

仅为有实际输入/先后关系的工作建立依赖，并保存理由。无依赖的工作视为可调度候选，而不是按列表顺序自动串行。实际同时运行数量由并发和资源策略控制。识别循环依赖、引用不存在的节点和无效边时，拒绝执行该计划并进入修正或失败流程。

### 5.4 规划失败

模型不可用、输出无效或无法形成覆盖关键目标的计划时：记录失败类型，进行有上限的重试或结构修复；仍失败则明确提示，允许用户重试、补充信息或选择由单个可用成员尝试直接处理。只有用户选择单成员尝试后才进入该降级路径，并标明未完成自动拆分。

不按成员数量创建“按职责执行本轮任务”等泛化节点，不宣称规划成功。无需用户补充的信息不应以追问代替系统故障说明。

## 6. 统一分配

### 6.1 决策流程

1. 校验本次任务明确指定的成员和排除项。
2. 将工作单元与用户明确职责做语义匹配；保留原文、匹配理由及来源，不能以固定字数相同片段作为唯一依据。
3. 无明确职责时，参考系统建议职责、成员信息、工具及可用性，为工作选择负责人。
4. 检查是否存在真实工具/运行环境缺口；能力证据未知单独标注。
5. 存在多个实质不同的合理负责人，且自动决定会违背或无法解释用户要求时，询问用户；普通的系统建议可自动决定并说明。

用户明确指定具有优先级，但不代表成员一定具备运行条件。指定成员不可用时，不静默改派；说明原因并提供重试、等待、更换或补员等适用选项。

### 6.2 分配记录与追问

`Assignment` 保存任务 ID、计划版本、工作单元 ID、负责人、来源、匹配的职责引用、理由、能力证据状态和用户确认。职责语义匹配由模型辅助，系统仍需校验成员真实存在、职责来源、排除条件和任务指令，不能将模型推测写成用户原话。

追问使用稳定 `decision_id`，关联工作内容和候选；回答持久化为结构化选择。重新规划时，只有工作目标及决策含义仍适用才沿用；变更实质内容时重新确认。重复提交同一回答应被识别，避免无限追问。

## 7. 调度、执行和产物

### 7.1 工作包

每次实际委派提供本次目标、该工作单元具体要求、相关用户职责、必要资料及前置结果、预期输出、约束和可用工具。按最小必要范围传递上下文，并记录实际传递的输入引用；不得把整个任务简单复制给每个成员。

### 7.2 调度

依赖满足且成员、工具和资源可用的节点进入就绪队列；调度器依据并发上限启动尝试。同一工作单元在同一时间默认只允许一个有效执行尝试；主动并行比较需要明确创建独立工作及汇总规则。涉及同一文件、外部对象或有副作用的操作应识别冲突并协调，不能仅因为 DAG 无边就盲目并行。

### 7.3 执行尝试与完成

`ExecutionAttempt` 包含 attempt ID、任务/计划/工作单元 ID、计划负责人、实际执行者、开始结束时间、输入引用、状态、错误、产物引用及必要的调用记录。重试产生新尝试，不覆盖历史尝试。

工作单元完成需要记录实际结果，并依据其完成条件作结构和必要的内容检查；检查无法确认时应如实标注。任务最终状态由工作单元、必要交付物和用户决策共同决定，不能因为模型返回文本或部分节点完成就显示全部成功。

## 8. 运行时补员与调配

### 8.1 类型 A：解决无法完成或实际受阻

例如缺少必需工具、运行环境不可用、必要工作反复失败。先识别具体障碍，再检查已有成员能否承担，最后从用户允许的候选中寻找临时成员。能力未知允许在可行时先尝试，不直接视为能力缺失。

### 8.2 类型 B：并行提速或提高质量

当前团队可以完成，但可拆分资料阅读、独立分析或独立审阅。补员前评估工作是否独立、结果能否合并、候选能否访问输入及工具、资源上限、协调成本与共享资源冲突。没有可靠测量时不承诺具体提速比例。未补员时原团队继续执行。

### 8.3 策略与约束

顺序：先考虑现有成员与现有并发，再考虑任务级临时成员。临时补员不写入长期团队，用户可另行选择加入。

默认策略建议：在用户已配置、允许使用的候选和资源限制内自动调度，并展示原因；改变本次明确指定的负责人时请求用户决定；新增未配置的服务或持久修改团队时由用户决定。专业设置可选择自动调配、建议后确认或固定团队，并设置并发和临时成员上限、是否允许并行/审核补员。

补员记录包含触发类型、具体原因、备选方案、候选及选择依据、承担的工作、资源策略和用户决定。候选不可用或搜索无结果时，显示受阻或继续原路径，不伪造成员和能力。

## 9. 状态、恢复与交互

### 9.1 状态机

工作单元：`pending → ready → running → completed`；按条件可进入 `waiting_user`、`blocked`、`failed` 或 `cancelled`。只有依赖满足且调度条件具备时才进入 `ready`；失败后的重试创建新尝试。非法状态转换由内核拒绝。

任务：`understanding → planning → running → completed`，也可进入 `waiting_user`、`blocked`、`partially_completed`、`failed` 或 `cancelled`。任务有可独立推进的工作时，即使部分节点等待用户也可继续运行；最终汇总须如实体现未完成项。需要用户验收时另记验收状态 `not_requested / pending / accepted / changes_requested`，不把待审阅与已验收混为一谈。

### 9.2 中断与恢复

先持久化计划、分配、决策和尝试状态，再执行相应调用；恢复时读取已完成产物和未完成工作，重新判断运行中的尝试是否已结束。外部副作用应使用对方支持的幂等键、可查询执行记录等机制降低重复风险；无法确认外部操作结果时标记为待核实，不声称能对所有外部系统保证恰好执行一次。

用户取消任务时停止可取消的后续工作；已发出的外部操作是否能撤销取决于对应工具，结果应如实展示。

### 9.3 用户界面

默认显示目标、当前进展、成员正在做什么、已有成果、需要用户处理的具体问题和结果。专业视图展开工作单元、依赖、分配依据、补员理由、计划版本及实际尝试。桌面端和网页端消费同一后端状态投影，不各自推测任务是否完成。

## 10. 核心对象与边界

| 对象 | 关键字段与关系 |
| --- | --- |
| Team / FormationPlan | team ID、版本、成员、职责原文和来源、用户约束、调配策略 |
| Task | task ID、团队快照、用户目标、输入、约束、状态 |
| TaskPlan | plan ID、task ID、版本、规划依据、工作单元与依赖 |
| WorkUnit | unit ID、目标、输入、输出、依赖、能力与工具要求 |
| Assignment | unit ID、负责人、职责依据、来源、确认状态 |
| ExecutionAttempt | attempt ID、unit ID、实际执行者、输入、状态、结果、错误 |
| Artifact | artifact ID、来源尝试、内容或引用、版本及状态 |
| UserDecision | decision ID、task/unit、问题、候选、答案、适用范围 |
| StaffingDecision | 触发类型、原因、候选、选择、任务范围及资源策略 |

建议内核按 `domain / formation / intake / planning / assignment / runtime / storage / presentation` 划分职责。应用服务协调流程；领域层定义规则；模型、Agent、工具、存储和前端通过接口接入。文件结构和字段可在详细设计时细化，但职责边界及不变量不可绕过。

**状态一致性：** 状态变更及待执行意图应在可靠的持久化边界内提交；外部调用在事务之外执行，通过记录、去重及结果对账处理异常。持久化方案需要结合当前存储能力选型，不假定所有现有存储天然支持同一种事务。

## 11. 示例：比赛材料任务

用户组队时指定 A 研究比赛规则、B 撰写、C 审核事实。用户请求“根据比赛要求准备申报材料，并检查功能描述是否真实”。

```text
A：整理比赛规则 ──┐
                  ├→ B：撰写 → C：核对事实和逻辑 → 汇总交付
整理项目事实 ─────┘
```

规则和项目事实可以并行，B 的工作依赖两者。若项目材料有大量相互独立的资料，系统可依据策略增加临时成员分批整理；若 A 的运行环境不可用，应说明并提供处理方式。最终显示材料、来源、待核实事项和审阅状态。

若同一团队只收到“检查这句话的错别字”，一个工作单元即可，无需让 A、B、C 都参与。

## 12. 旧实现处置与实施顺序

当前静态代码中需重点替换的路径包括：[多路径规划](../crew/team/graph_planner.py)、[团队管理与恢复](../crew/team/team_manager.py)、[工作流执行](../crew/team/team_workflow_runtime.py)和[运行时补员](../crew/team/runtime_staffing.py)。其中可复用能力需通过新接口评估；规划失败时按每位成员创建泛化职责节点、六字符职责兜底作为主要匹配、无依据地串行化等行为不保留为新内核规则。

1. **契约与详细设计：** 锁定对象、状态机、存储与事件边界、权限/资源策略和桌面/网页接口；盘点可复用接入与存储。
2. **协作内核：** 实现团队快照、任务接入、规划、统一分配和持久化；明确规划失败。
3. **执行闭环：** 实现调度、实际委派、产物、尝试、补员、用户决策和当前版本恢复。
4. **产品接入：** 对接组队、对话、协作面板，桌面端和网页端共享语义。
5. **收口：** 新任务仅走新内核；移除旧规划与调度入口，处理开发环境中的旧数据，并完成端到端验收。

阶段划分用于控制工程风险，不意味着将旧任务兼容作为交付目标，也不允许长期维护两套新任务决策链路。当前工作区已有未提交修改，实施时须先辨别哪些可复用、哪些被替换，避免误删无关工作。

## 13. 验收场景

每项同时核对用户界面、保存的输入与职责、计划、真实委派、执行尝试和最终产物。

| 场景 | 预期 |
| --- | --- |
| 只填团队名称、不选成员 | 从可用候选自动组队；目标推测标记为建议 |
| 名称含义模糊 | 能创建通用团队，不编造用户目标 |
| 无可用成员 | 解释缺少配置，不展示虚假成功 |
| 指定必选成员 | 成员保留；不强制每次任务都参与 |
| 用户编辑职责 | 不覆盖修改；任务分配可追溯到该职责 |
| 本次明确指定与长期职责不同 | 本次明确指令优先，记录依据 |
| 简单任务 | 一个可执行工作单元即可 |
| 复杂多交付任务 | 形成有意义的工作单元与必要依赖，覆盖目标 |
| 规划失败 | 明确失败或经用户选择单成员尝试，不生成泛化假拆分 |
| 职责同义表达 | 语义相关时可合理匹配；真实歧义才询问 |
| 用户回答后重新规划 | 决策仍适用于相同工作时被沿用，不重复追问 |
| 可并行分析 | 不因列表顺序串行；受资源限制时可排队 |
| 能力未知 | 不直接判定缺失或静默换人 |
| 缺少必要工具 | 解释缺口，寻找合适临时成员或明确阻塞 |
| 并行补员 | 工作可拆分且资源允许时调配；不补员也可继续 |
| 用户指定成员不可用 | 给出重试、等待、改派等合适选项 |
| 中断和重试 | 保留原尝试及成果；不能确认的外部副作用标记待核实 |
| 部分完成或待审阅 | 界面如实显示，不能宣称全部完成或已验收 |
| 桌面端与网页端 | 同一任务的负责人、状态和产物一致 |

验收还应收集：工作拆分是否覆盖目标、用户指定遵循情况、真实委派成功率、重复追问次数、恢复结果和任务完成耗时。并行收益需基于可比较的实际运行数据评估。

## 14. 待详细设计确认

1. 当前用户可用 Agent 清单、模型运行环境和工具可用性的权威来源，以及无候选时的具体引导。
2. 默认并发、临时成员数、调用预算及是否按任务设置；根据实际环境测量后确定。
3. 当前存储对事务、事件、唯一键和副作用对账的支持，以及新内核的持久化选型。
4. 独立审核何时默认启用、何时仅作为建议；不能为了展示多智能体而固定增加审核节点。
5. 外部 Agent 能力证据和实际工具可用性如何采集、过期和展示。
6. 精确的团队级调配默认策略，以及桌面端和网页端的入口文案。

以上属于实现前需要确定的工程和产品细节；不改变本文的统一协作链路和用户约束优先原则。
