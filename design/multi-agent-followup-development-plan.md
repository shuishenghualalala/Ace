# Ace 多智能体协同：后续阶段开发方案

日期：2026-11-05  
状态：待讨论的实施计划；不代表各阶段已完成。

## 1. 目标与边界

以用户在团队对话中提出的任务为起点，让系统完成任务理解、适度拆分、按职责分配、真实执行、必要时补员、汇总交付，并让用户看得懂进展和需要处理的事项。普通用户只需提出任务；专业用户指定的成员、职责和约束应有明确的优先级及可追溯依据。

沿用[阶段 0 契约](multi-agent-refactor-phase-0-contract.md)的阶段编号：先完成阶段 2，再依次进行阶段 3、4、5。开发环境无需迁移旧任务；现有未提交改动需逐项审阅，不能直接视为已验收的实现，也不因重构而覆盖无关工作。每一批次尽量形成独立提交，每个阶段结束进行一次人工验收；阶段内可以有多个提交。

## 2. 当前基线与主要缺口

- 阶段 1 已有组队流程和相关提交，最终质量仍以实际组队、职责编辑及后续分配的联动验收为准。
- 阶段 2 已有任务快照、规划、统一分配、用户决策和计划版本的基础实现，内置与外部团队已接入规划服务。已有针对性测试，尚不能据此认定真实模型、知识库、真实委派和前端完整链路通过。
- 当前新规划结果仍通过适配层交给现有执行链路；现有代码中存在执行、补员与状态处理能力，是否适合复用要按本方案的契约核实，不能把适配等同于新执行内核完成。
- 规划交接已做重复认领保护，但认领后发生故障的恢复、执行意图和外部调用对账尚需完整设计与验证。模型对复杂任务是否充分拆分、是否识别全部用户约束，也仍需真实场景验收。
- 用户此前遇到的“选择后无法确认”“重新提问后阻塞”，需要结合对应会话记录与复现检查。现有静态判断不足以认定单一根因或宣称完全修复。

## 3. 阶段 2 收口：任务理解、拆分与分配

### 3.1 目标

从对话接收新任务及其输入，生成具体、可解释、可交接的计划。简单任务可以只生成一个单元；复杂任务按交付物和实际依赖拆分，不按成员数凑节点。

### 3.2 开发批次

**2A｜任务接入与输入契约**

1. 区分新任务、补充当前任务、状态查询和普通对话；消息归属确实有歧义时才询问。阶段 2 先覆盖新任务及规划中的补充，运行中改计划在阶段 4 完整实现。
2. 固化任务 ID、用户原话、团队与职责快照、本次明确指派和排除、附件与知识库引用；明确可见范围和 owner。界面选中知识库、传到规划记录以及实际执行可访问，是三个分别核实的环节。
3. 为选择知识库但成员无法读取、附件失效或权限不足提供具体提示，不声称已经读取；需要资料才能规划时明确询问或说明缺口。

**2B｜规划质量与统一分配**

1. 一条任务先产出工作目标、输入、输出、完成条件和必要依赖，再对每项工作统一分配。校验不存在循环、无效引用、重复标识和空泛的“按职责执行”工作。
2. 加入有界的计划质量检查：识别明显遗漏、重复及无依据的依赖；语义覆盖可通过模型复核并记录依据，但不能声称已数学证明任务完整。
3. 本次明确指定优先，其次用户配置职责，再参考已确认建议及合理推断；能力未知与能力缺失分开。模型提取的用户约束须对照原文和真实成员校验，未提取出约束仍有模型误差，需在验收中覆盖。
4. 用户回答写入对应决策，语义仍适用时复用；不依赖固定的历史问题 ID。模型失败或输出无效时有上限重试，仍失败则说明原因和可用操作，不生成假拆分。

**2C｜交接一致性与验收**

1. 计划、决策和分配持久化后才能交接；检查计划版本、团队快照和负责人。认领与执行计划落库之间的失败窗口必须有明确状态及恢复方式；保证不重复派发的前提和存储事务边界要写清楚。
2. 清理或更新旧规划测试：区分旧测试断言与真实回归，不为通过测试而删掉应保留的行为。针对真实模型、已有会话的异常和知识库输入开展联调；必要时记录模型失败及其可观察证据。
3. 向执行侧交付固定契约：任务/计划/单元 ID、负责人和依据、依赖、输入引用、交付要求、约束及版本。暂用旧执行器的部分须标注，不能绕过统一分配器。

### 3.3 阶段验收

- 只问一个简单问题，可得到一个合理工作单元；要求“查资料、分别分析技术和商业可行性、汇总”时，能看到具体工作和必要依赖，独立分析不因顺序被串行化。
- 用户指定“甲负责技术评审，乙不参与”时，计划和依据反映该约束；成员不可用不会静默换人。长期职责采用同义表达时也能合理分配；确有歧义时才追问。
- 同一追问答复重复提交不会产生重复决策；规划失败有可理解的说明，不显示虚假成功或按人数生成相同工作。
- 选知识库后，任务记录包含所选引用；实际能否读取由执行联调验证。核对一次真实运行的对话、任务记录、计划、分配和交接，而非仅看 UI 或模拟模型。
- 附上实际模型、测试数据、结果及未通过项；如果模型或服务不可用，记录阻塞，不用模拟结果替代真实验收。

## 4. 阶段 3：执行闭环与桌面主流程

### 4.1 目标

让已提交的计划按依赖真正委派给成员，保存每次尝试和成果，并让桌面界面与后端记录一致。优先完成固定团队的可靠执行，暂不把自动补员当成成功执行的前提。

### 4.2 开发批次

**3A｜调度与执行边界**

- 实现 scheduler：根据依赖、可用资源和并发上限决定就绪工作；业务依赖与资源排队分开。未解决的共享文件或外部副作用冲突不能盲目并行。
- 实现 dispatcher 和成员执行适配器：复用已有内置/外部成员执行能力，明确模型、工具、workspace、会话和 owner 的边界；新调度器不依赖整个旧 manager 作为 host。
- 每个工作包只携带相关目标、职责、必要资料、上游成果、约束和预期输出；保存实际输入引用，验证所选知识库是否传到对应执行器且可读。

**3B｜尝试、产物与状态**

- 建立独立的执行尝试记录：计划负责人、实际执行者、开始结束、输入、结果、错误和产物；重试生成新尝试，不覆盖历史。
- 状态、事件及待执行意图在明确事务边界内落库，再触发外部调用；持久化失败不能显示已派发。对外部副作用不承诺全局恰好一次。
- 结构检查、必要内容检查和实际结果共同决定工作是否完成；失败、未知、部分完成及待验收分别展示。一个工作等待时，无依赖且资源允许的工作继续。

**3C｜桌面体验与联调**

- 默认展示当前目标、成员正在做什么、成果、需要用户处理的问题；专业详情展开依赖、分配依据、尝试和实际执行者。看板减少嵌套框和深棕色块，延续现有简洁可爱像素风；以状态文本和适当色彩共同表达，不只靠颜色。
- 桌面端消费后端状态投影，不自行推断完成；关键操作显示结果、失败原因和可执行的下一步。
- 将截图中的项目评审场景作为真实联调样本，核对选择知识库、计划、派活、结果和状态；缺失项目资料时说明缺什么，而不是给每名成员一份相同的泛化工作。

### 4.3 阶段验收

1. 至少完成一项简单任务和一项有两个独立工作、一个汇总工作的任务；对照实际成员调用记录、工作包、看板和成果。
2. 两个无依赖任务在资源允许时能并行；存在依赖时下游收到上游成果后才开始。并发限制导致等待时展示为排队。
3. 指定成员真正收到对应工作；失败重试产生新尝试，不能由一段模型文本冒充所有交付完成。
4. 知识库可用时执行者能读取；无权限或不可用时有具体原因，不能编造读取结果。
5. 并发认领或持久化失败不会导致同一单元重复派发；独立失败或等待不会无故阻塞其他可运行单元。对不能查询的外部调用结果保留待核实状态。

## 5. 阶段 4：动态协作、补员与恢复

### 5.1 目标

在任务运行中，以明确原因和用户策略处理两类补员，并安全处理决策、变更、取消与恢复。

### 5.2 开发批次

**4A｜解决能力或工具缺口**

- 依据可验证信息区分必需工具缺失、成员不可用、执行失败和能力未知；未知时可尝试，不自动判定无法完成。
- 先检查现有成员和可用工具，再从用户允许的候选中选择；保留障碍、候选、依据、选择和任务级范围。找不到候选时明确阻塞及原因。
- 用户明确指定的负责人不可用时，提供适用的等待、重试、允许原成员尝试、更换或补员选项；确认按钮必须与实际选择状态、提交结果和去重逻辑一致。

**4B｜并行提速或质量提升**

- 仅在工作可独立拆分、结果可合并、输入和工具可访问、资源允许时建议补员；优先复用现有团队并发。
- 给出拟承担的具体工作、成本或资源影响及预期价值；没有实测数据不承诺具体提速。用户拒绝或无候选时，原团队继续，不制造阻塞。
- 临时成员默认只服务当前任务；新增未配置服务、修改长期团队或改变本次明确指派时，由用户决定。并发数、成本和临时成员数量有可配置上限。

**4C｜版本、决策与恢复**

- 将新增信息、改派、补员与任务变更写入新的计划版本；标明沿用的已完成成果，记录正在执行的工作如何处理。决策绑定具体工作和语义，过期答案不触发派发。
- 提供暂停/取消、重试及恢复：停止后不再启动新工作；外部任务能否撤销以执行器能力为准。进程中断后先核对执行记录；无法确认的外部操作标记待核实，由用户或明确策略决定。
- 检查 planning、handoff、执行意图提交、外部调用前后等故障窗口，明确恢复状态、允许动作和幂等范围；不假定所有系统都支持查询或幂等。

### 5.3 阶段验收

- 缺少必需工具时能说明具体缺口并找到可用候选，或明确无法补员；能力未知不会单独触发强制换人。
- 可以并行的工作能建议并行补员；拒绝后原计划仍能完成。临时成员不会悄悄进入长期团队。
- 选择不同选项均可提交，重复提交不会重复派发；回答后任务按所选动作推进，不能无限重复追问。
- 进程在多个故障窗口退出后，已完成工作不重复执行；外部结果不可核实时明确标识。取消后不再启动新工作，并如实展示已发出的外部操作。

## 6. 阶段 5：双端收口与旧链路退役

### 6.1 开发批次

1. 桌面和网页接入同一任务状态投影、决策和成果接口；分别检查不同屏幕尺寸、交互可访问性和异常反馈，保持各端现有视觉体系一致。
2. 清点新任务所有入口、旧规划/调度/补员分支以及仍被其他功能引用的代码。先切换并验证入口，再删除确认无用的实现；独立 Dynamic Kanban 等非团队协同能力按原用途保留。
3. 核对团队组建、团队对话、知识库、内置/外部成员、重新打开会话、取消及 owner 隔离。收集运行记录和已知限制，整理面向普通用户的操作说明与面向专业用户的调试信息。
4. 评估现有未提交修改：属于本次交付的分批审阅和提交；其他改动保留，不把未经确认的代码混入交付。

### 6.2 阶段验收

- 新任务只有一个权威的规划和执行入口，同一任务不会被新旧调度器同时处理；无需兼容旧任务。
- 桌面与网页对同一任务显示一致的目标、负责人、状态、成果和待办；刷新或重新打开后能从权威状态恢复展示。
- 覆盖只填队名、明确职责、简单任务、复杂任务、知识库、真实派活、两类补员、失败/恢复、取消、部分完成和多 owner 隔离。记录实际模型与执行器，无法验证的项明确列出。
- 完成端到端演示：从组队到发起比赛材料任务，查看计划、实际协作与成果，并能解释每次追问和补员。

## 7. 提交、验收与观测要求

- 一个批次聚焦一个可审查的行为或契约；阶段内允许多次提交。提交说明写明范围和影响，避免混入工作区已有的无关更改。
- 每阶段先完成接口、实现和针对性验证，再交用户人工验收。验收记录包含前置条件、操作、预期、实际结果、任务 ID、模型/执行器、关键事件与限制。
- 建议记录规划耗时、规划失败与重试、节点和依赖、分配来源、实际派发、追问次数、补员原因、尝试与结果；避免把敏感内容或密钥写入日志。
- 不提前承诺成功率和提速比例。收集可比较的真实运行数据后再确定质量门槛。

## 8. 建议实施顺序与待定事项

建议下一步从 **2A → 2B → 2C** 开始；阶段 2 达到验收条件后进入 **3A → 3B → 3C**，再实施 **4A → 4B → 4C** 和阶段 5。若真实运行发现阶段 3 的执行适配器阻碍阶段 2 联调，可以提前完成最小接口，但不因此把执行阶段视为已完成。

需要在相应批次结合实际实现确定：候选 Agent/工具的权威可用性来源；知识库对各类执行器的权限和读取方式；默认并发与资源限制；外部执行器的取消、幂等和对账能力；规划质量复核的模型成本与失败处理。这些均应在实现前形成明确契约和验收样例。
