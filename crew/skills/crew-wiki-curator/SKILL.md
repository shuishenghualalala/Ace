# Crew 笔记 Curator Skill

> 术语约定：Crew 笔记是对外产品名称；Wiki、知识库和 Wiki 知识库是兼容别名。三者指向同一套数据和工具，不要因名称不同创建重复内容。

本 Skill 为 Crew Wiki Agent 提供知识工程判断标准。系统提示词决定必须执行的步骤、确认边界与完成标准；本 Skill 解释每一步如何判断和做好，不替代系统流程。

## 三层知识结构

- **Raw Source**：附件、URL、会话或粘贴文本的不可变原始材料。保留来源、hash、采集时间和解析状态；内容变化应采集成新 source，不覆盖旧 source。
- **Wiki Page**：面向长期阅读与复用的实体、主题和来源摘要页面。概念、方法、原则和机制统一归入实体；页面允许增量更新、交叉引用和归档。
- **Schema**：SCHEMA、index、log、标签体系及质量约束。它们防止知识库随时间出现重复、漂移和失去导航。

## Vault 与素材分类

- 每个 KB 根目录都是可直接用 Obsidian 打开的 Vault。
- 原始素材只按类型分类：`articles / pdfs / words / excels / ppts / notes / sessions / images / videos / assets`。
- 微信、知乎、X、小红书和普通 URL 都属于 `articles`；平台写入 `source_platform`，不要创建平台目录。
- YouTube 字幕和视频信息属于 `videos`。
- 面向用户的知识页统一位于 `wiki/`；计划、缓存、来源元数据和 FTS 位于 `.crew/`。

写工具会自动维护 index、log、搜索索引和摘要失效状态；不要重复调用内部收尾能力。

## Orientation 的判断重点

在 ingest、深度研究、lint 或批量维护前，用 `wiki_orient` 了解：

1. KB 的领域边界、页面类型和标签约束。
2. index 中已有页面及其一句话摘要。
3. 最近日志中的新来源、重命名、归档和未解决问题。
4. 当前页面规模、source 数量、摘要状态与 lint 风险。

简单事实查询可直接 search/query；只有需要理解全局结构时才 orient，避免机械调用。

## 页面匹配与粒度

创建页面前按以下顺序匹配已有知识：

1. 规范化 title：去除无意义空白、大小写和常见标点差异。
2. 检查 aliases：简称、全称、旧名和中英文名命中都视为同一候选。
3. 比较 tags 与 page_type：标题相近但领域或类型不同，不应误合并。
4. 阅读候选正文与 related：确认语义对象相同后再更新。

判断标准：

- 一个实体在两个以上 source 出现，或是单一 source 的核心对象，才值得独立建页。
- 路过性提及、孤立数字和领域外信息留在上级主题页，不制造碎片页。
- 有匹配页时优先更新；标题略异不是新建理由。
- 页面超过约 200 行、包含多个可独立复用的子主题，或不同部分更新频率明显不同时再拆分。
- 拆分后保留概览与双向 related，避免产生孤立页。

## 元数据与溯源

- **aliases**：只保存真实可检索别名；去重后不得与其他页面的主标题或关键别名冲突。
- **tags**：优先复用 Schema 中的稳定标签；新标签必须表达新的长期分类维度，不能只是正文关键词。
- **related**：仅连接读者下一步确实会访问的页面；保持语义相关，不追求数量。
- **sources / provenance**：关键事实能追溯到 Raw Source。多来源综合时区分各来源支持的主张。
- **claims / evidence**：主张是最小可追溯知识单元；每条主张记录 `statement`，并通过 `evidence.source_id`、`locator` 和短摘录定位原文。禁止把模型推断伪装成来源主张。
- **confidence**：high 表示多个可靠来源一致；medium 表示来源有限但无明显冲突；low 表示单一、间接或时效性存疑。
- **contested / contradictions**：来源对同一事实给出不可兼容结论时标记，不要静默选择一方。

## 新旧来源冲突

1. 比较发布日期、事件发生时间、来源权威性和是否为一手材料。
2. 新来源是明确修订时，更新当前结论并保留旧结论的时间背景。
3. 两方仍都可能成立时，并列陈述范围、日期和来源，降低 confidence 并标记 contested。
4. 冲突影响核心结论或将覆盖大量内容时，把影响写进 plan，等待用户确认。
5. 不因“更新”二字直接覆盖历史事实；区分事实变化与来源观点差异。

## 批量 ingest 与归档

- 批量材料逐个 capture/parse，先基于 hash 去重，再合并规划，避免同一事实重复创建候选页。
- 已解析来源使用 `wiki_batch_ingest`，每次最多五份；按 `next_cursor` 继续，保留部分成功、跳过和失败事实。
- 不按素材长度设置固定的 Entity 或 Topic 数量上限。分块用于保留语义上下文，跨块结果按规范标题和别名合并；是否入库由质量、独立性、长期复用价值和证据完整性决定。
- 概览负责整体理解，知识导航提供完整目录。分页、批处理、模型输出 token 和查询上下文预算只是工程保护，不能解释为知识容量或展示配额。
- `wiki_plan_ingest` 采用轻量知识单元：每个单元只表达一个 subject 的一条可追溯主张，页面聚合、规范匹配和 create/update/skip/contest 由编译器确定性完成。不要要求它一次撰写完整页面或穷举材料中的所有名词。
- 富文本按语义分块提取；成功分块会持久化缓存，失败重试只处理未完成块。模型响应在最后一个 unit 中途截断时保留此前完整单元，不重跑整块。`analysis_stats` 中的 `total_chunks`、`analyzed_chunks`、`cache_hits`、`truncated_chunks` 和 `elapsed_ms` 是真实处理状态。
- plan 中明确 create、update、skip、冲突与影响页面。`wiki.ingest.auto_apply=true`（默认）时计划工具内部立即应用并返回实际结果；配置为 false 时才展示计划、停止并等待后续确认回合。
- 内容 hash 完全重复时停止知识编译，不重复创建 Source 或规范页面；同 URL 内容漂移时继续生成更新计划并保留历史来源。
- 归档用于内容被完整替代、明显过时或不再属于领域的页面。归档前检查入链、related 和正文 wikilink。
- 重命名或归档后修复链接；写工具负责确定性修复与索引同步，Agent 负责确认语义是否仍正确。
- 不将删除当作普通整理手段。可保留历史价值时优先归档。

## 查询结果何时沉淀

仅在用户要求沉淀，或研究结果同时满足以下条件时建议建页：

- 综合了多个页面或 source，而不是简单摘录；
- 结论未来会重复使用；
- 有清晰主题、证据和可维护的 related；
- 不与现有页面职责重复。

先向用户说明建议的页面归属；实际写入遵守页面维护边界，以及 ingest 的 `wiki.ingest.auto_apply` 配置。

用户明确要求跨来源对比或综述时使用 `wiki_digest`。Comparison/Synthesis 至少需要两个独立 RawSource；不足时返回知识缺口，不生成只有模型常识支撑的页面。

## Lint 严重级别与修复顺序

- **阻断**：Raw Source 丢失、页面无法解析、跨 KB 引用、索引与实际页面严重不一致。优先修复。
- **高**：断链、标题/别名冲突、来源缺失、未标记的明显矛盾。
- **中**：孤立页面、标签不在 taxonomy、低 confidence 长期未复核、摘要漂移。
- **低**：格式不一致、related 稀疏、可读性问题。

先生成 lint 结果与修复计划。批量修复、覆盖、归档或删除必须经一次性确认；不要为了消除低级告警制造更多页面或链接。

## 长期健康策略

- 定期合并近义重复页，限制标签膨胀，并检查无入链/无出链页面。
- 对时效性强的页面记录证据日期；新 source 到来时优先复核旧结论。
- 把 unresolved contradiction 和 low confidence 作为复核队列，而非隐藏问题。
- index 应保持可导航的一句话摘要，不承载正文。
- 查询优先规范知识页，按需沿 related/wikilink/共同来源扩展一跳；关键结论存在争议或低置信度时回读 Source Page 核验。
- log 记录发生了什么和为什么，避免重复决策。
- 查询无结果时明确知识缺口；不得用通用文件搜索或模型记忆替代 Wiki 工具。
