CCrew 桌面端设计文档

Electron + Vanilla TypeScript + esbuild · 对接 crew.gateway · 2026-06-29 建立

1. 定位

  • 桌面端是 crew.gateway 的本地外壳：维护会话、WebSocket 流、任务板，复用后端契约，不发明新协议。
  • 技术栈与 web/（React + Vite）不同：纯 TypeScript + esbuild，无框架、无虚拟 DOM，靠 diffRenderUnits 做局部 DOM 更新。
  • 设计参考 hermes-agent/apps/desktop 的交互理念（stickyBottom 滚动、折叠持久化、流式 markdown），但实现按本仓库 vanilla TS 形态重写，不搬运 React 代码。

1.1 开发与交付规则

  • 每次功能开发完成后，必须先完成可执行验证，再交付；若无法运行某项测试，需在交付说明中明确原因和剩余风险。
  • 每次功能更新必须同步记录到对应模块文档；桌面端前端功能优先记录在本文，涉及后端协议时再更新对应 docs/backend/modules/*.html。
  • 开发文档和测试记录集中放在对应模块文档或既有 docs/desktop/ 专题文档中；除非形成独立设计主题，避免为了单次小改新增零散文件。
  • 代码结构以模块边界为先：同一功能尽量收敛在已有 feature 子模块、样式模块和 typed API 封装内，避免临时脚本式调用和跨层循环依赖。
  • 可以参考 Hermes 等架构的交互和分层，但实现需按本仓库 Electron + Vanilla TypeScript 结构落地，不直接堆叠不合栈的代码。

3. 交互行为约定

3.1 折叠

  • 用户手动折叠/展开后状态写入 localStorage，跨重启保留。
  • 新工具调用到达 / 模型继续输出文字时，不再自动展开已被用户折叠的卡片或回合。
  • 无用户偏好时：工具时间线项默认折叠（仅展示标题与耗时）；思考项流式中默认展开、完成后默认收起；流式回合默认展开，完成默认折叠。

3.2 滚动

  • 流式输出过程中不强制跟随（no_follow）：用户在底部才跟随，向上滚即停。
  • 提交新消息 / 切换会话 / 重连后用 jumpChatToBottom 显式跳底。
  • 程序滚动不 disarm stickyBottom，只有真实 wheel/touch 上滑才 disarm。

3.3 Markdown

  • 引擎 micromark + gfm：支持表格、删除线、任务列表、autolink、嵌套列表、引用块等完整 GFM 语法。
  • 流式：先 preprocessStreamMarkdown 闭合半截语法，再解析，避免源码闪烁。
  • 正文与过程旁白统一由 chat-render.ts 按消息 streaming/interrupted 状态选择 renderMarkdownHtmlStreaming；有序列表项里的半截粗体（如 2. **F2. Fork...）也会在流式中临时闭合。
  • 安全：DOMPurify 白名单 sanitize；外链强制 target="_blank" rel="noopener noreferrer"。

3.4 会话级模型（Composer）

  • 设计手册：docs/desktop/per-session-model.md。
  • Composer #chat-model-picker-inline-btn 浮层走 PUT /api/session/{id}/model，仅影响当前会话；session busy 时 pending，UI 提示下条消息生效。
  • 设置页模型列表仅 CRUD，已移除「切换」；active_model_id 表示新建会话默认种子。
  • 模块：features/session-model.ts（setSessionModel、syncSessionModelUi、草稿种子）。

3.5 对话 busy 状态

  • Composer 是否显示「对话中」只读 busySessions，不直接等同于后端 live=running。
  • final/error 后保留 activeRequestId 用于拒收旧帧；如果状态同步又返回同一 request_id 的 running，视为 stale live，不复活 busy。
  • 追问、澄清、Plan 审批属于等待用户输入，后端可能仍持锁 running，但 UI 必须保持 idle，用户提交后再由 resumeSessionGeneration 恢复 busy。
  • 细节文档：docs/desktop/conversation-busy-state-review.md。

3.6 同步状态机基准

  • Desktop 当前以 session_id 路由会话、request_id 划分回合、gateway_sequence 做 replay 去重，重连时读取 /api/session/{id}/status.active_request_id 绑定正在执行的回合。
  • Assistant 正文 delta 以 body.delta_start/body.delta_end 作为文本顺序 span；chat-reducer.ts 在 Bookkeeping.deltaSpans 中按 span 排序重建正文，避免实时/回放交错时后到低序号文本被追加到尾部。旧后端无 span 的帧进入 legacyDeltaText，按原到达顺序兼容。
  • chat-reducer.ts 的 turn gate 必须先于消息写入执行：旧 request_id 的生成帧、等待帧、todo/file/task 附属帧不得污染当前会话状态。
  • followup_question、plan_review 属于等待用户输入；它们会封住当前流式回合并解除 busy，用户提交后再由原回合身份继续。

3.7 Composer 输入（IME 合成拦截）

  • #chat-input 的 Enter 发送需先经过 IME 合成状态判定，避免中文/日文/韩文输入法选字时误发送。
  • 实现位于 features/composer-input.ts，三层拦截：
    • event.isComposing === true 或本地 composition 状态为 true 时忽略 Enter。
    • event.keyCode === 229 时忽略（Chrome IME 事件特征）。
    • Safari 中 compositionend 先于 keydown 触发，用 justComposed 标记拦截确认选字后的那一次 Enter，下一宏任务自动清零。
  • Shift+Enter 始终用于换行，不影响发送判定。

3.8 工具生成中状态

  • Desktop 独立适配后端 tool/generating，不复用 Web 渲染实现。chat-reducer.ts 将 generating/start 按同一 tool_call_id 聚合，避免生成中和执行中出现两张工具卡。
  • chat-render.ts 对 generating 使用 running 时间线项样式（图标脉冲动画），标题优先展示 uiLabel，因此长 file_write content 生成期间可以显示「正在写入 path」。
  • 运行中工具项通过 250ms 轮询实时更新已运行时长（data-started-at + .process-timeline__duration[data-active]），改善写文件等长耗时操作的感知性能。
  • 后端实时帧与历史回放都会裁剪 file_write 参数，Desktop 只接收 path/file_path/append 等展示字段，不接收完整 content。
  • pet-gateway-schema.ts 将 generating 映射为宠物侧 tool start 信号，并优先使用 ui_label，保持桌面宠物反馈不晚于主窗口。

3.9 看板 / Inspector 视觉

  • 右侧入口 #task-board-toggle：图标 + 竖排「看板」标签；颜色走 --shell-primary / --surface / --border-subtle，随亮暗主题切换。
  • --shell-primary* 映射到主题 --accent*，避免硬编码浅蓝在 dark/sepia 下失配。
  • 展开壳 Tab、会话信息网格、用量条、空态统一用语义 token；去掉虚线堆砌与紫渐变进度条。
  • Inspector 新增「协作」Tab，仅在 provider=team 或存在外源 Team 绑定的 Team Session 显示；普通 MobileWork 与外部单 Agent Session 不展示。Team Session 打开看板时默认进入「协作」。
  • 「协作」用 Desktop TypeScript DOM 重现 Web TaskBoard：协作看板标题 / Team Flow、产物文件抽屉、团队 DAG Hero、成员与 Leader、回合与依赖分层、节点状态与摘要、产物、执行详情、取消节点、错误提示和运行态均使用同一信息结构和视觉参数。
  • 成员说明复用 Web 的职责摘要规则：优先提取 Markdown「职责」区块，过滤工作原则、协作关系、输出格式和工作安排，只保留一条简短业务职责。Desktop 内置 Leader 按桌面产品身份显示为 MobileWork，头像复用 crew-ui-symbols.svg#avatar-headphones Q 版耳机机器人；这是相对 Web「Crew 内置智能体」的有意桌面端差异。
  • 看板每 2 秒读取当前 Session 的 task 与 runtime 快照；只在「协作」Tab 激活时轮询，离开 Tab、切换非 Team Session 或关闭 Inspector 后立即停止，避免后台冗余请求。
  • 既有 Kanban / Files / Context / Plan / Browser Tab 保持原实现；协作样式全部收敛在 .team-collaboration-board 作用域，避免影响 Desktop 其他页面。

3.10 Team Session 成员消息

  • Desktop 直接消费 Gateway 既有 team_internal 协议，不增加 Desktop 专用后端接口；chat-reducer.ts 将该帧纳入 request gate 与 replay 去重，避免旧回合成员消息污染当前回合。
  • 实时流与 Web 使用同一合并语义：相同 Team turn、相同 DAG node 的 team_stream 增量合并为一张成员卡；team_submit/team_review/team_summary/team_decision 到达后替换过程卡，同时保留 thinking、工具时间线和可折叠执行过程。
  • history-mapping.ts 保留成员身份、角色、tone、mention、node、display mode、过程和产物字段；历史回放与实时消息走同一个合并函数，不再把 team_internal 降级为普通 status。
  • chat-render.ts 使用原生 TypeScript DOM 重现 Web TeamAgentTurnBubble：成员名/角色、低饱和 tone 气泡、执行过程折叠、工具调用、产物卡和流式状态保持同一信息层级，不引入 React。内置成员按 Desktop 身份显示为 MobileWork 并复用 crew-ui-symbols.svg#avatar-headphones，外部成员使用团队 tone 头像。
  • Team 不新建第二套回合组件：team_internal 先转成 Agent Turn 渲染数据，然后复用 renderAgentTurn()、resolveTurnDurationMs() 和现有每秒 ticker。单 Agent 与专家团的原分支不改。
  • 规划运行中默认展开过程区，折叠标题以本地 ticker 实时更新“已等待”；规划完成后固化最终耗时并自动折叠。规划使用 Team Logo，成员/Leader 正式发言继续按真实身份显示。
  • Team transport status 仅更新 Session 运行态，不进入普通 assistant 气泡；需要呈现的规划、thinking、工具和节点过程统一由结构化 team_internal 进入同一 Agent Turn Timeline，避免 Leader 结论后多出独立思考气泡。
  • Team 实时分片沿用主聊天的 sticky-bottom 软追随：用户上滑后不再被后续分片拉回底部；Team thinking 取消独立内滚动并复用单 Agent 的增量/累计文本合并，避免重复和横向溢出。
  • 团队身份在首发前从现有 Team 配置预热：规划 Turn 展示团队名称与黑白 Team Logo，不显示 Leader 角色；逻辑 leader 从第一帧起映射为真实成员。协作看板轮询内容不变时不重建 DOM，保留用户滚动操作。
