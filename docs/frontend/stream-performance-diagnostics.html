流式首 token 性能诊断

该诊断用于区分模型 TTFT、Ace 网关转发和桌面端渲染耗时。埋点只记录时间、请求标识和请求规模，不记录 prompt、回答正文或密钥。

开启方式

  1. 桌面端 DevTools Console 执行 __mmStreamDebug.enable()，然后刷新页面。
  2. 发送一条消息，执行 __mmStreamDebug.dump() 查看最近事件，按同一个 request_id 串联。
  3. 关闭时执行 __mmStreamDebug.disable()。

关键事件

  • dispatch / send-ws：桌面端发起时间。
  • gateway_request_received：网关接收时间。
  • llm_first_event：provider 首个流事件，包含模型首 reasoning、正文或工具事件类型。
  • llm_first_text：provider 首个正文增量。
  • gateway_first_push：网关完成首帧 WS 推送。
  • ws-renderer / proxy-event-message：桌面端收到 WS 帧。
  • ttft-first-text-received 记录该请求的首个非空文本增量抵达 Renderer，包括随后被回合门控或分片重组拒绝的帧。
  • ttft-first-text-accepted 表示首个可显示文本已通过回合校验及顺序重组，并实际更新了对应助手消息的正文。foreground 记录此时对话面板是否处于前台。
  • ttft-first-text-mounted 表示已从当前前台对话找到同一助手段落的正文元素。此时该元素已挂载、可显示且包含文本。source=patch 对应增量写入，source=render 对应会话重绘后的观察。
  • ttft-first-paint-opportunity 表示连续两次动画帧回调均确认同一会话和正文元素仍在可显示的文档中。这个时间点衡量浏览器的绘制机会，实际屏幕像素时间需要合成器或显示设备侧测量。

四个阶段共用本地发送时刻计算 elapsedMs。按 send-ws 中的 requestId 与各阶段的 request_id 关联。建议在发送前开启诊断。每个会话仅跟踪本地最近发送的一轮，保留最多 80 个会话；缺少可关联请求 ID 的旧协议帧可从普通接收日志查看。账号或回合切换后会重新校验归属。后台收到正文时先记录接纳，切回并成功渲染后才能记录前台阶段。

判读

  • llm_first_event 本身很慢：主要是模型/上游服务或请求负载问题。
  • provider 首事件很快、gateway_first_push 明显变慢：检查网关发送限流或连接状态。
  • 网关已推送、接收后迟迟未接纳时，检查回合门控与分片重组。接纳后挂载较慢时，检查前后台切换、Markdown 渲染和主线程占用。
