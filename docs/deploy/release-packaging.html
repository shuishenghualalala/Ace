Crew / 部署与发布

三平台桌面发行包发布

macOS、Linux（UOS / Kylin）、Windows 安装包的制作内容与 GitHub Release 发布流程。

打包架构

安装包内 gateway 以源码形态携带（不再是 PyInstaller 二进制）：desktop 主进程用安装包内嵌的 Python 以 python -m crew.gateway.server 直接启动（CREW_PACKAGED=1 标记打包态）。gateway 与技能脚本共用同一个内嵌 Python，消除了原先 PyInstaller 解释器与技能运行时重复携带一套 Python 的体积浪费。

目录内容
crew-gateway/crew/gateway 源码全量（含 skills/scenarios/mcp_servers，排除 __pycache__）
crew-gateway/plugins/内置插件
crew-gateway/config/仅 .env.example、config.yaml.example、prompts/；构建期有安全检查，真实 .env / config.yaml 出现即失败
crew-gateway/runtimes/python/python-build-standalone 3.11.9 + gateway 依赖 + 技能依赖（pandas/pikepdf/pdfplumber 等）
crew-gateway/runtimes/node/Node.js 20.18.3 portable（裁剪 corepack/docs，保留 npm 供 docx/webapp 技能使用）
crew-desktop/Electron 桌面端（locales 只保留 en-US / zh-CN；macOS 保留 en/zh_CN/zh_TW lproj）

内嵌 Python 依赖的唯一数据源：pyproject.toml（核心 dependencies + wiki/pdf/docx/xlsx extras）与 deb-package/runtime-requirements.txt（技能脚本补充依赖）；markitdown 以 --no-deps 单独安装（其可选依赖链超 100MB）。运行时缓存（dist/runtimes-cache）以依赖清单哈希为戳，不变则跨构建复用。

发布入口

仓库新增 workflow .github/workflows/release-desktop.yml，两种触发方式：

方式触发条件说明
自动推送 v* tag（例如 v1.1.0）同时构建四个任务并上传到对应 GitHub Release
手动Actions 页面选择 release-desktop，填写 tag 输入适合打包已存在的旧 tag，例如 v1.1.0
自动触发只对“包含该 workflow 的提交上打出的 tag”生效。仓库中已存在的旧 tag 不会自动触发，需要用手动方式，或先合入代码后打新 tag。

发布产物

平台产物组成
macOS arm64 crew-desktop_<版本>_arm64.dmg Electron 桌面端 + gateway 源码树（内嵌 Python 直跑）+ 内嵌 Python/Node 运行时 + macOS 安全运行组件
macOS x64 crew-desktop_<版本>_x64.dmg
Linux UOS crew-desktop_<版本>_uos_amd64.deb /opt/crew-desktop（Electron + bwrap + 安全运行组件）+ /opt/crew-gateway（源码树 + 内嵌运行时）
Linux Kylin crew-desktop_<版本>_kylin_amd64.deb
Windows x64 Crew_Setup_v<版本>.exe win-unpacked 桌面端 + gateway 源码树与内嵌 Python/Node 运行时 + Windows 安全运行组件，Inno Setup 安装器

Release 同时附带 SHA256SUMS 校验文件和各平台体积报告。

打包内容约定

三个平台的安装包都不包含 web/ 目录及其构建产物 web/dist。桌面端界面来自 desktop/dist；Gateway 缺少 web 静态资源时，浏览器直连管理台显示“前端未构建”占位页，桌面端功能不受影响。

内置 skills 随安装包以源码携带于 crew-gateway/crew/skills，首次运行时释放到 ~/.Crew/skills；用户自定义 skills 保留在用户目录，安装包不覆盖、不写入用户数据。docs、测试、桌面端源码、本地配置与密钥一律不进包。

桌面端「更新」按钮的下载指向

桌面端设置页「关于我们」里的「更新」按钮，点击后由主进程请求 GET https://api.github.com/repos/shuishenghualalala/Ace/releases/latest，按当前系统/架构匹配对应安装包并打开下载页：

当前系统匹配产物
macOS（Apple 芯片 M 系列）crew-desktop_<版本>_arm64.dmg
macOS（Intel）crew-desktop_<版本>_x64.dmg
Linux 麒麟 Kylin（amd64）crew-desktop_<版本>_kylin_amd64.deb
Linux 统信 UOS / 其他发行版（amd64）crew-desktop_<版本>_uos_amd64.deb
Windows 10/11（x64）Crew_Setup_v<版本>.exe

Release 发布后会自动生成「平台选择表 + SHA256 校验说明」的 release notes，桌面端按钮的匹配逻辑与之一致。查询失败或无匹配资产时，按钮回退到 GitHub Releases 列表页。

按钮指向与分支无关：/releases/latest 是仓库级接口，始终返回该仓库最新发布的正式 Release（自动跳过 prerelease 与 draft），无论当前代码在 dev 还是 main 分支，按钮下载的都是仓库最新的正式版，而不是“当前分支的版本”。
内测版发布建议：若用 dev 分支发布内测版本、又不想让正式用户从「更新」按钮下载到它，给该 Release 打上 prerelease 标记即可（gh release create vX.Y.Z --prerelease ...）。prerelease 不会被 /releases/latest 返回，正式用户按钮不会指向它；main 分支发布正式版后按钮自动指向正式版。

发布步骤

自动发布（推荐）

git checkout main
git pull
git tag v1.1.0
git push origin v1.1.0

推送后进入 GitHub Actions 的 release-desktop 运行页观察四个构建任务，完成后 GitHub Release 自动生成并附带全部安装包。

手动发布旧 tag

进入 Actions 页面，选择 release-desktop，点击 Run workflow，在 tag 输入框填写 v1.1.0，分支选择包含该 workflow 的分支（例如 main）。workflow 会检出该 tag 并使用其代码打包。

注意事项

  • 当前产物未做 Apple 签名与公证，macOS 首次打开需要右键打开；Windows 侧未做 Authenticode 签名时 SmartScreen 可能拦截。
  • 每个构建任务都在目标原生平台 runner 上执行，不做交叉编译。
  • Linux 构建依赖 Docker，Windows 构建依赖 Inno Setup 6，workflow 已自动安装。
  • 打包脚本已不依赖本机 Python 环境（无需 .venv / uv / PyInstaller），仅需 Node 22+ 与 Rust 工具链；内嵌运行时与依赖由脚本自动下载安装。
  • 本地运行 pack_exe.ps1 时如遇 electron-builder 下载超时，脚本已内置 npmmirror 镜像（可用 ELECTRON_MIRROR / ELECTRON_BUILDER_BINARIES_MIRROR 环境变量覆盖）。
