Ace 安全系统

从产品模式到操作系统边界 · 面向开发者的技术分享与架构导读

Ace 的安全模块不是一个“危险命令关键词列表”，而是一条由宿主掌握的执行链：先从可信会话状态构造权限上下文，再对具体动作做授权判断。请求批准与替我审批会把命令交给原生运行组件，由操作系统限制文件、网络和进程能力；用户明确选择完全访问权限时则以宿主用户权限执行，仅保留不可覆盖的破坏性 hardline、显式拒绝规则、进程回收与审计。

先记住一个结论：请求批准与替我审批使用受管原生沙箱；完全访问权限是用户显式选择的宿主权限模式。完全访问不逐项申请目录或网络权限，但文件系统根删除、磁盘格式化、无条件清空数据库、关机等永久 hardline 仍不能执行。

1. 十分钟全景

Ace 把安全职责拆成五层。每一层只相信上游提供的结构化结果，并在缺少必要事实时失败关闭。

身份层从已认证账号、工作空间存储和运行时上下文中取得 OS 用户、owner、workspace、session、task 与 cwd；不接受模型自行声明权限边界。
决策层把命令、文件或网络动作规范化并计算摘要，依次检查不可变策略、永久拒绝、基础权限、永久允许和临时授权。
交互层需要用户选择时创建有时效、nonce 和上下文绑定的审批请求；工具调用原地等待，批准后继续，拒绝或超时则停止。
执行层Gateway 将受管 profile 编译为原生运行请求，Rust helper 在 Linux、Windows、macOS 上建立真实的文件、网络和进程边界；完全访问 profile 则明确走宿主执行。
证据层安全中心展示 live probe 结果、永久规则和审计事件；发布流程校验 helper 的平台、架构、摘要与源码漂移。

1.1 当前已经提供的能力

会话级安全模式

请求批准、替我审批、完全访问权限；模式变化会使旧的待审批失效，并停止仍使用旧启动快照的活动 turn。

动作与权限审批

支持仅这一次、本次对话、始终允许此操作、拒绝；审批同时绑定精确动作、额外文件/网络权限与 owner/workspace/session/task。

原生文件沙箱

前两档采用广泛只读基线，工作空间和系统临时目录可写；Ace 私有数据与项目元数据由结构化工具和各平台后端分层保护。

受管网络

命令默认不能直接出网；联网按精确主机、端口、协议进入代理，并执行私网与元数据地址检查。

进程生命周期

超时、取消、协议错误和输出超限都会回收 helper 与子进程树，避免命令脱离会话继续运行。

安全审计

记录授权来源、动作摘要、规则生命周期和稳定错误码；按 owner 隔离、敏感信息脱敏、默认保留 30 天。

运行组件完整性

固定位置发现 helper，验证 manifest、平台架构和 SHA-256；开发预编译产物额外检测 Rust 源码漂移。

安全控制面鉴权

安全 API 除登录态外，还要求 Desktop 实例生成的短时单次 HMAC 证明，网页不能只凭 Cookie 修改规则。

2. 安全模块解决什么问题

Agent 可以生成 shell、读写文件、启动后台进程和访问网络。如果只靠提示词或命令名称判断风险，换一种 shell 写法、借助子进程或利用符号链接就可能绕过。因此 Ace 把“模型想做什么”和“操作系统最终允许什么”分开。

需要防住的风险Ace 的控制点
模型伪造工作空间、账号或当前目录SecurityContext 从 Gateway 认证信息、owner 级 workspace store 和 host contextvars 重建。
审批 A，执行成 B动作规范化后绑定 argv、原始 shell 文本、cwd 等关键事实；额外文件/网络权限独立绑定到请求、grant、永久规则和最终启动快照。
命令绕过 Python 工具检查所有受管进程最终进入原生运行组件，操作系统边界不依赖命令名称。
子进程修改工作空间外文件或读取 Ace 私有数据宿主文件系统默认只读，写入只授予工作空间、临时目录和明确获批路径；Ace 私有数据由更具体 deny 重新覆盖。
进程直接联网绕过业务规则沙箱只允许到本次受管代理的路径；代理再检查目标并固定 DNS 解析结果。
审批被重放或跨会话复用审批请求有 nonce、TTL、精确上下文和一次性消费语义；once grant 使用后立即删除。
替换随应用或仓库提供的安全 helper运行前校验固定路径；产物 manifest 存在时强制核对目标平台/架构和二进制 SHA-256。
威胁模型边界：原生运行组件共享宿主内核，它是会话级进程隔离，不是虚拟机，也不承诺抵御内核漏洞、管理员/root 权限攻击或已控制宿主账号的攻击者。

3. 三种模式：同一套沙箱，两种审批策略，一个宿主模式

理解 Ace 模式最重要的一点，是把“何时询问用户”和“进程最终能做什么”分开。前者是审批策略，后者是执行边界。请求批准与替我审批虽然提示频率不同，但使用相同的 workspace-write 原生沙箱；完全访问权限才会取消文件与网络沙箱，转为宿主用户权限。

3.1 两个受管模式共享什么

settings_for_mode 会把请求批准和替我审批都编译成 PermissionProfileKind.MANAGED，并设置 full_disk_read=true。这不是“全盘完全访问”，而是宿主文件广泛可读、只有明确根可写：

  • macOS/Linux 的普通宿主文件默认只读；Windows 枚举系统目录和用户目录中的非敏感顶层路径作为可读根，不递归改整盘 ACL。
  • 当前工作空间、TMPDIR/TEMP 和平台临时目录可写。
  • .git、.agents、.crew 等项目元数据重新覆盖成只读。
  • Ace 数据库、认证、配置、审计、日志和 owner 凭据路径使用更具体的不可升级拒绝。
  • 网络是独立能力：能读文件不等于能联网；没有精确网络规则时，命令保持离线。
受管模式基础视图

宿主文件系统  ───────────────────────────────► 广泛只读
当前工作空间  ───────────────────────────────► 读写
系统临时目录  ───────────────────────────────► 读写
项目元数据    ───────────────────────────────► 只读覆盖
Ace 私有路径  ───────────────────────────────► 拒绝覆盖
网络          ───────────────────────────────► 默认关闭，按目标开放

因此，“批准一条命令”和“让命令离开沙箱”是两件不同的事。普通批准只允许动作开始，命令仍受上述文件和网络边界约束；只有审批界面明确显示额外权限或脱离沙箱时，执行能力才扩大。

3.2 请求批准：让用户控制动作发生的时机

请求批准适合需要审阅 Agent 行为、处理陌生仓库或执行高影响任务的场景。它采用受管沙箱，同时把主动变更的决定留给用户。

动作是否询问批准后的执行方式
读取工作空间或项目外普通文件不询问按广泛只读基线读取；Ace 私有路径和显式拒绝路径仍不可见。
结构化文件写入、补丁、删除每次询问工作空间内动作仍由基础可写根约束；项目外写入同时携带精确路径 overlay。
Agent 发起的终端命令每条询问默认以 use_default 留在原生沙箱中执行。
应用内公开 HTTP 或终端联网询问应用 HTTP 按精确目标放行；终端必须声明精确网络权限后进入受管代理。
私网、监听端口、项目外写入、脱离沙箱明确询问并展示范围只把已展示的路径、目标或命令写入本次启动策略。
示例：Agent 要执行 npm test

Desktop 先展示完整命令与 cwd。用户点“仅这一次”后，Ace 消费一次性 grant，重新从当前模式编译 ProcessLaunch，再由 Native Runtime 启动命令。命令可以读取系统依赖并写工作空间/临时目录，但不能改写项目外文件或直接联网。

3.3 替我审批：自动化的是决策，不是权限

替我审批适合日常可信项目。它和请求批准使用完全相同的受管 profile，差别仅在 ApprovalPolicy.AUTO_REVIEW：安全服务可以自动确认“现有沙箱本来就允许”的低风险动作。

自动放行仍需用户批准
普通文件读取项目外写入或额外文件权限
工作空间/临时目录内的结构化操作终端新增精确网络权限或监听本地端口
分类为可在当前沙箱内执行的终端命令危险命令分类、私网目标和额外网络能力
应用内经过公开地址校验的 HTTP 请求require_escalated 脱离沙箱执行

启用替我审批前，Gateway 必须完成真实 Native Runtime live probe。探针会证明项目外普通文件可读、项目外不可写、工作空间可写、项目元数据不可改写；探针失败时模式切换返回错误 ACK，不会只更新界面文字。

示例：Agent 修改工作空间代码并运行测试

结构化补丁和沙箱内测试命令自动通过；如果测试脚本随后尝试写入 ~/Documents，操作系统沙箱会拒绝。Agent 必须重新提出带精确目录权限的请求，用户批准后该目录才进入启动 overlay。

3.4 完全访问权限：明确切换为宿主执行

完全访问权限不是“更宽的 workspace-write”，而是 PermissionProfileKind.DISABLED。compile_process_launch 不再附带 Native Runtime helper，进程直接继承当前 Ace 宿主用户在操作系统上的文件与网络权限。

  • 普通动作不逐项询问，工作空间外文件和宿主网络不再由原生沙箱拦截。
  • 宿主 OS ACL、文件所有权、企业策略等仍然有效；Ace 不可能越过宿主用户本身没有的权限。
  • 永久 hardline、用户创建的显式拒绝规则、进程树回收、输出脱敏和审计仍执行。
  • 受管模式中的 Ace 私有路径 deny 不再作为文件沙箱规则生效，因此这是需要用户明确确认的高信任模式。
风险提示：完全访问下，一条普通 shell 命令理论上可以访问当前用户可访问的所有文件和网络资源。它应当用于用户理解并信任当前任务、且逐项授权会实质阻碍工作的场景，不应作为排查普通路径权限问题的默认开关。

字段含义审批与执行

3.7 模式切换为什么以 Gateway ACK 为准

Desktop 选择模式后不会先假定成功。Gateway 校验上下文与本机能力，更新 SecurityService 中的会话模式并返回 ACK；只有 ACK 成功，界面才展示新模式。模式变化会撤销旧模式下尚未处理的审批，并停止继续使用旧 ProcessLaunch 快照的 turn。下一轮执行重新从安全服务编译策略。

模式切换不会撤销用户已经明确授予的本次对话权限；这些 grant 绑定 OS user、owner、workspace 和 session，在真正结束会话、登出或 Gateway 重启时清理。完全访问只作用于当前会话；空白输入框中的选择是即将创建会话的一次性预设，不会静默继承给后续会话。

3.8 实际使用时怎么选

场景建议模式原因
第一次打开陌生仓库、审计脚本、处理敏感项目请求批准每条命令和变更都经过人眼确认，同时保留广泛只读能力，Agent 仍能完成分析。
日常维护自己的项目、连续改代码和跑测试替我审批工作空间内自动工作，越过文件或网络边界时再询问，减少无意义打断。
可信任务确实要操作多个宿主目录、系统工具或复杂本机网络完全访问权限避免反复声明大量精确权限，但需要接受宿主级访问风险。
只有一条可信命令确实无法在沙箱内完成保持受管模式，使用 require_escalated只扩大这一条完整命令，不把整个对话切到完全访问。
推荐默认值：陌生任务从“请求批准”开始；确认工作流稳定后切到“替我审批”。只有任务本身需要宿主级能力时才使用“完全访问权限”，不要把它当作修复普通文件权限问题的办法。

4. 授权模型：动作、规则与临时能力

4.1 先把动作变成稳定事实

NormalizedAction 是授权系统的共同语言，分为 exec、file 和 network。它先解析绝对路径、规范化主机名与协议，再计算 SHA-256 摘要。命令需要越过基础沙箱时，还会携带独立的 AdditionalPermissionProfile；两者共同决定授权是否匹配。

动作摘要绑定的关键字段防止的问题
命令最终 argv、用户可见 shell 文本、cwd审批后替换参数、目录或整段脚本。
文件规范化路径、read/write/patch/delete、offset/limit、写入内容摘要把已批准的读取变成写入，或在审批后替换写入内容。
网络精确 host、port、protocol用 wildcard、URL path 或协议变化扩大联网权限。

4.2 判定顺序

不可升级的拒绝
   ↓ 未命中
当前 owner + workspace 的永久 DENY
   ↓ 未命中
基础 profile（受管模式工作空间）
   ↓ 未覆盖
最具体的永久 ALLOW
   ↓ 未覆盖
once / session 临时 grant
   ↓ 未覆盖
替我审批的工作空间内命令自动执行；完全访问直接放行
   ↓ 否则
创建审批请求并等待用户

规则冲突时先比较具体程度；同等具体时拒绝优先。这个顺序保证一条更宽泛的允许不能盖过明确拒绝，也保证不可升级的 Ace 内部路径不能被后续授权打开。

4.3 四种审批结果

选择实际产生的权限何时失效
仅这一次当前完整动作和已展示权限的单次 grant。成功匹配一次后消费，或审批 TTL 到期。
本次对话文件目录覆盖后代、文件仅覆盖自身、网络按精确目标复用；脱沙箱仍绑定完整命令与 cwd。会话真正结束、登出或 Gateway 重启；切换模式不会撤销。
始终允许此操作持久保存完整规范化动作；旧 exec-prefix 允许规则停用，尾随参数变化必须重新批准。按 owner/workspace 隔离，直到用户禁用或删除。
拒绝不创建权限，并建立短暂拒绝冷却。冷却结束后可以重新发起新审批。

审批请求本身有随机 nonce、有效期、上下文、动作摘要和额外权限。Desktop 会逐条显示额外文件根、访问级别、精确网络目标与本地监听能力；提交决定时必须同时满足登录 owner、workspace、session、task 与 nonce。动作相同但权限范围不同的请求不会复用同一个 pending、grant 或永久规则。

4.4 一次批准如何真正进入执行边界

旧问题的根源是“UI 记录了允许，但实际执行仍拿旧沙箱策略”。现在审批结果不是提示状态，而是一份可执行权限数据。完整链路如下：

1. Agent 提交动作
   └─ NormalizedAction + AdditionalPermissionProfile

2. SecurityApprovalService 判断需要审批
   └─ 创建 request：action digest + 权限范围 + nonce + 上下文

3. Desktop 展示并提交 decision
   └─ Gateway 校验 owner/workspace/session/task/nonce

4. 后端生成 grant 或 exact rule
   └─ once / session / always 的作用域各自落地

5. 工具用同一个规范化动作重新授权
   └─ 命中 grant/rule，取回获批 AdditionalPermissionProfile

6. compile_process_launch 重新读取当前会话模式
   └─ base PermissionProfile + 获批 overlay

7. SecurityExecutionBroker 编译原生请求
   └─ writable/readable/readonly/denied roots + network rules

8. Native Runtime 建立 OS 边界后启动命令
   └─ 批准的能力在这里才真正生效

目录授权可以覆盖其后代，单文件授权只覆盖该文件；只读授权不能匹配写入请求。网络授权按 host、port、protocol 精确匹配。require_escalated 是唯一把当前命令编译成宿主执行的普通审批类型，而且即使选择“本次对话”，仍必须匹配完整命令和 cwd。

4.5 四个按钮不是四种安全模式

会话模式回答“默认如何审批和执行”，审批按钮回答“当前已经展示的动作要记多久”。两者是正交关系：请求批准和替我审批都可以产生 once/session/always 授权；完全访问通常不产生逐项审批。

按钮动作记忆权限记忆不会发生什么
仅这一次仅当前完整动作，匹配后消费。仅当前请求展示的路径/网络/监听或执行边界。不会自动允许第二次相同动作。
本次对话无额外权限的动作仍精确匹配；脱沙箱命令精确匹配。目录、文件和网络范围可在当前 owner/workspace/session 内复用。不会跨对话、跨 workspace 或跨账号复用。
始终允许此操作保存完整规范化动作摘要。同时保存该动作获批的精确 overlay。不会因相同 argv 前缀而允许额外尾随参数。
拒绝不创建动作授权。不创建任何权限，并进入短暂冷却。不会写入一条允许规则。

5. 文件系统：结构化工具与任意命令的双层边界

文件访问存在两条路径：内置 file/patch/search 工具先走 Python 结构化策略；请求批准与替我审批下的 shell 或外部适配器最终走原生运行组件。前者能理解具体“读、写、补丁、删除”，后者负责防止任意子进程绕开工具层。完全访问权限不应用下述受管目录边界，只保留文件系统根写入与终端永久 hardline。

5.1 基础权限

  • 项目会话把项目根设为可读写根；未选择项目的普通会话使用 owner 隔离的 task_workspaces/<workspace-id> 作为有效工作目录和可写根。系统提示会把这个 host 生成的 cwd 明确标为可信起点；沙箱私有 HOME/USERPROFILE 只用于隔离，不可用来反推工作空间。cwd 必须位于该根内，不能再出现“进程 cwd 已落到任务目录、沙箱却没有可写根”的断链。
  • 路径在判断前会解析为最终规范路径；符号链接、junction 和 TOCTOU 交换由文件工具与平台测试覆盖。
  • 写文件系统根目录被永久拒绝。
  • 在请求批准与替我审批中，Ace 数据目录、security DB 及其 WAL/SHM/journal 属于不可升级拒绝。
  • 在请求批准与替我审批中，workspace 下的 .git、.agents、.crew 是不可升级的只读元数据；结构化文件工具和任意受管 shell 都能读取，但不能创建、修改、重命名或删除。

5.2 权限合并规则

基础 profile 与用户追加授权按路径具体程度合并：更深的路径比父目录更具体，同等具体时 deny 获胜；标记为 escalatable=false 的拒绝和只读项永远不能被追加授权升级为写入。终端只能申请已存在的精确文件或目录；创建新文件时申请已存在的父目录，文件系统根写入永不开放。

原生命令的只读 carve-out：Broker 把不可升级的 READ entry 编译为协议字段 readonly_roots。helper 握手必须声明同名能力，否则 Gateway 按协议不兼容失败关闭。Linux 在可写 bind 之上重新挂载只读路径；Windows 为账户与 capability SID 同时授予读取并拒绝写入/删除；macOS 在 writable allow 之后为目标本身与子路径追加 deny file-write*。路径必须位于显式可写根内，符号链接/reparse point 会被拒绝；路径尚不存在时仍保护“创建目标本身”。

6. 进程执行：所有受管命令汇聚到一个边界

compile_process_launch 在每个 turn 入口根据可信上下文编译一次 ProcessLaunch。审批通过后，命中的 grant/rule 把额外权限写入该启动快照；前台、后台进程和 captured adapter 都把同一 overlay 交给 Native Runtime。终端还支持 use_default、with_additional_permissions 与 require_escalated：最后一种必须提供原因并单独批准，只让当前完整命令脱离沙箱，不会切换整个对话模式。

默认任务目录可能位于受保护运行时 home 的更深层。Broker 会在前台和后台共用同一个文件计划编译器：当一个 deny 是已认证工作区或已激活 Skill 只读根的严格祖先时，不把这个冲突的祖先 deny 交给原生后端；精确 deny、工作区内受保护元数据和 deny 的子路径仍保留。各后端保持 default-deny，因此该 carve-out 不会让同级凭据、数据库或其他 owner 目录变成可见资源。

6.1 失败关闭

  • 缺少 ProcessLaunch 时，受管适配器拒绝执行，不回退到当前 Python/Electron 用户权限。
  • helper 缺失、完整性错误、握手失败、能力不足、协议乱序或异常退出均返回稳定错误码。
  • 一个 monotonic deadline 覆盖启动、请求、输出和退出全过程。
  • 取消、超时、输出超过上限和协议错误都会终止 helper 及其进程树。
  • 原生协议具备双向 stdio 能力；尚未接入该 transport 的外部 adapter 会明确拒绝或使用已声明的受管兼容路径，不静默降级为宿主裸进程。

6.2 输入、环境与输出

  • stdin 只允许一次性载荷，默认上限 1 MiB。
  • 环境覆盖必须使用合法变量名，禁止覆盖 ACE_SECURITY_*、ACE_BUNDLED_* 和代理保留变量，总体默认上限 256 KiB。
  • 各原生后端从受控环境构建子进程环境；macOS 明确 env_clear，使用私有 HOME/TMPDIR。受管 PATH 会保留系统命令目录，并把随包 Python/Node/npm/npx 置于最前；开发态没有随包运行时时，只读开放当前开发 Node 的 launcher 目录、真实版本根和 npm 包根，不再因为 bin/ 位于某个 prefix 下就开放整个 prefix。
  • 用户显式激活的 Skill 根会重新对照当前 Skill 注册表和 realpath，匹配后仅作为本轮只读根继承到 terminal；伪造、移动或被替换的 Skill activation 失败关闭。Skill 的额外数据目录、虚拟环境和外部程序不会由 Skill 根隐式获得权限。
  • stdout 与 stderr 总量默认限制为 2 MiB，单帧最多 64 KiB；超限会停止进程。
  • 返回模型和任务日志前，会按注入的秘密值精确脱敏，并再执行通用敏感文本脱敏。

6.3 外部智能体兼容路径

Codex 与 Claude Code 在受管模式下不再尝试启动宿主上的 app-server/stream-json 长连接，而是退化为一次性 captured 调用：先申请一份绑定外部智能体可执行文件与模型服务精确目标的权限 overlay，批准后再通过 Native Runtime 启动。Codex 的 npm 启动脚本会在 macOS、Linux 和 Windows 上解析为随包提供的原生二进制，避免沙箱为了 Node 包管理器而开放整段安装目录；只有 provider 配置与凭据环境进入子进程，HOME、PATH、TMP 和代理变量仍由 Native Runtime 控制。

一次性调用会关闭外部 CLI 自己的交互审批和内部沙箱，因为真正的文件、网络和进程上限已经由外层 Native Runtime 执行；该开关只在 ProcessLaunch.managed 为真时注入，兼容模式保持原行为。当前兼容路径能完成基础问答与工作目录内的 Agent 操作，但不会伪装成完整结构化协议：会话恢复、MCP 动态工具、逐条 tool event、细粒度外部权限回调与真正的双向流式输出仍需要后续的 native bidirectional transport。任意 ACP adapter 在此之前继续失败关闭。

6.4 灵感站点构建

publish_site 不把模型给出的包管理器字符串直接交给宿主 PATH。host 先限制命令族为 npm/pnpm/yarn/bun，再解析实际 Node 与包管理器脚本入口，以最终 argv/cwd 进入统一 exec 审核；批准后只把解析出的运行时安装根作为可信只读资源加入本次 ProcessLaunch。构建写权限仍只有当前 Workspace，网络仍由会话 overlay 决定。Node 子脚本使用受控 PATH；OpenSSL 不读取宿主全局配置。这样既能让打包 Node、Homebrew、nvm 和 Windows Node 安装工作，也不会把用户 HOME 或任意 PATH 目录整体开放。

6.5 解释器、依赖与子进程的授权模型

6.6 随应用交付运行时的结论与阶段

结论：受控 Node.js 与 Python 基础运行时适合随应用交付，而且现有三平台构建已经有可用骨架；但当前构建还不能称为可复现、可持续修补的安全供应链。本轮不把它草率改造成新的打包体系。

  • 当前 Linux、macOS、Windows 脚本都下载 Python 3.11.9 与 Node 20.18.3，但下载未统一校验 SHA-256/签名；项目 README 的开发 Node 基线又是 22.12，版本策略已经分叉。
  • Skill Python 包大多没有锁版本或 wheel 摘要，三平台的 mcp 版本也不一致；Windows 还会安装后删除部分重型包。这会造成构建不可复现、原生扩展 ABI 与实际可用能力漂移。
  • 完整 Python 科学/办公栈显著增加包体、C/C++ 原生模块兼容面和漏洞修补压力；Node 本体相对适合整包携带，但 npm 全局依赖仍需独立锁定。
  • 第一阶段应生成三平台 runtime lock/manifest：来源 URL、SHA-256、版本、许可证、SBOM、Python wheel tag/Node ABI 和原生库清单，并在 CI 离线复验。
  • 第二阶段把 Python 拆成只读基础运行时与按 Skill 集合构建的版本化依赖层；禁止运行时向共享 site-packages 执行 pip install，每个依赖层用内容摘要寻址并只读挂载。
  • 第三阶段建立月度/紧急 CVE 重建通道与 macOS/Linux/Windows 原生矩阵；旧 runtime 与 Skill 依赖层按版本并存、原子切换和可回滚。

7. 受管联网：沙箱只见代理，代理才见目标

命令执行的网络策略不是“设置几个代理环境变量”。环境变量可以被程序忽略，因此操作系统层先切断直接连接，只留下运行组件建立的受管代理路径。

沙箱内程序
   │ HTTP / HTTPS / TCP（只能到受控本机入口）
   ▼
每任务代理
   │ 解析目标 → 匹配 exact host:port:protocol → DNS 解析 → IP 分类与固定
   ▼
批准的远端地址
  • 规则只接受精确主机名或 IP、端口和协议，不接受 wildcard、scheme、URL path 或空白变体。
  • 显式 deny 优先于 allow；目标未列入规则时默认拒绝。
  • DNS 结果在代理端检查并固定到数字地址，避免检查域名后重新解析到不同目标。
  • loopback、RFC1918、链路本地等地址默认拒绝，只有规则明确设置 allow_private 才可访问。
  • 常见云元数据地址永久拒绝，即使允许私网也不能升级放行；IPv4-mapped IPv6 会先归约再判断。
  • 未提供网络规则时不启动代理，沙箱保持离线；本地端口绑定是单独能力，不能由出网许可隐式获得。
浏览器与命令使用不同执行器，但都默认拒绝私网：Native Runtime 内的命令使用系统级网络边界；应用内 Chromium 使用每个 owner 独立、带随机凭据的 loopback policy proxy。代理在连接前解析并固定目标 IP，默认拒绝 loopback、RFC1918、link-local、非全局地址、IPv4 映射/转换地址和常见云元数据端点；只有 allowed_private_hosts 或 allowed_private_cidrs 的显式配置例外可以放行。Electron Host 收不到代理地址时会以 proxy_required 失败关闭。

7.1 搜索、网页提取、Wiki URL 与灵感 Automation

web_search、web_extract、Wiki URL 抓取和灵感 http_json Automation 共用 crew/security/outbound.py：只接受公开 HTTP(S)，拒绝 URL 凭据、localhost、私网、链路本地与保留地址；每次重定向重新校验，并只连接已经校验为公网的数字地址，避免 DNS 检查后再次解析。响应体有硬大小上限。网页工具和 Agent 手动 Automation 还会把精确 host/port/protocol 交给安全服务：请求批准模式等待 owner 决定，替我审批和完全访问权限可自动审核公开目标，跨域重定向逐目标授权，所有决定进入网络审计。完全访问不会改变某个专用工具自身“仅公网 URL”的输入契约，但可以通过宿主命令使用完整网络能力。灵感预览响应同时设置 connect-src 'none'，生成页面不能另开一条未审核的 Chromium 联网旁路。

7.2 进程内 HTTP 支持上游代理级联

outbound.py 的安全口径与 Native Runtime 受管代理一致：安全意味着“经过策略判断”，不是“直连目标”。判断通过后，默认把流量级联到用户已有的上游代理，由代理负责到达目标；没有上游代理时才直连。代理解析优先级（高到低）：调用方显式传入 → 配置 network.upstream_proxy（load_config 加载后注入为进程级默认）→ 环境变量 HTTP_PROXY/HTTPS_PROXY/ALL_PROXY（大小写都读）。支持 http://、https://、socks5://、socks5h://，纯标准库实现，三平台行为一致。

  • HTTP/HTTPS 代理走 CONNECT host:port 隧道；authority 始终带端口，CONNECT 握手限时后回到阻塞模式再做 TLS。
  • SOCKS5 走 RFC 1928 握手，支持无认证与用户名/密码；socks5h 把域名交给代理解析，socks5 由本地解析后再发 IP。
  • 代理模式下 DNS 解析交给代理，本地只做主机名校验；DNS pinning 会弱化（代理重新解析），这是受管代理级联的固有取舍。
  • 代理本身的 loopback 地址（127.0.0.1/::1）默认允许（本地 Clash 等场景）；network.allow_loopback_proxy: false 时拒绝。
  • 私网目标拒绝、URL 凭据拒绝、重定向逐目标授权、响应大小上限在代理模式下全部保留。

7.3 浏览器上传边界

上传和拖放先按结构化文件读取策略授权源路径；受管模式的广泛只读基线允许读取工作目录外的普通文件，但 Ace 私有路径与显式拒绝路径仍不可见。读取通过后，Python 在账号浏览器目录下创建一次性 approved-uploads/<nonce>，安全快照普通文件或目录，拒绝符号链接、junction/reparse point 与特殊文件，并执行总字节和条目数护栏。Electron Host 再独立验证暂存根、目标 realpath 和整棵目录；Playwright 操作结束后立即清理该次暂存区。Host 不再接受工作目录原始路径，也不再使用与 Playwright 能力不一致的 256 个顶层路径硬限制。

8. 原生协议与运行组件完整性

8.1 每任务、经认证、可验证的 stdio 协议

Gateway 每次执行都会启动新的 helper，通过 stdio 交换 NDJSON；helper 不监听网络端口。协议版本为 v3：

helper 启动
  └─ 从 ACE_SECURITY_RUNTIME_TOKEN 读取随机启动令牌（至少 32 字节）
  └─ ready { version: 3, capabilities: [stdin_once, stream_output, full_disk_read] }

host 请求
  └─ { version, token, nonce, request }

helper 响应
  └─ started(seq=0, capabilities, pid?)
  └─ stdout / stderr(seq++)*
  └─ completed | error(seq++)
  └─ EOF

令牌使用常量时间比较；nonce 至少 16 字符并在有界缓存中防重放。host 校验每帧的 version、nonce、严格递增 seq、事件顺序、终态和 EOF。Windows helper 还必须同时报告 restricted token、ACL、Job Object 和显式句柄继承能力，否则 host 拒绝结果。

8.2 helper 从哪里来

运行组件不会从任务 cwd 或任意 PATH 中搜索。开发态依次选择：

  1. ACE_SECURITY_RUNTIME 指定的绝对路径；
  2. desktop/security-runtime-bin 本机 staging；
  3. security-runtime/prebuilt/<platform>-<arch> 仓库预编译目录；
  4. 旧版兼容目录 security-runtime/bin。

manifest 存在时必须匹配 schema、平台、架构、文件名和二进制 SHA-256。源码树中的预编译产物还记录 source_hash：Rust 源码、测试、Cargo.toml 或 Cargo.lock 变化但未重建时，安全中心报告 runtime stale，不把旧二进制声明为可用防护。

9.1 Linux：namespace + bubblewrap + seccomp

Linux 的 workspace-write profile 先把宿主根目录 ro-bind 为只读，再覆盖工作空间与临时目录的可写 bind，最后重新覆盖项目元数据与 Ace 私有 deny；同时开启 user、PID 与 network namespace，挂载受控 /proc，并设置父进程退出联动。内层在执行命令前应用 no_new_privs 与 seccomp。WSL1 缺少所需 namespace 能力，因此直接拒绝。

9.2 Windows：低权限身份 + ACL + WFP + Job

Windows 不递归修改磁盘根 ACL。Host 枚举 Windows、Program Files、ProgramData、工作目录与用户目录中非敏感顶层路径作为只读根，并排除 .ssh、.aws、.azure、.kube、.docker、.gnupg、.config 等目录；额外读取或写入通过精确 ACL lease 添加，并在进程结束时清理。

安装期创建 offline/online 两个技术账户并持久化受保护身份状态。每次命令在跨进程 mutex 内下发临时 ACL lease，使用 restricted token 和 capability SID 启动，只继承显式句柄，再放入 kill-on-close Job Object。可写根内的受保护元数据对账户和 capability SID 都使用“允许读 + 拒绝写/删除”的窄 ACL，避免父目录的写权限向下继承成修改能力。offline 账户不能联网；online 账户由 WFP 只允许到运行组件固定的本机代理端口。命令结束后先关闭代理，再回收 ACL lease。

9.3 macOS：Seatbelt deny-default profile

macOS 每次运行生成独立 Seatbelt profile，并通过系统 /usr/bin/sandbox-exec 启动。workspace-write profile 开放全局文件读取，但文件写入只开放工作空间、临时目录和精确获批根；随后对 readonly_roots 与 denied roots 重新施加更具体的拒绝。用户路径通过 -D 参数进入策略，避免路径内容成为 profile 语法。在线模式只允许本次代理的精确 loopback 端口；离线模式没有出网 allow。helper 为子命令建立独立进程组，取消或退出时整体清理。

10. 安全控制面：为什么普通网页不能替用户授权

安全中心能切换模式、处理审批、启停/删除永久规则、查看和导出审计。这些接口不仅要求 Gateway 登录态，还要求由 Electron main 持有的实例密钥签发 Desktop security proof。

Electron main 持有本机 instance key
       │
       ├─ Gateway health challenge → HMAC 实例证明
       │
       └─ 安全 API 请求 → HMAC(timestamp, nonce, method, path, SHA256(body))
                                  │
                                  ▼
                         Gateway 校验并消费 nonce

证明默认只在 30 秒窗口内有效，并且 nonce 单次消费。POSIX 上密钥目录/文件要求 0700/0600、当前用户所有，读取时拒绝符号链接并核对打开前后的 inode。密钥强制绑定当前绝对 CREW_HOME，不同开发/账号实例不能隐式共享安全权限。

11. 状态、审计与竞态防护

11.1 哪些状态持久化

状态存储位置/方式生命周期
会话模式Gateway 内存；前端仅持有界面预设当前 Gateway/会话；完全访问只可作为一次性新会话预设。
once/session grantGateway 内存，包含动作与额外权限 overlay一次消费、会话结束、登出或进程重启。
always ruleSQLite security_rules，包含动作与额外权限 overlay按 OS user + owner + workspace 隔离，直到禁用/删除。
审计事件SQLite security_audit_events默认保留 30 天，可筛选、分页、导出 JSONL 和清理。
Windows 沙箱身份/WFPDesktop security state + 系统配置安装后持久化，卸载时回收。

11.2 审计写入也属于授权事务

审批决定、规则创建/禁用/删除和秘密注入是关键事件，无法持久写入时会让授权失败并回滚刚创建的 grant 或规则。普通事件可进入有界内存缓冲，后续成功写入时再刷新。这样不会出现“执行已经放行，但决定没有证据”的静默状态。

审计保存动作摘要和动作 hash，不直接依赖原始工具参数展示。命令行 token/password、HTTP 鉴权头、注入的秘密值等会在事件创建与入库阶段重复脱敏。查询始终按 owner 过滤，OS 用户仅保存 SHA-256。每次 captured execution，以及终端前台/后台进程结束时，都会写入 exec_result，包含实际 sandbox backend、已启用 capability、exit code；超时、runtime 崩溃、协议不匹配和 sandbox 拒绝则保存稳定错误码。后台 bridge 通过位于 Ace 受保护目录的随机 nonce sidecar 回传运行元数据，命令本身不能伪造该结果。

11.3 并发边界

  • decision lock 把 grant/rule 发布、审计提交与授权消费串成同一临界区；审计失败回滚时，不会有另一个线程已经消费临时权限并开始执行。
  • 模式切换、会话结束和登出在相同决策边界内撤销 pending/grant，避免清理窗口中新权限逃逸。
  • Windows ACL lease 使用跨进程 mutex；固定代理端口的生命周期与 lease 串行，避免不同任务共用错误网络策略。

12. 安全中心展示的是实测能力，不是文件存在

/api/security/capabilities 不会因为 helper 文件存在就声称沙箱有效。Gateway 会创建临时 workspace、项目外普通文件、项目外写入 marker 和带哨兵内容的 .git/config，让 helper 同时尝试“写入允许目录”“读取项目外普通文件”“写入项目外路径”和“改写应当可读但不可写的元数据”。只有工作区 marker 成功写入、项目外普通读取成功、项目外写入失败、元数据哨兵保持原样且能力帧声明 full_disk_read，文件沙箱才通过 live probe；联网能力使用独立的受管网络探针。

安全中心据此展示：

  • 本机运行组件：helper 是否存在且通过基本校验；
  • 文件沙箱：真实 canary 是否证明边界生效；
  • 联网管控：在线探针是否证明网络经过受管路径；
  • 永久规则与审计：当前 workspace 的授权状态和当前 owner 的历史记录。

macOS 防护随应用提供，不需要安装或管理员权限。Windows 安装/修复按钮通过主进程受控 IPC 和 UAC 执行，渲染层不能传入任意命令。能力接口失败时，界面不能把未知状态显示成已受保护。

13. 当前边界与维护时不能误写的承诺

范围当前事实文档/产品口径
隔离强度共享宿主内核的进程级边界。称为原生沙箱或受管隔离，不称为 VM 级强隔离。
浏览器网络Chromium 全部 HTTP、HTTPS 与 WebSocket 连接强制经过认证的 DNS-pinning policy proxy；私网与元数据地址默认拒绝。需要访问本机开发服务时，必须通过 allowed_private_hosts/allowed_private_cidrs 做部署级显式例外。
普通/Wiki 工作目录没有项目根时使用 owner 隔离任务目录作为 cwd 与可写根；Wiki Agent 同样消费有效工作目录。Host 拥有的更具体任务根可以从宽泛运行时目录保护中 carve out；数据库、身份、审计和仓库元数据的更具体不可升级保护仍优先。
网页与 Wiki 出站搜索、提取和 Wiki URL 统一做公开地址校验、重定向复检、DNS 地址固定、响应上限与网络审批/审计。不把应用内 HTTP 请求当成“不是命令所以无需审核”；也不允许它访问本机或内网服务。
浏览器上传源文件先走广泛只读与保护路径判断，再复制到账号隔离的一次性暂存区；Host 只接受该根下的普通文件/安全目录。工作目录外普通文件可以读取并上传；Ace 私有路径和显式拒绝路径仍不可见，Host 也不能直接读取任意宿主路径。
替我审批基础沙箱内的普通终端命令自动执行；危险动作、权限扩张和监听端口仍询问。自动执行只省去不必要的提示，不扩大文件或网络权限。
Codex / Claude Code 外援受管模式使用 Native Runtime 内的一次性 captured 兼容路径，并为精确模型服务目标单独审批；不会回退到宿主裸进程。基础回答与工作目录内操作可用；结构化工具事件、MCP、恢复与双向流能力在兼容路径中明确降级。
项目元数据三平台受管 shell 都实现可读、不可写的 readonly_roots；旧 helper 不声明能力会失败关闭。保护只覆盖进入 Native Runtime 的受管进程，不扩展成宿主上所有进程的系统级防篡改。
执行结果审计授权决定、规则变更与 exec_result 均已入库，结果事件记录 backend、capabilities、exit code 或稳定错误码。运行结果与授权原因是两条事件，可通过同一 owner/session/request/action 摘要关联。
发行信任链跨平台 workflow 在原生 runner 构建、测试、生成 SHA-256 manifest 与 GitHub build provenance；证书存在时额外签署 macOS/Windows helper。仅通过 GitHub 分发不强制申请证书；无证书资产仍有摘要和 provenance，但免除 Gatekeeper/SmartScreen 的未知发布者提示需要 Developer ID / 公证或 Authenticode。当前尚未实现完整桌面应用的 macOS 公证。
宿主进程执行面Sites 构建和 Wiki 旧 Office 转换均已进入 execute_captured；Skill 后代与开发脚本已在执行面清单中按边界分类。新增直接进程创建或 Desktop child_process 文件未登记时，CI 清单测试失败。
长连接子进程managed transport 尚不支持任意双向长 stdio；Codex/Claude Code 仅有上面的安全一次性兼容路径。通用 ACP 明确拒绝，不承诺自动兼容所有外部 agent adapter。
发布证据mock/source test 只能提供开发反馈。三平台 release 必须使用真实 runner 的原生矩阵和打包产物证据。

16. 最小系统模型

如果只保留理解 Ace 安全系统所需的最少概念，可以记成四句话：

  1. 权限来自宿主事实，不来自模型参数。 owner、workspace、cwd 和模式由 Gateway 重建。
  2. 授权的是精确动作和精确权限，不是模糊意图。 规则和 grant 同时绑定规范化动作与额外权限 overlay。
  3. 普通批准不能替代隔离。 用户允许后，命令仍进入平台原生沙箱，只在基础 profile 上叠加已显示并批准的权限；只有明确的单命令脱沙箱或完全访问会走宿主执行。
  4. 没有证据就不宣称安全。 helper、协议、live probe、审计和真实 runner 共同构成可验证链路。
