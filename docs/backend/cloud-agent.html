A云端 Agent 高并发架构设计

用一套共享的无状态 Worker 池服务所有用户的会话；会话状态外置，执行副作用单独成层。不做"一个用户一个 Agent 实例"。

1. 定位与约束

  • 要解决的问题：云端 Agent 服务需要支撑大量并发会话；"一个用户部署一个实例"资源消耗不可接受。
  • 核心思路：把传统认知里的"Agent 实例"拆成 4 样生命周期完全不同的东西，让其中唯一昂贵的东西（Worker 进程）被全体用户共享。
  • 不在本文范围：具体队列/存储选型、计费与配额产品化（见第 8 节 TODO）。

2. 概念澄清："Agent 实例"是 4 样东西

东西是什么生命周期与用户会话的关系
Agent 代码图定义、prompt、工具 schema、模型配置随发布版本固定全租户共享一份，与 session 无关
Worker 进程执行 run 的容器/进程常驻，随扩缩容生灭与用户零绑定，任意 worker 可服务任意会话
Run一次"从当前状态跑到停下来"的执行秒~分钟级一个 run 属于一个 thread
Checkpoint会话状态快照（消息历史 + 图状态）永久（存储中的一行）唯一与 session 1:1 绑定的东西

"一个用户一个实例"之所以贵，是因为把 Worker 进程和 Checkpoint 绑死了（进程即用户）。本设计把这两者解耦：用户只拥有自己的 checkpoint，worker 是共用的出租车。

checkpoint 存在的意义：worker 任何时刻挂掉，下一个认领者从最近快照继续，内存状态可随时丢弃重建

注意：checkpoint 在步骤边界保存，不是每行代码后保存。worker 中途崩溃时 run 需要重试，所以工具调用必须幂等或可安全重放。

5. 高并发设计清单（要做什么）

#做什么为什么不做的后果
1Worker 无状态化
进程内不落任何用户数据的真相；任意 worker 可服务任意会话		 这是水平扩容的前提；扩容 = 加副本 必须做粘性路由，缩容/故障把用户会话一起带走
2状态外置 + 会话串行化
checkpoint 唯一真相源在 Postgres；同一 thread 内串行，thread 之间全并行		 并发写同一会话会互相踩状态；thread 内排队、thread 间并行是并发度的正确粒度 两个 run 同时改一个 checkpoint，历史错乱
3队列 + worker 池 + 慢缩容
run 入队等待认领；缩容前等待 in-flight 排空（分钟级延迟再缩）		 削峰；扩容只动 worker 数量；避免缩容杀掉正在跑的 run 突发流量打垮服务；缩容中断用户任务
4冷启动分层处理
L1 基础设施（秒级）：常驻 worker 池，别用 FaaS 把它放进请求路径；L2 应用热身（百毫秒）：worker 启动时做一次；L3 会话装载（毫秒级）：每次认领 run 读 checkpoint		 只有 L3 在请求路径上，而它足够便宜 用户请求路径上出现秒级抖动（FaaS 回收容器）
5缓存分三层
热身缓存必做；状态缓存（热点 thread 放 Redis）可选；LLM prompt cache 靠稳定前缀设计白拿		 缓存只是加速，不是正确性依赖——清空任何缓存，系统必须照样正确，只是变慢 把状态藏进缓存；缓存失效即数据丢失
6执行副作用单独成层
沙箱/浏览器/文件系统类工具独立部署；会话按需分配沙箱，租约续期，用完回收；编排层只存引用		 这是唯一真正需要"粘住一台机器"的东西（见第 6 节分界线） 沙箱状态渗进编排层，被迫退回"一人一实例"
7瓶颈与限流
识别真实瓶颈（PG 连接池、LLM rate limit、沙箱总量）；每用户并发上限；全局队列深度监控；工具幂等设计		 编排层本身不是瓶颈，下游才是；一个用户不能拖垮所有租户 单用户打满 LLM 配额，全服务雪崩

6. 分界线：什么时候才需要"一人一实例"

判断标准只有一条：状态能不能序列化进存储。不是因为"会话"本身。

维度会话状态（对话历史、图变量）执行环境（沙箱、文件系统、浏览器）
形态可序列化的数据活进程，序列化不了
存放Postgres，一行一个会话一台真实机器上的容器
粘性需求无——任意 worker 读取即可必须粘住分配到的那台机器
失败恢复从 checkpoint 重放重置/重启环境
扩容方式加无状态 worker 副本沙箱池预热 + 空闲回收

所以架构上始终是两层：编排层（对话、调度、状态）无状态水平扩；执行层（沙箱）按需分配、租约管理。会话粘性只存在于执行层，且被压缩成 checkpoint 里的一个引用。

8. 当前存在的问题 / TODO

  • 队列选型：复用 Redis 还是独立 MQ，待压测后定。
  • checkpoint 粒度与写入放大：PG 行大小上限、大对象是否外置 blob 存储。
  • 多租户配额：每用户并发上限数值、公平调度策略（防止单用户占满 worker）。
  • 沙箱租约时长、心跳间隔与回收策略。
  • 长任务接管：worker 崩溃后 run 的租约超时与接管机制。
  • 流式输出通道：Redis PubSub 断线重连期间的事件补发（或降级为拉取）。

10. Mermaid 架构图

10.1 LangGraph Platform：共享 Compiled Graph + Queue Worker 池

flowchart LR C["客户端"] --> LB["负载均衡"] LB --> API1["无状态 API Server 1"] LB --> API2["无状态 API Server N"] API1 --> Q[("持久化 Run Queue")] API2 --> Q API1 --> PG[("Postgres：runs / threads / checkpoints")] API2 --> PG Q --> R1 Q --> R2 subgraph W1["Queue Worker 1"] G1["启动时加载 Compiled Graph"] --> R1["并发执行多个 Run"] end subgraph W2["Queue Worker N"] G2["启动时加载 Compiled Graph"] --> R2["并发执行多个 Run"] end R1 --> PG R2 --> PG R1 --> Redis[("Redis：取消 / 心跳 / PubSub")] Redis --> R1 R2 --> Redis Redis --> R2 Redis --> API1 Redis --> API2 API1 --> C API2 --> C

Compiled Graph 是 worker 的共享代码/对象；每个 Run 只创建自己的执行上下文，并从 Postgres 装载对应 thread 的 checkpoint。扩容时增加 worker 副本和执行槽，不增加用户专属 Agent 进程。

10.2 Codex / Kimi Code 类 Agent：共享 Agent Kernel + per-Run Activation

flowchart LR C["客户端"] --> LB["负载均衡"] LB --> API["无状态 API Server"] API --> AD["Session Admission"] AD --> Lease["Session Lease：同一 Session 串行"] Lease --> Q[("持久化 Run Queue")] Q --> A1 Q --> A2 Q --> B1 subgraph W1["Agent Worker 1"] K1["共享 Codex Agent Kernel"] A1["Activation Slot A"] A2["Activation Slot B"] K1 --> A1 K1 --> A2 end subgraph W2["Agent Worker N"] KN["共享 Codex Agent Kernel"] B1["Activation Slot A"] KN --> B1 end A1 --> PG[("PG：Event Log / Session State")] A2 --> PG B1 --> PG A1 --> Redis[("Redis：取消 / 心跳 / 流式事件")] Redis --> A1 A2 --> Redis Redis --> A2 B1 --> Redis Redis --> B1 A1 --> Sandbox["Sandbox / Terminal / Browser Resource Pool"] B1 --> Sandbox API --> Redis API --> C

这类 Agent 的常驻部分是共享 Kernel、工具注册表、连接池和运行时；每个并发 Run 只占一个 Activation Slot。真正需要持久占用资源的终端、浏览器和文件系统放进独立 Sandbox 池，由会话租约管理。
