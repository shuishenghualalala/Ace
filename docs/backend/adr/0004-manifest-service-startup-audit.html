ADR-0004 · Manifest 服务依赖与启动审计

状态：Accepted · 日期：2026-09-02 · 阶段：插件架构 Stage 1 / Commit 5

背景

Feature Runtime 已能解析服务依赖，但目录插件的 Manifest 尚未进入该模型，加载顺序仍由目录顺序决定。插件也可以继续从无约束字典读取服务，无法区分必需、可选和对外提供的能力；插件停在 Waiting 或 Failed 时缺少统一、可机器读取的启动结果。

决定

目录插件使用 Manifest 的 requires、optional 和 provides 声明服务边，PluginManager 一次发现全部定义，再由 Feature Runtime 计算确定性激活批次。

  • Consumer 即使目录排序在 Provider 之前，也必须等 Provider 的服务实际可见后再安装。
  • provides 是可验证契约：安装结束前必须通过当前 Scope 注册对应 Service，否则整代安装失败并回滚。
  • PluginContext.register_service() 只允许发布已声明服务；resolve_service() 与 get_service() 只允许读取已声明依赖。
  • 组合根通过 publish_host_services() 把 Host 对象同时发布到兼容字典和类型化 Registry；后到服务触发 Waiting 插件重试。
  • Runtime 输出包含状态、Generation、配置版本、服务依赖、缺失项、注册标签和错误的稳定快照。
  • build_app() 在装配收敛后执行一次审计；crew --dump-features 输出同一数据，存在 Waiting/Failed 时返回非零退出码。

兼容与跨平台

旧 Manifest 不声明服务时行为不变；requires_services、optional_services、provides_services 作为显式别名可用，但同一字段不能同时使用两种写法。实现只依赖 Python 数据结构与 asyncio，不依赖文件系统排序差异、Unix 信号或进程模型。
