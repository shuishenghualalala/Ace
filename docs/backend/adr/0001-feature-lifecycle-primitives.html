ADR-0001 · Feature 生命周期所有权原语

状态：Accepted · 日期：2026-09-02 · 阶段：插件架构 Stage 1 / Commit 2

背景

现有目录插件把工具、Hook、Router 等贡献直接写入全局表，再分别记录名称；异步 disposer 在有事件循环时只被创建为后台任务。结果是安装中途失败无法统一回滚，卸载返回也不代表资源已经静止。第一方功能又由 CrewApp 单独管理，无法共享同一套所有权。

候选方案

  • 直接在 PluginManager 中逐项补充清理逻辑：改动较小，但会继续把生命周期绑定到目录插件，并让每种贡献维护不同撤销代码。
  • 先建立中立 Feature 生命周期内核，再由旧管理器适配：多一个迁移步骤，但第一方与第三方能力可以收敛到同一模型。
  • 一次性替换全部装配流程：目标结构直接，但变更面不可独立验证和回滚。

决定

在 crew/features 建立与目录发现无关的所有权原语：FeatureGeneration 标识单次激活，FeatureScope 持有全部带标签的 RegistrationToken，FeatureTransaction 负责未提交安装的统一回滚。

  • disposer 可以同步或异步；Scope 返回前必须等待异步清理完成。
  • Token 单次执行；并发和重复调用共同等待同一清理任务。
  • Scope 关闭后拒绝新注册，并按后进先出顺序尝试全部清理。
  • 单项清理失败不阻断其余项，最终以标签和原始异常聚合报告。
  • 本提交只建立生命周期所有权；贡献的事务可见性由下一步 Service/Contribution Registry 提供，旧 PluginManager 在再下一提交接入。

跨平台影响

实现只依赖 Python 3.11 标准库的 asyncio、dataclasses 与时区时间，不依赖 POSIX 信号、文件锁或平台路径语义；macOS、Linux、Windows 使用同一代码路径。

回退方式

当前没有生产调用方，回退时可整体撤销 crew/features、对应测试与文档，不影响现有 PluginManager 行为。旧管理器接入后则通过 Legacy Adapter 提交边界单独回退。
