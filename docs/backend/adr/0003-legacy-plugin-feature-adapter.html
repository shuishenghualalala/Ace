ADR-0003 · 目录插件接入 Feature Runtime

状态：Accepted · 日期：2026-09-02 · 阶段：插件架构 Stage 1 / Commit 4

背景

旧 PluginManager 在安装时直接修改多个全局表，只记录贡献名称；失败只清理平台项。卸载在事件循环中把异步 disposer 留给后台任务，因此返回成功并不代表资源已经停止。重复 discovery 会清空管理表但不先释放旧插件，容易留下重复工具或后台资源。

候选方案

方案结论
保留旧卸载逻辑，只在 Browser 特判等待拒绝；会继续形成每个插件一套生命周期。
要求所有目录插件立即重写入口拒绝；迁移成本大，无法保持旧插件兼容。
将 register(ctx) 转换成 FeatureDefinition采用；旧 API 保留，内部所有权统一。

决定

新增中立 FeatureRuntime、FeatureDefinition 与运行记录。PluginManager 只负责目录发现和旧 API 适配，每个目录插件最终由一个 Feature Generation 管理。

  • Tool、Hook、Middleware、Command、Router、Platform、Skill Root 和插件资源全部登记为带标签 Token。
  • Token 分为 Contribution 与 Resource 两相。停用先逆序关闭对外贡献，再逆序等待资源，避免清理期间继续接收新调用。
  • 安装失败由同一个 Scope 完整回滚；清理失败聚合到 Feature 记录，并阻止带孤儿资源的 Feature 自动重试。
  • discover_and_load_async() 与 unload_plugin_async() 是异步宿主的可靠入口；同步 discovery 保留兼容桥。事件循环中的同步 unload 明确报错，不再伪装成已完成。
  • 重复 discovery 先等待旧 Generation 清理，再创建新 Generation。
  • Browser 作为真实多贡献试点；应用关闭统一调用 PluginManager.aclose()，BrowserManager 不再走旁路关闭。

兼容与限制

插件的 register(ctx)、全部 register_* 方法、Manifest 和 LoadedPlugin 查询仍可使用。同步构造 Ace 时行为不变；已处于事件循环的宿主应迁移到异步 API。现有 ctx.services 字典暂时保留；Manifest 服务映射已由 ADR-0004 接续实现。

跨平台影响

生命周期只使用 Python 标准 asyncio 与 threading。同步兼容桥不依赖 Unix 信号或 fork；macOS、Linux、Windows 使用同一实现。

回退方式

该提交可整体回退到旧 PluginManager；Feature Runtime 与 Service Registry 本身没有破坏性数据变更。Browser 的业务实现、工具 schema 和用户偏好均未改变。
