ADR-0014 · Feature Event 命名空间与旧帧出口适配

状态：Accepted · 日期：2026-09-03 · 阶段：插件架构 Stage 2 / 核心协议演进（§7.3）

背景

核心 ChunkKind 枚举把 wiki_cards、wiki_ingest_progress、team_internal 三个业务概念写进了稳定协议：每增加一个业务事件都要改核心类型。生产侧也分散——team_internal 由 Team 编排以 ResponseChunk 产出，wiki_cards/wiki_changed/wiki_ingest_progress 由 Gateway 推送点直接拼帧。桌面端与 Web 端的 reducer 只认识这些旧 kind。

决定

核心协议新增唯一开放事件帧 feature_event，body 固定为 {feature, event, version, payload}；生产侧全部改发命名空间事件；在 WS 出口（connections.push_payload）由 Legacy Adapter crew/gateway/event_compat.py 把已登记事件翻译回旧 kind 帧，线上协议对现有客户端逐字节不变。

职责所有者契约
事件信封结构crew/core/envelope.pyResponseChunk.feature_event() 与 feature_event_body()；核心不含任何 Feature 名称。
新→旧映射与出口展开crew/gateway/event_compat.py(feature, event, version) → 旧 kind；帧级字段透传；未登记事件记日志并丢弃。
出口唯一转换点crew/gateway/connections.pypush_payload 先展开再入回放缓存；断线 replay 因此也保持旧协议。
team 内部消息crew/team/team_manager.pyteam.internal_message v1，payload 即原 team_internal body。
wiki 卡片/变更/摄取进度Wiki Bundle Event Contributors、routers/wiki.pywiki.cards / wiki.changed / wiki.ingest_progress v1；WS 只提供中立 dispatch sink。

行为兼容

  • 桌面端、Web 端、CLI 均不改：WS 线上帧与回放帧仍为旧 kind（契约测试逐字段验证）。
  • CLI 本来就不消费这三种帧，无需适配。
  • history_projection 的 team_internal 持久 role 属于会话投影（§7.4 Session Event），不在本切片。
  • 其他业务 kind（kanban、workflow_progress 等）本次不动，迁移顺序按计划另行评估。

边界与后续

本切片选择「出口转换」而非「双发」：旧客户端只看到旧帧，feature_event 先在后端内部流动并积累契约测试。阶段 5 前端 reducer 迁移到 ace.feature-event.v1 后，删除 event_compat.py 与三个旧 ChunkKind 枚举（deprecated_after 的跟踪要求见计划 §15.2）。新增业务事件的规则：生产侧只发 feature_event 并登记映射，不再往 ChunkKind 加业务枚举。

2026-09-05 的 Stage 3B 后续切片新增 FeatureEventContributorRegistry：Wiki cards/changes 来源已从 WS 移入 Wiki FeatureScope，按 Generation Lease 顺序 dispatch；命名空间和出口兼容决策保持不变。

跨平台

纯协议与字典转换，不引入进程、路径或平台分支。
