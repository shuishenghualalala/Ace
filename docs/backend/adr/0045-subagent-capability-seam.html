ADR-0045 · 子智能体 Capability Seam 与单一发布边界

状态：已批准，阶段 A / A2 已实施 · 日期：2026-09-16 · 分支：codex/subagent-multiagent-upgrade。

背景

旧实现把参数适配、Agent 创建、执行循环、双超时、并发、任务兼容和 JSON 输出集中在工具模块中。它能工作，但进程外 Provider、持久身份或续聊一旦接入，就必须复制或侵入这条循环；同时 Provider 能否满足结构化输出、工具收窄等请求没有统一的 fail-loud 边界。

源码调研显示：dsh 的能力 seam 与运行句柄适合承载语义骨架；Codex 的预留/回滚和“权限只减不增”适合安全边界；Kimi 的批量隔离和子级结果回传适合产品兼容。Ace 保留现有工具名与返回 JSON，不把任何参考项目名称写入产品代码或注释。

决定

  1. 建立传输无关的 StartRequest、五位能力矩阵、immutable descriptor、稳定结局和幂等运行句柄。
  2. SubagentRuntime 是能力预检、深度检查和发布的唯一边界；未知 Provider、能力不支持和发布失败在越界前抛出，已运行子级的业务失败折叠为数据。
  3. 执行细节放进 Provider。首个 inprocess-spawn Provider 持有 Envelope/chunk 循环、idle/absolute 双超时、部分输出、interrupt 与资源关闭。
  4. 子级构造通过 core.agent-factory Feature 暴露 typed ChildAgentRequest，Provider 不再依赖 CrewApp 私有 dict 工厂。
  5. 工具授权拆成纯策略函数；preset 的专用工具只能从父级授权上限加回。
  6. 工具层保留参数 schema、旧 JSON、后台任务兼容和三种工具名，其 handler 不再持有信号量或超时循环。
  7. 主 Agent 默认采用显式委派纪律；配置键为 features.subagent.delegation_mode，值为 explicit 或 proactive。
  8. core.subagent 通过 Feature Service Registry 发布 SubagentService；进程外传输由 product.external-agents 以可选依赖单向贡献，Core Runtime 与工具层不出现外援分支。
  9. 外援注册采用 Feature Scope 持有的动态 Provider family，而非启动时枚举单一 owner。解析 external:<agent_id> 时按当前 owner 查询 Catalog；Scope 停用即撤销 family。
  10. Preset 声明绑定 Provider，但模型 schema 不暴露 Provider。Roster、model 参数和自包含简报提示按当前 Provider 的可用性、能力与上下文继承属性生成。

关键不变量

不变量保证方式
Provider 不虚报能力Runtime 在 start() 前逐位校验，缺能力即拒绝。
权限不能扩张父授权快照先交集，黑名单与 reserved 后扣减；preset addition 受 ceiling 约束。
发布前失败零残留Provider 成功构造运行句柄才进入 Runtime 活跃表；失败不会留下 active 记录。
结局不被清理覆盖先确定 SubagentResult，清理异常只记录；dispose() 幂等。
批量失败隔离每项独立折叠，按输入顺序返回；一个发布失败不会取消兄弟项。
旧消费者不破坏工具 schema 和六字段结果形态由回归测试锁定。
插件停用即收缩外援 resolver 的 disposer 归当前 Feature Scope；停用后 roster 缩小，新委派 fail-closed，不回退传输。
Owner 不串线Provider family 在解析时读取当前 owner 并查 Catalog；启动阶段不缓存全局 owner roster。
外援不获得父权限inherits_parent_context=false，五项能力全 false，外部 permission handler 固定 deny。

阶段 A2 验证

第二个 Provider 使用 Catalog、DelegationService 与进程外事件流完成执行。它与进程内 Provider 共享同一个 Runtime 预检/发布边界，但对模型覆盖、工具过滤、结构化输出、父上下文继承和续聊给出相反能力声明。这个差异验证了 seam 表达的是委派语义，而不是进程内实现细节。

外援事件折叠采用“失败是数据”：提交前 Catalog/Delegation 失败不发布 Run；发布后的 stream/error/cancel 形成稳定 SubagentResult。Usage 事件视为累计快照，以最后值覆盖；完成后的 dispose 只回收资源，不改写已完成结局。

后果

新增 Provider 只需实现命名、能力声明、上下文继承声明和 start()，并由所属 Feature 注册/撤销；调用方无需理解传输。动态 family 会在 schema 与启动前查询 Catalog，这是换取 owner 隔离和即时 roster 的有意识成本。后台任务持久化尚未迁入 Feature 生命周期；该剩余边界由阶段 B/C 处理。

未选择的方案

  • 继续在工具 handler 内增加分支：短期改动少，但每种传输都会复制生命周期。
  • 把外援、Team 与 Subagent 统一为一个巨型接口：它们的身份、生命周期与权限语义不同，会迫使接口说谎。
  • 先做持久化和 UI：在结局与发布边界尚未稳定时固化表结构，会放大迁移成本。

回退

阶段 A 未改变数据库。可按文件回退 Runtime/Provider/Factory，并让三个旧工具重新使用原执行循环；配置默认值为 explicit，删除该提示词注入即可恢复旧模型行为。
