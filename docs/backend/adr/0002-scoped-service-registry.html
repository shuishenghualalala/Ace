ADR-0002 · 作用域化 Service Registry

状态：Accepted · 日期：2026-09-02 · 阶段：插件架构 Stage 1 / Commit 3

背景

现有 PluginContext.services 是一个全局字典，只能按字符串读取单实例。它无法表达同一能力在不同 Workspace、用户或 Session 下的实现，也没有 Generation 所有权、激活可见性和缺失依赖诊断。若直接以全局单例定义 Knowledge、Provider 等契约，后续多租户迁移会再次改写接口。

候选方案

方案收益问题
扩展现有字典改动最小所有权、作用域和依赖仍靠调用方约定。
引入通用依赖注入框架功能完整引入重量级概念，难与现有 FeatureScope 和渐进迁移边界对齐。
建立小型作用域注册表契约明确，可直接复用 Feature 生命周期需要先定义 Ace 的租户层级和冲突语义。

决定

建立类型化 ServiceKey[T] 与 ServiceRegistry。注册地址由 Service Key、作用域类型和规范化租户路径共同决定；解析从最窄的 Session 向 User、Workspace、Global 回退。

  • 四级作用域接口一次定义完整；首个调用方可以只使用 Global/Workspace。
  • 同一精确地址只能有一个所有者，不同作用域允许提供同名能力。
  • 激活中的注册保留在诊断表，但只有所属 Scope 进入 ACTIVE 后才可解析；进入 STOPPING 时立即停止新解析。
  • 注册返回上一 ADR 定义的 Token，回滚或停用自动删除且只删除本代拥有的条目。
  • FeatureDependencyGraph 记录 required/optional/provides，提供运行期解析、启动批次和循环/断路诊断。
  • FeatureConfigRevisions 分开记录 desired/effective；过时 Generation 不能覆盖更新的配置意图。

跨平台影响

实现是内存数据结构与纯 Python 状态转换，不依赖文件系统、进程、信号或线程模型；macOS、Linux、Windows 使用完全相同的路径。

回退方式

当前尚未替换 PluginContext.services。可以整体撤销 Service Registry 和配置版本类型，现有插件继续使用原字典；后续 Adapter 接入将另设提交边界。
