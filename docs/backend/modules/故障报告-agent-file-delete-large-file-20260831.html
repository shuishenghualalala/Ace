删除大文件导致 Gateway 重启与 Agent 回合失败

报告编号：ACE-20260831-AGENT-FILE-DELETE-LARGE-FILE　·　发现日期：2026-08-31　·　状态：已修复
结论：删除动作触发前，Agent 工具执行器会同步、无上限地读取目标文件内容以生成变更记录。针对 626,377,419 字节的 Git bundle，这个读取会阻塞 Gateway 事件循环；桌面端随后将 Gateway 判定为失联并重启，正在执行的 Python 协程无法跨进程恢复，最终任务显示“服务重启，Python 协程无法恢复”。

1. 用户现象

  • 用户要求删除：/Users/ahuamao/Downloads/mobileworkFuWuDuan-client-feature-0827-mind-map-20260824.bundle。
  • 文件类型为 Git bundle，现场大小为 626,377,419 字节，约 597 MiB。
  • 界面先出现工具执行中的卡片，随后出现“服务重启，Python 协程无法恢复”。
  • 当前现场检查确认文件仍存在，因此这次请求没有完成删除。

2. 现场证据

  • Gateway 启动日志 gateway-startup.log：桌面端 spawn、回收和重探测决策。
  • 运行时数据库 crew.db：runtime_tasks 中保存了失败任务的状态、请求 ID 和错误原因。

3. 代码调用链

  1. 模型选择 file_delete 工具后，进入 ToolRunner.run_batch。
  2. 在真正执行工具前，代码调用 ToolRunner._read_file_before，读取删除前内容。
  3. 该方法使用 target.read_text(encoding="utf-8", errors="replace")，没有大小上限、文件类型判断或二进制快速路径。
  4. 读取是在当前 Gateway 协程中同步执行的；它不是通过线程池执行，因此会阻塞同一事件循环上的健康检查和其他请求。
  5. 真正的删除实现位于 handle_file_delete，内部使用 asyncio.to_thread。但本次请求很可能在到达真正删除前，就已经被前置读取拖住并触发 Gateway 重启。
  6. Gateway 重启后，TaskRuntime.reconcile_after_restart 会将未完成的非 shell 任务标记为失败，因为 Python 协程无法跨进程恢复。

4. 根因定位

直接根因

ToolRunner._read_file_before 为了生成文件变更 diff，对 file_write 和 file_delete 都执行完整内容读取。对于大文件和二进制文件，这是不必要且无界的工作。

设计不一致

Ace 已有带 128 KiB 上限的文件状态读取实现：_read_text_with_limit 和 read_file_state。该实现会把超大文件标记为二进制，只保留元数据，不读取全部内容；但当前 ToolRunner 仍在使用旧的无上限读取逻辑。

注意：identity-mismatch 是桌面端健康证明失败后的监督动作记录，不代表删除目标路径鉴权失败，也不代表 Git bundle 文件损坏。

5. 影响范围

范围影响
file_delete 删除大文件高风险：可能阻塞 Gateway，导致删除未完成、Agent 回合失败和服务重启。
file_write 覆盖大文件存在同类风险：执行前读取无上限；执行后生成变更事件时仍有直接读取逻辑。
小型文本文件删除通常不受影响，现有文件变更卡片逻辑可以继续工作。
用户原始文件本次现场文件仍在，未发现删除成功或误删证据。

6. 建议修复方案（已实施）

  1. 让 ToolRunner 复用 crew.agent.file_changes.read_file_state，不要继续使用无上限的 Path.read_text。
  2. 对 file_delete 不生成内容 diff：只记录 exists=true、binary=true 等状态，删除后生成 status=deleted 的元数据变更。
  3. 对 file_write 的执行前和执行后状态同样使用大小上限；超限文件只展示路径、大小/二进制状态，不读取全文。
  4. 增加回归测试：使用临时大文件或模拟超限读取，验证 file_delete 能完成、任务能进入 completed，并且不会调用无界全文读取。
  5. 增加一条集成级日志：记录文件变更快照被截断为元数据的原因，便于后续区分“工具失败”和“变更展示降级”。

7. 验证建议

  • 小型文本文件删除：应保留现有删除文件变更卡片。
  • 大于 128 KiB 的文本文件删除：应快速完成，变更卡片不包含全文 diff。
  • 大于 128 KiB 的二进制文件删除：应快速完成，标记为二进制删除。
  • 大文件覆盖写入：应验证执行前后均不发生无界读取。
  • Windows、macOS、Linux 均执行一次，因为文件读取、删除和进程托管路径存在平台差异。

8. 修复与验证记录

本次修复已落地并通过单元与端到端验证，核心思路是「统一读取上限 + 不无界读」：让 ToolRunner 复用 crew.agent.file_changes 既有的 128 KiB 受限读取层，而不是在每个调用点各自无界 read_text()。

改动文件

  • crew/agent/loop/tool_runner.py：_read_file_before 与 _file_change_event 改用 read_file_state / file_change_from_states 生成 before/after 状态与变更；超限或二进制文件只记录元数据（binary=true、diff=[]），并新增降级日志。路径解析抽为 _mutation_target_path，消除重复。
  • tests/test_file_changes_security.py：新增超限文件删除的元数据降级单测。
  • tests/test_agent_loop.py：新增完整 run_batch 链路的 file_delete 大文件端到端测试（真实 handle_file_delete + 真实文件系统 + 断言不再调用无界 read_text）。

验证结果

  • 单元测试：tests/test_file_changes_security.py 5 passed；tests/test_tools.py 50 passed。
  • 端到端：tests/test_agent_loop.py（含新增 case）69 passed。
  • 真实规模回归：用稀疏文件模拟 626,377,419 字节 bundle，修复前无界 read_text 单次读取约 1.08s（阻塞事件循环）；修复后完整删除链路约 0.086s，文件成功删除，变更条目为 status=deleted / binary=true / diff=[]，无 error、无“服务重启”。
  • 删除本体仍由 handle_file_delete 的 asyncio.to_thread 执行，不阻塞事件循环；本次改动不涉及删除/写入本体逻辑。

说明

  • 变更快照上限沿用 Ace 既有的 FILE_CHANGE_MAX_BYTES = 128 KiB，与「文件系统读取层统一设 512 MiB 上限」的思路一致，仅阈值按 Ace 现有约定保留。
  • 本次没有删除用户现场的目标 bundle 文件，也没有新增模块或数据表。

9. 扩展修复：文件工具统一读取上限

参照「整读上限 + 读取前 metadata 预检 + 异步读取」的思路，审查发现 Ace 的 file_read / patch / file_write / grep 仍存在无界读取或同步阻塞，本轮统一修复。

改动

  • crew/tools/file_utils.py：新增 MAX_READ_FILE_BYTES = 512 * 1024 * 1024（统一整读上限）；snapshot_file 增加 max_bytes 参数。
  • crew/tools/builtin.py：handle_file_read 读取加 max_bytes（读前拒绝超大文件）；_write_file_sync 的 snapshot_file 加 max_bytes。
  • crew/tools/file_tools.py：handle_patch 的 snapshot_file / atomic_replace_bytes 改用 asyncio.to_thread（阻塞 I/O 丢线程池），并对超限抛干净 ToolError；grep 兜底改为读前按大小拒绝（max_bytes=_DEFAULT_MAX_FILE_BYTES），不再整读后再判断。

验证

  • 单元/回归：tests/test_tools.py、tests/security/test_file_races.py、tests/test_agent_loop.py、tests/test_file_changes_security.py、tests/security/test_outbound_tools.py 共 155 passed；新增 4 个回归测试覆盖 snapshot_file/file_read/patch 的读前拒绝。
  • 真实规模：600 MiB 稀疏文件 file_read 读前拒绝耗时 0.0017s，patch 读前拒绝耗时 0.0018s（不再整读进内存）。
  • 端到端：complex_tasks 4 个 case 全 PASSED（write_file / delegate_task_batch / team_workflow / dynamic_kanban）。

10. 附件读取读前上限

附件与图像注入上下文时同样存在「同步读整个文件再截断」的无界读取：_read_attachment 用 read_text()[:8000]、_read_image_as_data_url 用 read_bytes()，用户 @ 引用超大附件时会同步整读进内存并阻塞事件循环。本轮统一改为：

  • _read_attachment / _read_image_as_data_url 改用 read_verified_bytes(path.resolve(), max_bytes=MAX_READ_FILE_BYTES)，读前拒绝超大文件，并经 asyncio.to_thread 异步读取。
  • _build_user_text 改为异步方法，调用点改为 await。
  • 路径先 resolve() 再读取，避免 macOS 上 /var 符号链接导致目录链打开失败。

验证：tests/test_agent.py 新增 _read_attachment 超大 / 正常两类回归用例；600 MiB 稀疏附件读前拒绝耗时 0.0015s，小附件正常读取；相关测试 192 passed。
