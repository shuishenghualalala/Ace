2. 搭建顺序

  1. Core：先固定 Envelope、Message、接口，确保所有模块说同一种语言。
  2. State + Provider + Tools：补齐 Agent 需要的历史、模型和行动能力。
  3. Agent：把历史、记忆、插件、模型、工具串成单智能体循环。
  4. App + Gateway/CLI：用 app.py 做装配，入口层只负责协议转换。
  5. Team + Tasks + Cron：在单 Agent 基础上增加多智能体协同、任务看板和自动化。

3. 与 Crew 的差异

本索引对应 Ace（Crew 开源版）实际代码。Ace 的 sites 模块对外提供“灵感”统一 App 库；内部继续保留网站 Release 与 Canvas/Widget 运行时。Ace 移除了 api 模块（开源版脱敏移除）。

4. Team @Agent 直达入口第一阶段（2026-08-17）

  • WebSocket Gateway 只校验并透传结构化 user_mentions；它不解析用户输入中的 @名称，稳定 member_id 仍由 TeamManager 对当前团队名册校验。
  • 带有合法结构化 mention 的 Team 回合在 TeamTurnRouter、TeamSpec 和 DAG 之前进入既有 route_user_mention / TeamAskCoordinator 直达链路；普通 Team prompt 的工作流路径不变。
  • Gateway 不接受非法 mention 结构并回送状态提示，避免错误数据静默回退成普通 DAG。

验证：Gateway mention 结构回归与 Desktop composer mention 回归通过；本阶段没有新增后端模块或 Team 数据源。

5. Team @Agent 直达生命周期第二阶段（2026-08-17）

  • 直达回合统一使用 user_mention_answer 搭配 waiting_reply、answered、failed、expired、cancelled 状态。
  • 失败、超时或取消先发带 request_id、reply_to 和原始请求文本的终态通信帧，再发错误帧，实时 UI 不会停留在“等待回答”。
  • 历史仍复用直接 Agent 子会话作为 canonical transcript；终态通信元数据随子会话恢复，不创建 TeamPlan、DAG 或额外持久化模块。

验证：成功与终态失败回合、历史通信字段和前端状态展示回归通过。

6. Team @Agent 并发与取消竞态第三阶段（2026-08-18）

  • 同一 request_id 继续复用既有幂等锁与终态历史，不重复发送 Team Bus 请求或唤醒成员；显式重试必须使用新的 request_id。
  • Agent/Provider 抛出未结构化异常时，通信层统一转换为 failed 终态，写回 Team Bus 与 Agent 子会话，避免只留下网关通用错误。
  • 取消后迟到的旧请求帧由 Web 按 request_id 丢弃；重试回合仍走既有发送链路并使用全新的请求身份。

验证：直接 mention 异常终态、幂等重放、取消/重试旧帧隔离、Web/ Desktop typecheck 与相关回归通过。本阶段没有新增后端模块或通信协议。

7. Team mention 运行时安全启动上下文修复（2026-08-18）

  • 问题：单 Agent 通过 Dispatcher 进入 Agent.run 时会携带已编译的 ProcessLaunch；Team 用户 @成员直接进入 TeamAskCoordinator，原链路绕过 Dispatcher，外部 ACP/Kimi 无法取得启动上下文。
  • 修复：复用当前 Team 回合已经生成的不可变 _security_process_launch，由 TeamManager → TeamCommunicationRouter → TeamAskCoordinator 显式传入回答成员的子 Envelope。
  • 边界：不放宽安全策略、不新增进程启动逻辑；若 Team 回合没有明确的 ProcessLaunch，ACP 仍按既有 fail-closed 规则拒绝启动。

验证：Team 用户 mention、幂等/失败状态与 WebSocket 结构化 mention 回归通过。

8. Team @Agent 直接通信流式 timeline（2026-08-18）

  • 单独用户 mention 继续走 TeamAskCoordinator 的直达回答，不创建 TeamPlan、DAG、任务或产物；但现在通过 per-request callback 将 Agent 的 delta、thinking 和 tool 帧透传到 Team 内部消息协议。
  • 流式帧使用既有 team_internal + event_type=team_stream + communication_kind=user_mention_answer，终态仍使用同一请求的 answered/failed/expired/cancelled 状态。
  • 安全边界和 direct ask 的只读回答提示保持不变；一致的是 Agent 回答过程，不是把 direct mention 伪装成团队节点。

验证：用户 mention 流式/思考/工具回归、Team Bus 状态与无 DAG 断言通过。

9. Team 历史 mention 成员身份恢复（2026-08-18）

  • 历史投影对 user_mention_answer / ask_answer 优先使用持久化的 mention_from 解析成员画像，而不是直接沿用旧事件里的 agent_id。
  • 兼容旧事件中 agent_id=crew::builtin 但实际回答成员为 kk 的情况；历史回放恢复 kk 的成员名称、职责、色调和头像身份，Crew 头像只保留给真正的 Crew 成员或规划回合。
  • 修复集中在既有 team/history_projection.py，不新增历史字段、迁移脚本或通信模块。

验证：旧事件身份恢复、Crew 子会话身份映射与重复通信回归通过。

10. Team direct mention 历史消息所有权（2026-08-18）

  • 通信语义：普通用户 Prompt 仍由 Leader 进入 TeamSpec / DAG；用户 @Agent 走“用户 → 目标 Agent → 用户”的直接通信；成员之间的 mention 只回复给发起成员。
  • 唯一可见回复：direct mention 的成员子回合是 canonical 对话消息；Dispatcher 创建的父 agent_turn 只作为运行时记录，不再被历史投影成第二条 Crew / Leader 回复。
  • 关联方式：历史投影使用 request_id 和 communication_kind=user_mention_answer 识别 direct mention，不解析 Prompt 文本，也不依赖关键词。
  • 影响边界：普通 Team workflow 的父任务结果和 team_summary 去重规则保持不变；本阶段不新增数据库表、迁移脚本或前端渲染模块。

验证：新增 direct mention 父任务与成员 canonical 回答的历史投影回归，确认用户消息和 kk 回复保留且不再生成 Crew 重复气泡。

11. 外援身份一致性 P1 修复（2026-08-27）

  • 外部 Team 成员的运行时 member_id 统一使用不可变的 external_agent_id，展示名称只作为 name；同名外援不会再因字典键覆盖而丢失。
  • 单外援 Session 将 external_agent_id 归一到 external.external_agent_id。顶层、acp 和 canonical 字段的相同旧写法可兼容读取；缺失或互相冲突时在持久化前返回 400。
  • 旧 Team 快照、计划节点和派活记录仍支持按唯一展示名称解析到稳定 ID；重复名称不会猜测改派，避免静默执行到错误成员。

验证：外援/Team Gateway 与任务回归 293 passed, 1 skipped；新增覆盖单外援配置缺失/冲突/重复字段及 Team 同名成员身份隔离。本阶段未新增后端模块、数据库表或迁移。

12. TeamPlan 派活语义收口 P2-4（2026-08-28）

  • 唯一派活入口：内部 delegate_to_teammate、Team team_mention(assign) 和外部控制面 request_delegate 均必须绑定现有 TeamPlan 节点；无计划、缺少节点、成员不匹配或节点状态不允许时统一拒绝。
  • 移除旧语义绕过：删除 allow_legacy_without_plan 和无计划 Legacy Delegate 分支。Workflow Runtime 预先标记节点为 in_progress 时使用显式内部预占校验（preclaimed_node），仍不允许重复绑定已有任务。
  • 兼容边界：旧 TeamPlan/看板继续由 TeamPlanStore.hydrate() 恢复；旧事件仅用于读取和恢复，不再作为无计划派活入口。无法恢复计划的旧 session 返回明确错误，不静默执行旧逻辑。
  • 结构清理：TeamManager 删除重复的 Leader 解析 if/else，计划派活回调不再使用 legacy_delegate 运行语义。

验证：Team 回归为 251 passed, 1 skipped，Gateway/Kanban 回归为 94 passed；覆盖有/无 TeamPlan 的内部与控制面派活、持久化计划恢复、重复派活拒绝和 Workflow Runtime 预占状态。同步完成 Python 编译、Ruff 的 E9/F 检查与 git diff --check；全量 Ruff 的历史遗留告警未在本阶段扩大范围。

13. 外援 Timeout Policy 统一接入（2026-08-31）

单外援与 Team 外援统一由 core/timeout_policy.py 管理 idle timeout、hard deadline、Followup 等待和交互绑定 grace period。配置入口为 runtime.timeout_policy；显式 hard_timeout_seconds: 0 表示不设外部适配器硬截止，同时保留 idle 与 token 生命周期边界，应用级 TaskRuntime 仍可独立兜底。省略配置时继续使用各协议现有兼容默认。

验证：Timeout Policy 与外援/Team/Gateway/Kanban 组合回归 483 passed, 1 skipped；macOS Seatbelt 安全 Runtime 组合中 2 项受当前执行环境 preflight 限制。
