Acrew/agent/subagent

把“如何委派”与“在哪里运行”分开；Provider 由 Feature 插件贡献，模型只选择任务或专家，不接触传输路由。

本模块按“请求契约 → 策略收窄 → Provider 解析 → 能力预检 → 结果折叠 → 旧工具适配”运行。阶段 A 建立语义内核，阶段 A2 用进程外外援作为第二种真实传输验证抽象，阶段 B 补齐账本与调度，阶段 C 将完整能力迁入 product.subagent Feature Generation；阶段 D1-D5 已补齐持久 continuable 身份、隐藏子会话、驻留控制面、父级授权、持久邮箱和通知来源分离，fork 与 UI 贡献仍属于后续切片。

层回答的问题阶段 A 状态
契约调用方请求了什么能力，Provider 能否诚实满足已落地
策略子智能体最终能看到哪些工具，是否可能越过父授权已落地
运行时谁负责发布、结局、超时、清理与批量隔离已落地

产品面旧工具 schema、返回 JSON 与后台任务如何保持兼容兼容适配保留，资源由 Feature Scope 管理

1. 职责与边界

  • 负责：能力预检、Provider 路由、一次性运行句柄、深度入口、双超时、部分输出、批量并发隔离、工具权限只收窄、旧返回格式适配。
  • 不负责：主 Agent 缓存、Team Formation、外援 Catalog 与进程安全、fork 上下文继承和 UI；持久化身份的核心控制由本模块负责，Team 通信仍由独立方案承接。
  • 跨平台边界：只依赖 Python 的 asyncio、值对象和进程内回调；不依赖 Unix signal、fork(2)、文件锁或权限位。

2. 一次委派如何运行

发布边界只有一处：请求在 Provider 启动前完成能力与深度校验；Provider 成功返回 SubagentRun 后才算发布。发布前异常向调用方抛出，运行中的异常则折叠为结果数据。

工具参数
  │ 参数校验 + ChildAgentRequest
  ▼
SubagentRuntime.start
  ├─ 未知 Provider / 不支持能力 / 深度越界 ──► 直接失败，无活跃残留
  └─ 生成 immutable descriptor
           │
           ▼
Provider.start
  ├─ inprocess-spawn：AgentFactory + chunk + idle/absolute timeout
  └─ external:*：Catalog + DelegationService + external event stream
           │
           └─ 两条传输均折叠为 SubagentResult
           │
           ▼
SubagentRun.dispose（并发与重复调用均只清理一次）
           │
           ▼
结算：run log 折叠 stop_reason（唯一推导入口）→ runs/edges/descriptors 落库
           │
           ▼
工具适配器输出旧 JSON：agent/status/stop_reason/summary/duration_seconds/tool_calls/last_tool

错误通道与模型输出分离：诊断进入 diagnostic，子智能体真正说出的内容进入 output/partial_output。清理失败只记录日志，不覆盖已确定的业务结局。

3. 核心契约

抽象运行时含义
StartRequest传输无关的启动意图；声明目标、父会话、生命周期、深度与所需能力。
SubagentCapabilitiesProvider 对结构化输出、深度、工具过滤、persona、agent options 的五位诚实声明；不支持即 fail-loud。
SubagentDescriptor发布时冻结的身份快照；由 subagent.db 的 descriptor 表持久化。
SubagentRun已发布运行的句柄；暴露结果 awaitable 与幂等 dispose()。
SubagentResult稳定结局：completed / aborted / error / max_tokens / refusal / timed_out，超时另带 idle / absolute 类型。
SubagentProvider传输扩展点；阶段 A 的默认实现为 inprocess-spawn。
AgentFactory由 core.agent-factory Feature 提供的 typed child 创建服务，避免 Provider 依赖 CrewApp 私有 dict 回调。

4. 权限与委派纪律

工具策略是纯函数。普通子智能体的工具集合按“父授权快照 ∩ 用户请求 ∩ access control − 黑名单 − reserved toolsets”计算；preset 的专用工具只能从预先计算的授权上限中加回，不能借 preset 扩权。无 tools 能力的模型得到空集合，文本模型会去掉视觉工具。

主 Agent 的静态提示词由 features.subagent.delegation_mode 控制：默认 explicit，只有用户、项目指令或技能明确要求委派/并行才允许使用；proactive 才允许在边界清晰且有并行收益时主动委派。轻量子智能体不注入这段主 Agent 纪律，其简报要求把自包含结果交回父级、不得直接向用户提问，并区分已验证事实与自述。

5. 外援作为插件 Provider

product.external-agents 声明对 ServiceKey("subagent") 的可选依赖。安装时它只注册一个 external: Provider family resolver，注册 token 归当前 Feature Scope；Subagent Runtime 和工具层不导入、不判断任何外援类型。

product.subagent Feature ──提供──► SubagentService
                                      ▲ optional resolve
product.external-agents Feature ──────┘
  ├─ owner-aware Catalog 查询
  ├─ 动态解析 external:<agent_id>
  ├─ ExternalDelegationProvider → DelegationService
  └─ Scope stop：先撤 resolver，再关闭 admission / run / resource

resolver 每次按当前 owner 查 Catalog，因此不会在进程启动时把 local owner 固化为全局 roster；新建、删除或跨 owner 不可见的外援会即时反映为 Provider 可用性。外援 Feature 停用后 resolver 被撤销，preset roster 自动收缩，新委派返回 UnknownProviderError，不会回退到进程内执行。

ExternalDelegationProvider 的五项能力全部为 false，且 inherits_parent_context=false。它把自包含简报、cwd、owner/workspace 与外援自身模型配置组装成 RuntimeExecutionRequest；权限请求固定拒绝。text、tool、usage、session/session_reset 与 error 事件被折叠为稳定结果，usage 采用最后快照而非重复累加。

6. Feature 生命周期

product.subagent 是可停用、可重启的 Feature Generation，必需依赖 core.agent-factory，提供版本化 SubagentService。每代独立拥有 SubagentRuntime、ActiveSubagents、SubagentStore、通知队列、三个模型工具、preset contributions、/api/subagents 路由和 subagent.lifecycle 事件源。

core.agent-factory
        │ requires
        ▼
product.subagent Generation
  ├─ ServiceKey("subagent")
  ├─ Scope-owned runtime/store/background tasks
  ├─ tool/context/preset/route/event registrations
  └─ stop=DRAIN · update=RESTART · optional product feature

Gateway 通过 Route Registry 的代际闸门访问 /api/subagents；请求先租用当前 Generation，再读取当前 owner 的活跃快照和历史 runs。工具处理器同样持有 Feature Lease，因此更新或停用只会拒绝新工作，并等待在途调用完成后撤销贡献和关闭资源。CrewApp.subagent_* 仅保留兼容视图，不再负责构造或注册内部对象。

7. Preset 路由与能力塑形

Preset 可在声明中绑定 provider，该字段从不进入模型参数。run_agent 只列出当前 owner 下 Provider 可解析的 preset；不支持 agent_options 的 Provider 不暴露 model，混合 roster 用互斥 schema 分支约束可覆盖模型的专家集合。零上下文继承的 Provider 会在工具文案中要求自包含 goal/context。

工具/技能范围、模型覆盖、结构化输出等请求先转成显式能力需求。Provider 不支持时由 Runtime 在发布前抛出 SubagentCapabilityError；不会忽略配置，也不会换一个 Provider 偷跑。

9. Continuable 身份与控制面（D1-D5）

开启 features.subagent.continuable 后，新的 delegate_task / run_agent 委派以 subagent_id 作为持久身份，并把 session_persistence 固定为 hidden。进程内 Provider 每轮使用 {parent}::subagent::{subagent_id} 作为 canonical session，复用既有隐藏会话列表约定；descriptor 的 first-wins 规格保证恢复时不会被后续请求改写。

parent session
  │ owns + authorizes
  ▼
subagent_id ── descriptor(spec, provider, depth, hidden session) ── subagent.db
  │
  ├─ Activation.lock：同一身份的 send_message 串行
  ├─ pending_messages：trigger_turn=false 时进入 ready
  └─ state：running / idle / ready（由驻留与队列派生）
工具语义授权边界
send_message向 continuable 子身份投递消息；可选择立即开轮或先排队。必须同时匹配当前 owner 与直接 parent session。
list_agents列出当前父会话的直接子身份与派生状态。查询在 Store 层按 owner + parent 过滤。
interrupt_agent中断正在执行的子轮次，或清空尚未开轮的待投递消息。不接受任意 parent/owner 的跨身份操作。

10. 已知边界与后续阶段

  • 阶段 B 已交付：run log 与六态结局折叠、四张自有表（runs/edges/descriptors/messages，first-wins descriptor + 软删除边 + 保留期清理）、深度账本（单调下界 + allow_nested 可见性真值表）、通知四态路由（消失丢弃/拆除只入队/忙 steer/空闲等恢复轮，内容单通道）、批量调度（爬坡 + 限流退避 + 定序聚合）与同构模板批量（prompt_template + items）、摘要兜底（preset 可覆盖阈值）。
  • 阶段 C 已交付：product.subagent Feature 统一拥有 runtime/store/background tasks、通知、工具、通用 preset、路由和生命周期事件；配置仍从现有 Config 兼容入口读取，外援以 optional Service consumer 方式在其后激活。
  • 阶段 D1-D3 已交付：continuable 身份、隐藏 canonical session、first-wins descriptor 中的运行规格、Activation 单身份串行锁、owner/parent 双重授权，以及 send_message / list_agents / interrupt_agent 控制面。features.subagent.continuable=false 时工具保持 one-shot 且控制面不注册。
  • 阶段 D4 已交付基础持久邮箱：trigger_turn=false 的消息写入 subagent_messages，重启后仍可由授权父会话消费；D5 已补齐后台结算通知的结构化来源分离；D4-D6 余项为更细粒度冷恢复身份校验、三态驻留事件、task_id/subagent_id 分账和连续会话 UI 消费。
  • 阶段 E：fork、结构化输出、preset 收尾与 UI Contribution。
  • 限流重试目前是"同一简报重放"（进程内 one-shot 子级无可复用轮次）；子级上下文复用型重试随阶段 D continuable 引入。
  • 后台任务持久化仍由兼容适配器承接；语义执行、并发、超时与调度已从 handler 移入 Runtime/Provider。

12. 小结

Subagent 已从“工具文件里的内联执行循环”演进为“稳定语义内核 + Feature-owned Provider 插件”。进程内与进程外传输共用同一份请求、能力预检、发布边界和结局；新增传输不需要修改 Runtime 或模型工具协议。
