Ace Nearby 蓝牙同伴

Ace 的“同伴”模块通过 Bluetooth Low Energy 发现附近运行 Ace 的电脑。用户选择设备后建立会话：文字与控制消息继续走 BLE；文件请求、接收授权和 WebRTC SDP 也走 BLE，但文件字节走加密的 WebRTC DataChannel。两台电脑不要求连接同一局域网；跨网络直连失败时，需要配置 TURN 中继。产品层面的定位、模型与页面设计见 同伴（Nearby）产品设计。

产品流程

  1. 进入“同伴”页面后，Ace 发布 BLE GATT 服务并扫描附近使用相同服务 UUID 的设备。
  2. 发现结果只作为候选设备展示，不会自动进入聊天状态。
  3. 用户点击“连接”后发送 peer.connect 控制消息；双方界面同步显示已连接。
  4. 直聊默认发送 peer.message（人对人，不触发 Agent）；@ 对方 Agent 时发送 agent.request，接收端按对端隔离的会话调用本机 Agent，返回 agent.response 或 agent.error。
  5. 群主通过 create_room 建群并选择 Agent 触发模式（mention / auto / quiet），再用 invite_to_room 追加成员；模式与群名修改通过 room.settings 在群内广播同步。
  6. 发送文件时先通过 BLE 发送名称、大小与 SHA-256；接收方在 Desktop 原生弹窗中点击“接收”后才交换 SDP 并启动 DataChannel。
  7. 关闭“允许被发现”会停止本机 BLE 广播；停止查找只影响本机扫描。

BLE 协议

服务 UUID 为 5957645b-4b06-49cf-bde2-366a593e73a7。GATT 服务包含 PeerInfo、IncomingMessage 和 OutgoingMessage 三个特征。Central 订阅 OutgoingMessage 通知，并向 IncomingMessage 写入分片 JSON 帧。

每个实例持久化一个随机 Peer ID。物理连接建立后，Central 先读取静态 PeerInfo，再按两个 Peer ID 确定唯一连接发起方；非发起方会在写入通知订阅前关闭重复物理连接，避免 macOS 与 Windows 同时扫描和广播时争用 GATT 会话。保留连接随后订阅 OutgoingMessage 并完成 hello 身份握手。Windows 写入 Notify 的 CCCD 失败时会清理监听器并最多重试 3 次，日志保留底层 WinRT 状态和完整错误链。

只有用户选择设备并交换 peer.connect 后，界面才进入已连接状态。主动断开使用 peer.disconnect。当前协议为 v4（PROTOCOL_VERSION = 4）：新版本增加文件授权和 WebRTC SDP 信令；版本不一致的客户端不会交换业务消息。

文件传输链路

  1. Gateway 校验附件属于当前账号 uploads 目录，限制 4 MiB，并以 64 KiB 缓冲流式计算 SHA-256；Desktop/Rust IPC 只传受控绝对路径，不传 Base64。
  2. 发送方通过 BLE 发送 file.offer；接收方弹出原生确认框，并用 file.decision 回复接收或拒绝。
  3. 接受后，发送方创建 WebRTC Offer，接收方创建 Answer；两段 SDP 通过现有 BLE 会话交换，不需要中心信令服务器。
  4. ICE 优先选择可用直连路径；不同网络或严格 NAT 下直连失败时使用 TURN。DataChannel 使用 DTLS/SCTP，配置为可靠、有序传输。
  5. 发送端按 12 KiB 流式读文件并做发送缓冲背压；接收端写入 ~/.Crew/nearby/received/*.part，核对大小和 SHA-256 后原子改名，再回完成 ACK。
  6. 拒绝、120 秒超时、BLE 会话断开、WebRTC 关闭或摘要不匹配都会产生 file_transfer_failed，临时文件会被清理。
ACE_NEARBY_STUN_URLS=stun:stun.example.com:3478
ACE_NEARBY_TURN_URLS=turn:turn.example.com:3478?transport=udp,turns:turn.example.com:5349
ACE_NEARBY_TURN_USERNAME=ace
ACE_NEARBY_TURN_CREDENTIAL=replace-with-secret

ACE_NEARBY_STUN_URLS 逗号分隔；未设置时使用公共 STUN 默认值。TURN 不随 Ace 内置，生产环境建议部署 coturn 并通过上述环境变量注入短期凭据。STUN/TURN 是 ICE 连通服务，不负责“发现附近同事”；附近身份和用户授权仍由 BLE 完成。

消息类型

类型用途
peer.message人对人直聊文本，payload 为 {text, mentions[]}，≤ 8000 字符，不触发对端 Agent。
agent.request / agent.response / agent.error直聊中 @ 对方 Agent 的请求与回复。
room.invite / room.join建群邀请与入群确认；本轮新增可选字段 agent_mode、owner_peer_id。
file.offer / file.decision文件元数据和接收方授权，私聊与群聊共用。
file.webrtc_offer / file.webrtc_answer通过 BLE 交换非 Trickle ICE SDP；文件字节不进入 BLE。
room.message / room.file群聊文本与已完成文件投影；room.file 只记录受控本机路径和摘要。
room.settings房间设置变更，payload 为 {room_id, agent_mode?, room_name?}，收到后向其他成员 gossip 扇出，保证全员配置一致。
room.leave成员退出。

旧的 peer.file / room.file Base64 分片仍可读取历史并用于 Mock 回归，但 BLE 生产发送路径已停用该实现。v4 与旧协议节点通过版本检查隔离。

中继转发规则

群聊依赖中继：成员两两之间不一定都有直连会话，消息沿已有会话转发。

  • room.* 消息允许 sender ≠ 传输会话对端——sender 始终是原作者，接收方按原作者更新成员状态并继续向其他成员转发。
  • 1:1 消息（peer.message、agent.* 等）仍强制 sender 与会话对端一致，防止伪造身份。
  • room.join / room.leave 收到后向除本机与原作者外的其他成员转发，保证全员的成员列表一致。

群聊状态与持久化

  • 房间状态：RoomState 新增 owner_peer_id（群主），与房间名、成员集合、触发模式、最近消息一起随 rooms.json 持久化；每房间历史上限 200 条。
  • 直聊历史：dms.json 按 Peer 持久化直聊消息，每个 Peer 上限 200 条；peer.message、agent.request、agent.response 均落盘。
  • 幂等合并：create_room 对已有 room_id 改为幂等合并，不重置历史；invite_to_room 仅群主可调用，同样幂等合并新成员。
  • 启动恢复：IPC 进入 ready 后推送 history_snapshot 事件，携带 rooms + dms 全量快照，桌面端据此恢复会话列表与历史。

主进程编排（nearby-agent-bridge）

desktop/src/main/nearby-agent-bridge.ts 监听 Nearby 运行时事件流，维护每个房间的触发模式与最近消息，收到 room.message 后按以下裁决链决定本机 Agent 是否响应：

  1. 本机自己发的消息直接跳过；
  2. auto_reply 开关关闭则不响应；
  3. 按房间 agent_mode 裁决：quiet 一律不响应，mention 仅在 @ 本机时响应，auto 全员响应；
  4. 并发上限 8、按 room_id + message_id 去重、回复截断 8000 字符；
  5. 裁决通过后调用 runNearbyAgentTurn，携带 room_id、room_name、最近 ≤ 20 条 history 与 allowed_toolsets；
  6. 回复以 send_room_message 发回群内，并 @ 原发送者。

同伴 Agent 设置存于 ~/.Crew/nearby/settings.json：discoverable 由 Rust 运行时持有，auto_reply / allowed_toolsets 由主进程读改写合并（只覆盖这两个字段，其余原样保留）；收到 discoverability_changed 事件后主进程会重合并一次，防止 Rust 侧写入时覆盖主进程的设置。

后端 agent-turn 扩展

POST /api/nearby/agent-turn（crew/gateway/routers/sessions.py）本轮新增入参：

  • room_id / room_name：携带 room_id 即视为群内触发，群会话 key 为 agent:main:nearby:room:<hash>，与直聊会话 agent:main:nearby:dm:<hash> 相互隔离；
  • history[]：群聊最近消息，最多取 20 条、单条截断 500 字符，拼入 channel_system_hint；
  • allowed_toolsets[]：工具白名单。用 crew.registry.toolsets() 校验，非法条目（含 * 通配）忽略并告警；生效时 disabled_toolsets = 全集中减去白名单，缺省 / 为空 / 全部非法时维持全禁。

安全约束不变：executor 固定 builtin、Skills 全部禁用、纯文本回复；白名单只收窄不放宽。crew/app.py 的 _make_agent 新增对会话级 disabled_toolsets 的运行时消费：在全局访问控制之上叠加排除，* 表示全部禁用。

macOS + Windows 双机验收

  1. 打开两台电脑的蓝牙；文件测试还需要双方存在可用 IP 网络。两台电脑不要求连接同一局域网，但严格 NAT 场景必须配置 TURN。
  2. 在两台电脑安装并启动同一版本 Ace，授予系统蓝牙权限后进入“同伴”。
  3. 保持“允许被发现”开启，确认双方列表出现对方设备，未点击前状态为“可连接”。
  4. 在 Mac 点击 Windows 设备的“连接”，确认双方都显示“已连接”。
  5. Mac 直接发送消息，确认走 peer.message 到达对方的人；再 @ 对方 Agent，确认 Windows 自动调用本机 Ace Agent，Mac 随后收到 Agent 回复；不需要 Windows 用户手工输入回复。
  6. 连续发送第二个问题，确认对方 Agent 保留该 Peer 的上一轮上下文；再换一台 Peer 时应使用独立上下文。
  7. 建群并邀请对方入群，切换触发模式（mention / auto / quiet），确认两端成员列表与设置一致、系统消息条正确展示。
  8. 发送文件，确认接收端先出现系统确认框；分别验证拒绝、接受、进度、保存、摘要一致，以及不同网络下的 TURN 回退。
  9. 点击“断开”，确认双方输入框被禁用；再次连接后重复双向发送，确认会话与历史保留。
  10. 关闭一端“允许被发现”，另一端重新查找后不应再出现新的发现结果。

当前边界

  • 文件单文件上限仍为 4 MiB，暂不支持断点续传；新文件内容不再受 BLE 吞吐限制。
  • 不提供已读回执、reaction、引用回复 UI。
  • 当前调用对端的默认内置 Ace Agent，不支持由请求方选择对端的其他 Agent。
  • Nearby Agent 会话默认禁用全部工具与 Skills，只能生成文字回复；主人在「同伴 Agent 设置」里配置工具白名单后，仅白名单内的工具集开放，Skills 始终禁用。
  • 文字和控制消息仍直接通过 BLE；文件优先 WebRTC 点对点传输，配置 TURN 时可能经 TURN 转发密文。Agent 生成回复时，内容仍会按接收端现有模型配置提交给本机或外部模型服务。
  • 接收端必须保持“同伴”页面打开，使 Nearby 服务继续运行，并且本机模型配置可用。
  • WebRTC 文件通道具备 DTLS 传输加密，但 BLE 控制消息尚未实现配对码和独立的应用层端到端加密；正式身份指纹确认仍待实现。
  • Linux 平台只支持主动连接，不支持被发现后被动接入。
