Crew Nearby / BLE Transport

本文档记录 Ace 的 Crew Nearby 跨平台 BLE 同伴与群聊模块。BLE 核心由 Rust 进程承载，Electron 通过 JSONL IPC 接入；macOS 使用菜单栏，Windows/Linux 使用系统托盘，三者统一显示“同伴”。

目标与边界

  • 验证 macOS、Windows、Linux 主机之间的 BLE 广播、扫描、连接、GATT 读写、订阅和通知链路。
  • 同时启动 Peripheral 广播和 Central 扫描。
  • macOS/Windows 按字典序由较小的 peer_id 主动连接；Linux 因 BlueZ Peripheral 通知 writer 的多客户端限制，由双方建立 Central 会话并在消息层去重。
  • 消息采用 JSON；BLE 层使用固定大小分片、乱序重组、重复帧抑制和未完成传输清理。
  • 桌面端可以发现多个 Agent，选择已连接的 Agent 创建房间，并通过直接 PeerSession 广播群消息。
  • 用户可以单独关闭“允许附近设备发现我的 Agent”；关闭只停止本机 BLE 广播，仍可扫描附近 Agent，也不主动断开已建立的群聊会话。

Apple CoreBluetooth 广播接口适合携带本地名称和 Service UUID，因此 Token 与完整身份信息放在 PeerInfo 特征中读取，不依赖把 JSON 塞进广播包。

发现隐私与工作目录边界

附近发现页提供“允许附近设备发现我的 Agent”开关。设置持久化在状态目录的 settings.json，默认开启；关闭后服务调用 BLE Peripheral 的停止广播接口，但保留 Central 扫描和现有会话。桌面端收到 ready 与 discoverability_changed 事件后更新开关状态。

广播发现和 GATT 读取只提供经过筛选的 PeerInfo：显示名称、Agent 名称、能力列表、协议版本和用于会话识别的 Peer ID/Token。不会把工作目录、环境变量、密钥、认证信息或本机绝对路径放入 PeerInfo，也不会在发现列表里为远端目录提供浏览或选择入口。发现页会明确显示“工作目录：对方本机私有”。

本模块对 Buzz 的工作区处理方式做了边界对齐：Buzz 在创建 ACP 会话时把 cwd 作为本地会话参数传入，公开 Agent 投影不包含文件系统路径、环境变量或密钥。因此 Nearby 的第一版只交换 Agent 能力和身份；如果后续把真实 Agent 执行接入群聊，工作目录必须由本机用户在本机安全边界内选择，不能由附近设备远程指定。

消息与分片

Message 当前覆盖 peer.hello、chat.message 和房间消息。Frame 使用 12 字节头部：协议版本、保留标志、传输 ID、序号、总片数和 Payload 长度，字段按大端序编码。实际分片容量按 Central 报告的 MTU 计算，并为 ATT 操作保留保守开销。

群聊消息使用 room.invite、room.join、room.message、room.file 和 room.leave，房间 ID 和成员列表放在消息 Payload 中。room.message 可以带 mentions 和 reply_to；提及只发送房间成员的 Peer ID，回复引用只保留消息 ID、发送者和截断后的原文。

room.file 的 Payload 包含文件名、MIME、总字节数、SHA-256、分片序号/总数和 Base64 分片。当前单文件上限为 4 MiB，Base64 会按 8 KiB 字符分片后走同一套 BLE FrameCodec；接收端允许乱序和重复分片，全部到齐后才展示“保存文件”。发送端和保存端都会校验 Base64 解码后的字节数与 SHA-256。文件不经过 Relay、S3 或 REST。

Peripheral 通知在部分平台上会广播给所有订阅者，因此接收端还会按成员列表过滤邀请和群消息，未被选择的 Agent 不会自动加入房间。PeerSession 同时承担 Central 主动连接和 Peripheral 被动接收，避免桌面端暴露 BLE 库类型。

桌面 IPC

Rust 子进程通过 stdin/stdout 交换一行一个 JSON 对象。Electron 主进程只接受受信 Renderer 的白名单命令：启动/停止发现、设置是否可被发现、创建房间、发送带提及/回复的房间消息、发送小文件、退出房间。Renderer 通过 Preload 暴露的系统文件选择器读取文件，接收端通过保存对话框落盘。Rust 输出 ready、discoverability_changed、peer_discovered、peer_connected、room_created、room_joined、message 和 error 事件。

npm run build:dev
# 或直接启动独立 IPC 模式
cargo run --manifest-path nearby/Cargo.toml -- --ipc

完整 CLI 验证模式

CLI 会启动同一个 --ipc BLE 运行时，终端输入会被转换为桌面端使用的同一组 Nearby 命令。这样可以把 UI 与 BLE/IPC 问题分开验证；CLI 的 BLE 诊断日志仍直接输出到当前终端。

cargo run --manifest-path nearby/Cargo.toml -- \
  --cli \
  --display-name "Mac CLI" \
  --agent-name "Mac Agent" \
  --peer-id crew_mac

peers
room create test --name "Test room" crew_win
send test -- "hello from Mac CLI"
send test --mention crew_win -- "please check this"
file test ./hello.txt
save <received-file-id> ./received-hello.txt
room leave test
quit

可用命令还包括 rooms、status、discover on|off 和 advertise on|off。发送消息时使用 -- 分隔选项和正文；回复使用 --reply <message_id> <sender_peer_id> <quoted_text>。收到文件后，CLI 会先完成分片重组，再使用 save 按文件 ID 校验 SHA-256 后保存。

macOS 蓝牙权限

CoreBluetooth 的权限声明嵌入 crew-nearby 二进制的 __TEXT,__info_plist 段，因此 npm run dev 和 Electron 打包产物都使用同一份声明。首次打开“同伴”并启动 BLE 后，macOS 会显示蓝牙授权提示；如果之前拒绝过，需要在“系统设置 → 隐私与安全性 → 蓝牙”中重新允许，或使用 tccutil reset BluetoothAlways com.crew.nearby 清除该进程的授权记录后重试。

诊断日志

Nearby 的 Rust 运行时把脱敏诊断日志写到标准错误，桌面端会在启动它的终端输出 [nearby][runtime] 前缀。日志覆盖适配器枚举、Peripheral 上电、GATT Service 注册、Advertising、扫描事件、连接、服务发现、PeerInfo 读取、连接优先级、订阅、Hello 写入和失败阶段；不会输出 Peer Token、消息正文或环境变量。

cd desktop
npm run dev
# 打开“同伴”后，在当前终端搜索：
# [nearby][peripheral] advertising_started
# [nearby][central] scanning_started
# [nearby][session] stage=connect_started
# [nearby][session] stage=peer_info_read
# [nearby][session] stage=connection_policy

运行

cargo run --manifest-path nearby/Cargo.toml -- --display-name "Mac One" --agent-name "Crew Agent" --capability chat --capability tools

可用参数：--display-name、--agent-name、重复使用的 --capability、--peer-id、--state-dir、--discoverable 和 --no-discoverable。未指定状态目录时优先使用 ${CREW_HOME}/nearby/，否则使用用户目录下的 .Crew/nearby/；其中 peer.json 保存 Peer ID，settings.json 保存发现开关。CLI 开关只覆盖本次启动，桌面端开关会更新持久化设置。

启动后，在终端输入文本即可发送；收到聊天消息时显示为 Peer: ...。CLI 的较大 Peer ID 一侧会在收到 peer.hello 后建立被动回传会话，因此两端都可以继续发送。macOS 首次运行可能需要授予蓝牙权限。

Mac + Linux 双机验收

在两台设备上分别执行下面命令，使用不同的显示名和固定 Peer ID，避免之前的状态文件造成误判。两台设备需要打开蓝牙并允许应用访问蓝牙；Linux 侧需要运行 BlueZ/DBus。

# Mac
cargo run --manifest-path nearby/Cargo.toml -- --display-name "Mac One" --agent-name "Mac Agent" --peer-id crew_mac

# Linux
cargo run --manifest-path nearby/Cargo.toml -- --display-name "Linux One" --agent-name "Linux Agent" --peer-id crew_linux
  1. 两端都看到 Crew BLE started、Advertising... 和 Scanning...。
  2. Peer ID 较小的一端主动连接；两端最终都看到 Connected to: ...。
  3. 从任一端发送文本，另一端应看到 Peer: ...；再反向发送确认回传链路。
  4. 桌面端打开“同伴”，选择连接的 Agent 创建群聊，依次验证普通消息、@、回复和小文件。

桌面端进入“同伴”后，选择 Agent 创建群聊；输入 @ 或点击 @ 按钮提及成员，消息卡片上的“回复”按钮会建立回复引用，文件按钮可发送不超过 4 MiB 的文件。

依赖与平台

  • btleplug：Central、扫描、连接、GATT 服务发现、读写、订阅和通知。
  • ble-peripheral-rust：Peripheral 广播和 GATT Server。
  • 未将 AGPL 项目加入依赖；当前实现保持独立 Rust CLI，未引入 Swift/CoreBluetooth 原生桥接。
  • 运行时依赖各平台 BLE 后端和系统权限：macOS 需要蓝牙授权，Linux 需要 BlueZ/DBus，Windows 需要系统蓝牙权限。Linux 的多成员路径使用 Central→GATT Write 双向传输，避开当前 Peripheral 单 writer 限制。
  • PeerInfo 特征使用静态 GATT 值直接提供完整身份 JSON；消息写入和通知仍由运行时事件处理，以兼容 Windows GATT Server 的读请求时序。
  • 桌面构建会按当前目标运行 scripts/build-nearby.mjs，并把 crew-nearby 放入 Electron extraResources。

已知限制与失败处理

  • 群聊当前是小规模直接 PeerSession 广播模型，成员必须先完成 BLE 连接；暂不提供公网服务器、历史云同步或大规模群组路由。
  • 扫描候选的连接失败会从抑制集合中清除，后续广播事件可以触发重试；已建立的会话仍保持重复连接抑制。
  • Linux 为支持多个 Peripheral 客户端采用双向 Central 会话；这会增加物理连接数量，但通过 Peer ID 逻辑会话和 message_id 去重避免重复消息。
  • Peripheral 和 Central 在同一进程内共存的稳定性需要分别在 macOS、Windows、Linux 硬件上验证。
  • 当前没有可用的第二台 BLE 测试设备，因此代码与自动化测试通过，三平台真实硬件验收仍待执行。
