2. 问题一：compact e2e 套件失效（与本次合并无关）

2.1 现象

  • 全量运行时仅 test_deepseek_connection 通过，其余 6 个用例在测试自身的 setup 步骤（app.session_store.save，crew/state/session_store.py:354 → crew/state/sqlite.py:102）抛出 sqlite3.ProgrammingError: Cannot operate on a closed database。
  • 单独运行 test_l1_microcompact_clears_old_tools 不触发数据库错误，但在 tests/test_e2e_compact.py:221 报 未找到该 session 的 LLM 请求 trace —— 对 llm.jsonl 的 trace 查找与当前应用行为不匹配。

2.2 两个独立缺陷

缺陷事实含义
A. trace 断言失效单独运行即失败；read_trace_entries 类辅助函数按 session 过滤 llm.jsonl 的约定与当前写入行为不一致任何依赖 trace 断言的 compact 用例都无法通过
B. 共享 app 生命周期fixture 为 scope="module"（test_e2e_compact.py:150），7 个用例共用一个 app；第一个用例结束后 SQLite 连接即被关闭。代码库中 CrewApp.shutdown / _close_persistent_stores 没有被测试路径显式调用的入口，关闭来源未定位第一个用例之后的所有用例必挂

2.3 与合并无关的证据

在合并前的 dev（a8d337a）临时 worktree 中，配置相同、单独运行 test_l1_microcompact_clears_old_tools，结果同为 FAILED（trace 断言）。同一次运行中模型链路健康：单次 LLM 请求 total 8.362s，run_total 33.24s。

3. 问题二：真实模型用例的时限预算不足

用例预算实际行为证据
test_e2e_run_agent_explorecollect_chunks timeout=240s（tests/_e2e_helpers.py:26 超时后追加「总超时」错误帧）超时合并代码 PERF 日志健康：skills_index 0.145s、build_prompts 0.165s；失败仅因总时长超预算
批量场景 site_skill_survives_compactiontimeout_seconds: 600（tests/e2e/scenarios.yaml）717.2s 被 runner 终止工作全部完成：3 个 widget、app-notes.md、interaction-notes.md、最后一帧为正常 final；全案 265 次 LLM 请求、skill_view 仅 4 次 start（无重复读取，watcher 化索引行为正确）

这类失败是「预算 vs 本机模型延迟」问题：deepseek-v4-flash（火山方舟）单次请求延迟叠加多轮任务后超出预算。断言的行为本身没有错。

4. 问题三：e2e 的 API Key 环境依赖

  • 应用从 profile 的 api_key_env 指定的进程环境变量读取 Key（本机为 CREW_MODEL_API_KEY，见 config/config.yaml 的 llm.models.default）。
  • 仓库根的 .env 不会被 e2e 自动加载：e2e 使用隔离的临时 crew_home，只加载 {crew_home}/.env。
  • e2e 文件头注释约定的用法即为环境变量方式（CREW_MODEL_API_KEY=... pytest -m e2e ...）。批量 runner（tests/e2e/_run_case.py）内有从 CREW_MODEL_API_KEY 补齐 profile Key 的桥接，pytest e2e 文件没有，需直接提供该环境变量。
  • 本机 .env 与 config/config.yaml 已于 2026-09-04 配置完成（均为 gitignore 文件），e2e 已可运行。

5. 建议修复方向

  1. compact 套件：修正 llm.jsonl trace 查找约定；定位共享 app 的连接关闭来源，或将 fixture 改为每用例独立 app。
  2. 预算调整：test_e2e_run_agent_explore 的 240s 与 site_skill_survives_compaction 的 600s 按本机模型延迟放宽（例如 480s / 900s），或在文档中明确这些用例的最低模型速度要求。
  3. 问题三无需修代码，属运行约定；如需更顺滑，可让 e2e 辅助函数统一支持从仓库根 .env 读取。
