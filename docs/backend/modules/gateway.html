Acrew/gateway

Gateway 网关：HTTP/WebSocket API 入口、认证与 owner 归一化边界、渠道（飞书/微信等）接入与归属、请求分发。

1. 职责

  • 对外入口：桌面端/浏览器的 HTTP API 与 WebSocket（app.py 装配，routers/ 分域路由，ws.py WS 入口），以及平台渠道（飞书/微信等，经 platform_registry + plugins/platforms）的接入与生命周期管理。
  • 认证与 owner 归一化边界：auth.py 把可信传输映射为 AccountContext（loopback → 本机 owner local；remote/email → 签名会话 → provider:user）；dispatcher.py 是 ContextVar set 点，normalize_owner_account_id 只在这类系统边界出现。
  • 请求分发：dispatcher.py 对同一 session 串行化执行（per-session FIFO + 忙时策略 queue/interrupt/steer + 全局并发上限），触发 session/agent 生命周期钩子。
  • 渠道归属：按 (platform, owner) 注册/投递渠道实例（channel_manager / delivery / channel_sessions / channel_bindings），对话事件实时广播给桌面 WS 观察者（broadcast）。
  • 不做：业务逻辑与 LLM 调用（在 crew/app.py / agent 层），gateway 只做协议转换、鉴权、串行化与投递。

2. 功能拆解

POST /api/session/{id}/side-chat 为当前账号的内置智能体会话创建独立侧边会话。服务器沿主会话的活跃历史链取最近结算切口，排除开放回合与未配对工具；新会话与源共用工作空间并固定历史前缀，不写主会话、不复用运行中的请求或授权。已明确设置的模型与外部账号权限上限可保留。普通桌面首发附带的单一 blueprint.authoring 仅在主会话生效，侧聊不继承。其他自定义能力、非内置执行、Plan 模式或没有可用切口的主会话拒绝创建。

Gateway 为已订阅会话保留精确回放序号，断开后最多保留最近 128 个会话的精确水位。淘汰时同步移除回放尾部，并在固定的 128 个槽里按账号和会话键记录已退休序号的最大值。返回的旧数字游标可以继续前进，长期离线后序号可能跳跃。带版本的游标早于保留范围时仍走历史重同步。每个回放锁只在持有它的操作和等待者存活期间占用内存。

置顶、归档、新建和删除后的桌面目录刷新共用同一请求代际。启动新一轮读取会取消较早的读取，晚到的旧响应不会覆盖最新目录。管理会话窗口在完整目录上切换归档筛选，设置页的归档查询只用于显示该页。

桌面首屏先请求当前工作空间最多 32 条未归档会话，同时读取工作空间、配置与渠道。/api/sessions 的 sidebar_status=true 把状态附在会话摘要中。窗口可以在其余分页读完前使用首批会话，恢复旧检查点时按 session_id 读取一个归属本账号的摘要。完整目录随后按每页 256 条拉取，供跨工作空间搜索、归档和管理使用。新一次刷新会取消前一次，切换账号会丢弃旧请求的结果。向旧 Gateway 请求时也兼容未分页的数组响应。

桌面首发使用 POST /api/session/{id}/ensure 的 prepare_builtin_authoring 选项，将创建空会话和补齐内建交互组件能力合并到同一个账号范围内的 SQLite 事务。Gateway 保留现有模型与会话配置，已有创作能力或使用外部执行器的会话无需改写。桌面收到合并操作的回执后继续原有权限确认和发送。与旧 Gateway 配对时，兼容原有的配置查询和更新流程。

调度器在读取起始历史前绑定所属账号、父会话和 SQLite 实例。私有执行会话另有自己的实例。旧回合收敛历史、写终态和移除私有转录时分别校验原实例。父会话被替换后停止归并，原请求按 session_replaced 收尾，原回执仍可查询。

GET /api/sessions/status 为桌面侧栏恢复状态点。Gateway 一次读取本账号可见会话及其最近终态，再以调度器内存中的运行和排队状态为准。后台失败的会话显示错误。桌面将整份快照合并为一次状态更新，保留正在处理的本地流和后台完成的未读标记。侧栏只刷新已挂载的对应行。

WebSocket 回放日志为每个账号和会话保存连续的序列后缀。每个会话最多保存 2,000 帧、2 MiB 编码内容，全部会话合计最多 16 MiB，最多保留 128 个窗口。较旧窗口按最近写入顺序淘汰。单帧超过会话限额时清除旧前缀，序列水位继续递增；带游标的客户端落在保留范围外会收到 gateway_resync，仍位于范围内则只重放缺失的后缀。活跃回合快照与回放共用同一份不可变帧字节。

同一连接的回放和实时帧进入同一个先进先出队列，在会话锁内预订回放位置后即可释放锁。每个连接允许最多 4 MiB、4,096 个待发送帧，每批从入队起最多等待 15 秒。连接超限时关闭并返回 1013，客户端可用已确认的游标重连。单个超大实时帧发送权威恢复水位；会话合包达到 256 KiB 或 256 帧会提前刷新。其他订阅者可以继续接收实时帧和终态。

桌面端的四个 Gateway 启动入口共用 GatewayStartupLog。标准输出和错误输出按 PID、来源与时间写入 userData/logs/gateway-startup.log。活动文件达到 2 MiB 时顺延至 .1 和 .2。轮转使用串行的异步文件操作。首次写入时，旧版本遗留的超大文件各保留最近 2 MiB 内完整的 UTF-8 尾部。

写队列按编码后的字节数计量，包含正在写盘的数据。达到 256 KiB 时暂缓读取子进程管道。100 ms 后磁盘仍忙就恢复读取，512 KiB 上限之外的日志计入缺口，预留 4 KiB 给进程生命周期消息。磁盘错误会向主进程控制台报告错误码，随后到达的输出在一秒冷却后触发重试，日志恢复时写入未确认或省略的字节数。退出与安装器交接先停止 Gateway，再用最多 1.5 秒等待管道关闭及日志收尾。

Gateway 退出时仅向仍开放的 WebSocket 传输启动关闭流程。客户端已请求关闭且传输正在排空时，沿用原连接的关闭回调，随后继续等待其他连接及应用退出，避免重复发送关闭帧中断数据库与技能监听器收尾。

实时推送的 gateway.push_min_interval 默认 30 毫秒。普通连续帧按同一账号和会话的发送间隔合并，序号分配并写入内存回放日志后才进入限流。工具开始、追问、Plan 评审和终态仍按原顺序先刷新待发送帧。YAML 显式间隔继续生效，配置为 0 时关闭间隔限流。

WebSocket 重连时，Gateway 按账号和会话串行处理序号分配、回放和实时订阅。新连接先按游标接收回放，再加入实时订阅。已经进入回放缓存的限流帧会先发给原订阅者，避免新连接在回放后重复收到这些帧。

会话帧包含 gateway_epoch 和 gateway_sequence。支持代次的客户端在 gateway_cursors 中按会话发送 {epoch, sequence}。Gateway 重启和账号退出都会更换对应代次。旧客户端仍可使用 last_gateway_sequences。

回合终态通过 WebSocket 的 body.outcome 发送。公开会话历史在对应用户或助手条目中提供 outcome 和 request_id，会话状态接口同时提供最近的 last_outcome。Web 使用原请求归属恢复部分完成或失败的说明，并保留该回合已有正文。Web 会话数据流

历史卡片按来源会话和发起工具调用的助手消息配对，存在请求标识时同时检查请求。旧记录以消息顺序为准，同一个调用 ID 可以在后续助手消息中复用。增量窗里的结果若对应已经显示的助手消息，网关回送快照以更新原卡片。全量和分页共用结果配对规则。

提交的游标格式无效、代次不符或越出保留窗口时，Gateway 给请求 socket 返回 gateway_resync，包含当前代次、保留下界和后续实时帧的起始水位。客户端从持久历史恢复已结束的回合。恢复消息也可携带仍待答的追问，最多保留 128 个会话、每会话 8 条、每条 32 KiB。

客户端可用 gateway_snapshots 协商在途快照。普通前台 Agent 回合在用户消息提交后捕获一页历史，按回放锁记录已过滤的增量、工具和状态。恢复响应在同一水位发送历史与在途投影，客户端重建界面并接续新帧。最多保留 16 个在途快照、每个 2 MiB 的编码数据。快照缺失、超限或回合已转后台时，客户端保留已显示的内容，在回合结束后补齐历史。

独立线程 Health 服务与循环活性哨兵（2026-09-17）

主 /api/health 与所有 agent 业务共用 uvicorn 的 asyncio 事件循环，业务卡顿时健康探测随之超时。健康端点因此拆成两层：

GET /api/health（主端口）          FastAPI 路由；components 由 build_health_components 计算
health 线程服务（默认主端口+1）     stdlib ThreadingHTTPServer 独立线程，仅 /api/health
  独立 Gateway 可以用 runtime.health_port 覆盖端口，绑定失败后继续使用主端口
  桌面受管 Gateway 必须获取主端口 +1，绑定失败时主端口返回可验签的启动失败
响应语义                            与主端点完全对齐：复用 build_gateway_health_payload
                                    （instance proof fail closed）+ components 快照
loop_lag_ms                         业务循环滞后毫秒：哨兵 task 每秒 note_loop_tick(loop.time())，
                                    health 线程读时间戳差值；区分「进程活但循环忙」与「进程死」

components 快照（startup / cron 状态）由业务循环上的哨兵 task 每秒戳到模块级变量，主端点与线程服务共用同一份 build_health_components 逻辑，两处响应不会出现语义分叉。线程服务生命周期挂在 FastAPI lifespan 内：启动早期拉起，shutdown 的最后一步停止——shutdown 期间桌面端仍能看到进程活性与循环滞后。桌面端探测优先打 health 线程端口（主端口 +1，backend-health-probe.ts 推导），验证失败（旧 gateway 无独立 health 线程）再回退主端口。

桌面受管启动通过父进程租约辨认。若独立健康端口无法绑定，lifespan 跳过核心任务及可选服务的启动，主端口健康响应返回 GATEWAY_HEALTH_PORT_UNAVAILABLE。REST 和 WebSocket 的业务入口继续受启动状态约束。桌面验签并确认这是本次启动的子进程后，关闭该进程的父管道并等待退出，再继续选择端口。

Windows 安装版启动受管 Gateway 时传入当前桌面沙箱准备状态的位置。后台调用只在实际启动同一随包运行时前等待；独立启动的 Gateway 在引导阶段清除此位置。Windows 沙箱准备流程
