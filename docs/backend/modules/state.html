Acrew/state

State 状态层：配置加载/写回、API Key 凭证库、Crew Home 与 owner 运行时目录、会话/工作区存储、日志。

1. 职责

  • 持久化与配置事实来源：config.yaml（结构化配置，不含密钥）+ .env（环境变量密钥）+ credentials.json（模型 API Key 凭证库）。
  • 目录布局（方案 A）：CREW_HOME（默认项目根 .crew/，打包环境 ~/.crew/）退役为安装级目录（config.yaml、日志、skills 模板）；所有 owner（含本机 local）的运行时 home 统一住 accounts/<hash>/，目录名由 owner_path_segment 从 owner id 哈希派生，不泄露身份。
  • 不做：业务逻辑、LLM 调用（装配在 crew/app.py）。

4. 数据模型与接口

模型 API Key 解析链（resolve_profile_api_key，所有 profile 构建点统一走它）：

凭证库[profile_id]（owner 作用域，credentials.json）
  → api_key_env 环境变量（env_map 优先于进程环境）
  → （仅全局/共享层）CREW_API_KEY 兜底

写路径（crew/app.py 模型 CRUD）：默认 store_key(owner, profile_id, key)； 显式传 api_key_env 才写 .env——当目标变量名被其它 profile 引用且已有不同旧值时， 必须 payload 带 overwrite_shared_key: true 才放行（防"所有 apikey 变成最新的 apikey"）； remove_model 同步清理凭证库条目。

owner 归一化规则（owner 统一化改造）：空 owner 不再是一种"模式"，而是归一为本机 owner local 的特例。 归一化原语 normalize_owner_account_id() / 常量 LOCAL_OWNER_ACCOUNT_ID 定义在 crew/core/runctx.py，只允许出现在系统边界——gateway 认证、CLI 入口、ContextVar set 点、 store 创建入口与存量回填；边界之内 owner 恒非空，owner_account_id="" 在存储层不再是合法模式， 读取方不写任何 if not owner / or "local" 防御分支。

回合内 durable boundary（2026-09-18）

SessionEventType 新增 tool_execution_intent 与 tool_result_commit 两类 durable 事件。它们和 session leaf 在同一写事务中提交，但不进入 Message 投影，因此不会污染下一次 Provider 请求。

Agent 在用户消息完成校验后先保存 canonical history；工具开始前记录 intent，结果（包括 timeout、aborted 和异常）记录 commit。启动恢复扫描 intent/commit 链，对未闭合的工具追加 status=interrupted、side_effect_state=unknown 的结果边界，保持幂等且不自动重放副作用。

Channels 配置读写闭环（6AA）

features.channels 与旧 channels 的双读优先级沿用 6X。保存当前渠道时，将完整有效值写入选定节并清除该渠道的旧别名，避免更新后重载恢复旧值，以及删除字段、清空 extra 后再次被兜底补回。其他渠道、未知有效字段和其他 owner 保留；owner 仅读取自身 overlay，不继承全局渠道配置或旧 platforms。

仍使用配置写锁、系统路径与临时文件原子替换。设计与回退见 ADR-0039，验证见 6AA 测试记录。

配置写回隔离与事务（2026-09-14）

渠道配置写回的两个契约修复：隔离性——_write_channel_config 在构造目标渠道有效配置前对平台值与渠道有效合并结果做深拷贝，YAML anchor 使两个渠道共享嵌套 extra 时，删除一方字段不再串改另一方或调用方传入对象；事务性——提取 _atomic_write_yaml（tmp 写入 + 原子替换 + 失败清理残留并重抛），channel / mcp_servers / model_profiles / evolution 四个 persist 统一为磁盘提交成功后再发布内存状态，写盘或替换失败时内存与磁盘一致保留旧值。验证见 整改批次测试记录。

配置操作完整事务（2026-09-15，第二轮整改 S2）

配置写回从"先改内存再持久化"升级为候选值 → 校验 → 持久化 → 发布的统一事务边界，覆盖 MCP servers、模型 profiles（含激活/默认切换）、evolution 开关三类操作：MCP 的 _commit_mcp_servers 与模型的 _commit_model_profiles / set_active_model / set_evolution_config 都在候选副本上计算、经 _atomic_write_yaml 落盘成功后才发布内存（mcp_servers/model_profiles/raw_config 等）。持久化失败时内存与磁盘一致保留旧值、可直接重试，且不得触发任何运行资源操作（provider 重建、MCP 子进程启停等只在持久化成功后进行）；"已保存但连接失败"如实上报、不回滚伪装成保存失败。gateway Router（mcp_servers / misc）与 CLI（integration / knowledge）全部改走事务入口，遗留 set_mcp_server/persist_model_profiles 等两步式入口仅为未迁移调用方保留并标注。模型配置 owner 语义：全局事务只写 config.yaml 的 llm 段，owner overlay 层天然按文件隔离，互不影响。边界：不承诺多文件与外部运行资源的分布式原子性。

llm_trace 队列落盘与运行期超时配置（2026-09-17）

llm_trace 开启时热路径（每次工具 start/result）只做 queue.put：json 序列化与 .jsonl 文件写入都在 QueueListener 后台线程完成。队列为带排空等待的 _TraceQueue（put 计数 + task_done 条件通知），flush 可等全部已入队记录真正落盘；listener 随日志装配建立、atexit 收尾。工具媒体读盘、prompt 文件读取等其余热路径 I/O 治理见 agent 模块文档。

SQLite 同步写路径（BEGIN IMMEDIATE + busy 重试）的睡眠收进模块级 _busy_retry_sleep（可注入，测试替换为 no-op）：只允许在非事件循环线程执行——execute() 是同步 API，事件循环上的写必须走 execute_async（内部 asyncio.sleep + to_thread）；个别存量同步 store（如任务看板 TaskManager）的写方法会被事件循环直接调用，消除方式是把调用方挪到 asyncio.to_thread（后台子任务已治理，见 agent 模块）。

runtime.tool_execution_timeout_seconds  # 单工具执行段看门狗，默认 600，0=关闭
runtime.turn_deadline_seconds           # 整回合 deadline，默认 0=不限
runtime.interaction_timeout_seconds     # 追问/权限默认等待上限，默认 3600，0=默认不限
                                        #（显式传 timeout 含 None/0 始终优先于默认值）
runtime.health_port                     # 独立线程 health 服务端口，默认 0=主端口+1

追问默认上限由装配层（crew/app.py 的 set_followup_default_timeout）注入 core/followup，core 不反向依赖配置实现；wait_for_answer 未传 timeout 时用该默认值，超时按「用户未回答」收尾（返回空答案）。

本次更新：TraceStore 与有界写入（2026-09-23）

TraceStore 使用独立 SQLite 文件、owner scope、外键和 WAL（不支持 WAL 的文件系统回退 DELETE）。无受信业务归属的启动/第三方日志写入独立 system scope，不伪装成 local；系统追踪日志由诊断管理员专用查询合并展示，trace/span/payload 仍严格按 owner 隔离。ObservationRecorder 在业务线程完成脱敏后进入有界队列，由单一 writer 以批量事务写入；队列满、SQLite 忙或关闭超时只标记降级，不阻塞业务收尾。trace 计数和字节账本有固定上限，关闭不会在满队列上无限等待，stop 哨兵也会完成队列计数。

payload schema 保存 capture_layer、policy/version、截断原因及引用水位。分页查询使用 keyset cursor；导出通过独立临时文件分页生成，并在 manifest 中记录 snapshot 水位、数量与 partial 原因。
