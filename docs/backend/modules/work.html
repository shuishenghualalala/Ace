Acrew/work

Work 工作单元：用户工作上下文与长期任务管理。

1. 职责

  • 管理办公会话、Work Item、Reference、Preference、Source、Brief、Settings、Template 与知识发布请求。
  • 通过 product.work Feature Bundle 统一发布稳定 Service、REST Route 和 agent:end Hook，并拥有本代 SQLite 资源。
  • 个人知识只消费可选的 KnowledgeService 契约，不持有 Wiki Store；组织知识通过只读 Provider 注入。
  • 不负责用户认证、Workspace 授权、Wiki 存储实现或 Gateway 全局装配。

2. 功能拆解

子功能说明状态
WorkService组合领域 Store，提供办公会话、工作项、偏好、数据源、仪表盘与模板用例。已落地
product.work以 DRAIN + RESTART 管理 Service、Route、Hook 与八个 SQLite Store。已落地
WorkKnowledgeStore个人知识按调用租用 KnowledgeService；组织知识、发布请求与索引状态保持 Work 本地边界。已落地
REST Consumer52 个 endpoint 从 Feature Route Contribution 装配，owner 来自认证后的 request state，同代 Service fail-closed。已落地
CLI Consumer现阶段保留 app.work_service 兼容入口，后续迁为动态 Service Lease。待迁移

4. 数据模型与接口

Feature 通过稳定 Service Key 暴露能力，具体 Store 不进入跨模块契约。

WORK_FEATURE_ID = "product.work"
WORK_SERVICE_KEY = ServiceKey("work")

build_work_feature(host, *, db_path, wal_enabled, ...)
  - optional: knowledge
  - provides: work
  - stop policy: drain
  - update strategy: restart

REST 请求先持有 Route Generation Lease，再按该 Generation 获取 WORK_SERVICE_KEY；任一步不可用都返回 503。个人知识操作独立获取并释放 KnowledgeService Lease，使 Wiki 重启时不会保留旧 Provider。

5. 当前存在的问题 / TODO

  • Work CLI 仍通过迁移期兼容字段取 Service，后续应改为动态 Service Consumer。
  • Desktop/Web 的 Work 页面、API Client 与事件 reducer 尚未进入 UI Contribution 生命周期。
  • 当前本地 Knowledge 页面模型仍使用 Wiki 公共 Schema；远程 Knowledge Provider 落地时需核验该 DTO 是否应提升为独立契约。

6. 扩展点

  • 新增领域能力优先扩展现有子域 Store 和 WorkService，不在 CrewApp 增加业务分支。
  • 新增 API 放入 crew/work/routes.py，并保持 request.state.account owner 与同代 Service Lease。
  • 新增外部知识实现通过 KnowledgeService 注册；Work 不导入 Provider 内部对象。
  • 逃逸请求调用栈的 Task 必须由 Work Generation 的 FeatureScope 创建和回收。
