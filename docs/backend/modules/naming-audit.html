1. 命名空间约定（正式约定页）

以下六条自本页发布起作为开发约定。命名空间一经发布视为公共契约，变更走与 API 相同的兼容流程。

资源约定示例说明
配置 key features.<name>.*；核心保留 core.* features.wiki.provider 每个 Feature 只读自己的子树；env 覆盖变量统一 CREW_<NAME>_* 风格并在 Feature 内声明。
数据目录 crew_data/<name>/；Feature 不得读写其他 Feature 的目录 crew_data/wiki/ owner 隔离由统一入口（get_owner_runtime_home()）派生，Feature 不自行拼 accounts/ 路径。
数据库表 统一表前缀 <name>_；跨 Feature 不建外键、不 JOIN 他人表 wiki_documents、team_tasks 跨 Feature 关联只能经 Service 接口或冗余快照字段；表结构变更必须向后兼容。
Migration 入口 每个 Feature 独立入口与版本表 ace wiki migrate 每张库表归属唯一 Feature；版本表记录该 Feature 的 schema 版本，禁止在别处隐式改表。
Service Key 稳定命名空间，带主版本 knowledge.v1 key 常量只在 owning Feature 定义一次；消费方只 import 常量，不重复写字面量。
Feature Event <feature>.<event> + version 字段 wiki.cards v1 feature 段与 Feature ID 的尾段一致；新事件必须登记总目录（本页 §5）。

P1 合计 3 项、P2 合计 7 项、P3 合计 4 项，明细见 §6。

7. 修复建议（供后续切片逐项处理，本切片未改代码）

优先级建议对应偏差
1 解除 team → external_agent 数据耦合：去掉两个外键与两处 JOIN，改为经 ExternalAgentCatalog Service 查询，或在 external_team_member 内冗余 agent_name/agent_provider 快照字段（外部 Agent 改名不影响 team 历史）。 P1-2
2 消除 state → wiki 的模块反向依赖：Config 对 wiki 节改为原始 dict 透传（与 team_config 同法），WikiConfig.from_raw 的解析移回 crew/wiki/ 内在装配时执行。 P1-3
3 ServiceKey 加主版本并单一事实源：ServiceKey(name, version=1)（默认 v1 保持兼容），8 个 key 一次性带上版本；删除 app.py:441-442 的字面量，改 import Feature 常量。 P2-2、P2-3
4 建立 per-feature schema 版本底座：提供共享的 <prefix>_schema_version 表助手 + ace <feature> migrate 命令骨架；先把现有 rebuild/ALTER 逻辑挂到版本号下，为 P1-1 拆库铺路。 P2-4、P1-1
5 配置节迁移到 features.*：分两步——先让 loader 同时读旧节与 features.<name>（新节优先），example 给出目标形态；再按 Feature 逐个切换并删除旧节。 P2-1、P3-1
6 表前缀归一：runtime_tasks → tasks_*（或 Feature 更名）、inspiration_annotations → site_inspiration_annotations、notifications/memory 表加前缀；team 的 external_team* 更名 team_external_*。均需带兼容视图或迁移。 P2-5
7 事件命名空间决策：正式确认 kanban 为已发布契约（文档注明与 Feature ID 尾段的映射），或安排一次带 compat 的更名；新 Feature 一律取 Feature ID 尾段。 P2-6
8 清理项：删除 teams/ 死目录创建；host scope 前缀清单写入约定页；channels 绑定/路由表随生命周期化迁回 Feature 自己的 Store。 P3-2、P3-3、P2-7
