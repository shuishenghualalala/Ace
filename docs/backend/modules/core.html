Acrew/core

Core 契约：Envelope、Message、接口与所有模块共同语言。

1. 职责

  • 提供所有 Host、Core Feature 和 Product Feature 共同依赖的稳定协议与接口。
  • 定义请求、响应、消息、错误、运行上下文和 Provider/Store Protocol。
  • 不构造具体 Feature，不导入 Team、Wiki、External Agent 或 Gateway 实现。

2. 功能拆解

Core 是依赖图的底部，不是业务代码的公共杂物箱。只有跨多个 Feature 稳定复用的契约才能进入这里。

子功能说明状态
envelope统一请求与流式响应协议；mode 为开放字符串，未知能力使用稳定错误码。mode 已开放，业务事件待迁移
types消息、工具调用、模型响应等基础数据类型。已落地
interfacesLLM、Memory、Session、Workspace、Tool、Agent 等稳定 Protocol。已落地
runctx请求级用户、Workspace、权限与 Agent 运行上下文。已落地
asyncio_bridge同步代码显式调用异步能力；无事件循环时直接运行，有事件循环时投递到独立桥接线程，并拒绝在桥接线程自身同步等待，避免自循环死锁。已落地
errors / followup跨 Host 的错误和用户交互协议。CrewErrorKind 语义分类枚举 + CrewError.RETRYABLE_KINDS 可重试白名单；ProviderError 携带 kind/status/retry_delay，category 保留为兼容别名（与 kind 双向映射）。已落地

4. 数据模型与接口

稳定方向是“实现依赖 Protocol，Core 不依赖实现”。业务扩展事件与服务能力应使用命名空间标识。

Host / Product Feature / Core Feature
                  |
                  v
          crew.core Protocol

禁止：crew.core -> crew.team / crew.wiki / crew.gateway / crew.agent.external

5. 当前存在的问题 / TODO

  • ResponseChunk.kind 仍包含业务枚举，阶段 2 后续迁为命名空间 feature_event。
  • followup.py 仍依赖 crew.state.logging，后续需判断日志接口是否应成为 Host 注入能力。
  • 旧 team_internal 等业务事件仍在 Core Chunk 枚举中，后续由 Feature Event 协议迁出。

6. 扩展点

  • 新增核心接口前必须至少有一个真实消费者和一个可替换 Provider。
  • 接口只表达能力和生命周期，不暴露具体 Feature 的 Store 或 Manager。
  • 所有依赖调整必须先通过 lint-imports，不得扩大历史豁免范围。
