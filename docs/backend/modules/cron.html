Acrew/cron

Cron 计划任务：持久调度、触发执行、投递与 Agent Prompt Context。

1. 职责

  • 持久化按 Owner 隔离的定时任务和运行记录，计算 trigger 并调度执行。
  • 构造 Cron Envelope，交给共享 SessionDispatcher 执行，并记录终态。
  • 拥有定时任务触发轮的模型上下文；Agent Runtime 不理解 Cron 产品语义。

4. 数据模型与接口

    contributor_id="cron.trigger.reminder",
    phase=ContextPhase.PROMPT,
    priority=50,
    persistent=False,
)

await contribute_cron_trigger_reminder(envelope)

bundle = build_cron_feature(host, registry, store, enabled=True, max_parallel_jobs=2)
app.declare_managed_feature(bundle.definition)
await app.update_managed_feature(next_bundle.definition)

启动时，Cron 先通过 SQLite 异步写入收口进程退出前遗留的 running Fire，统一标记为 abandoned。数据库等待由写入线程承担，Gateway 事件循环仍可接收本地会话。从恢复完成到调度器启动，当前 Feature 按顺序执行，随后重新读取 Active Owner 并挂载待执行任务。恢复期间已登录或已连接的 Owner 一并挂载。同一宿主复用持久 Store 的在线重启沿用首次恢复结果，避免把后续正在执行的 Fire 当成遗留记录。恢复失败时调度器尚未启动，由 FeatureRuntime 公布启动失败并回收本代资源。

Owner 挂载与登录准入解耦。WebSocket 或本地登录只调用 request_owner_mount 登记票据，准备事务在 SQLite 写线程推进；主端口签名请求、聊天准入和注销都不等待 cron.db 写锁。同一 Owner 的重复请求复用同一个挂载任务。准备期间发生的创建、暂停、恢复和删除记入票据，安装前重读这些 Job 后一次合并，避免装入准备开始前的旧快照。注销立即让票据失效；尚未提交的准备事务回滚，已经准备好的快照不再安装。单个 Owner 挂载失败只记录日志，product.cron 保持运行，该 Owner 下次激活时重试。工具、HTTP 路由、会话删除和 Fire 收尾在访问共享 Store 前等待同一准备屏障，避免读到挂载事务提交前的任务集合。

手动执行与 Fire 重试接口只在 Owner 已挂载时受理。挂载准备中返回 409 cron_owner_mount_pending，未激活返回 409 cron_owner_not_mounted，两者都不创建 Fire。前端据此区分“正在准备”和“需要重新连接会话”两种状态。

只有 channel=cron 的 Envelope 产生 fragment；任务名来自 cron_job_name。product.cron 在宿主事件循环中激活，六个工具和每次 Fire 都持有本 Generation Lease。更新采用 restart：先取消并清理旧代，再启动新 Scheduler，最后重新挂载当前 Active Owner；失败由 FeatureRuntime 恢复旧定义。

5. 当前存在的问题 / TODO

  • HTTP Route 仍由 Gateway 内置路由表装配；下一步迁入 Cron Bundle 的 Route Contribution。
  • 持久 Store 当前作为停用后仍可访问的数据平面由 Host 关闭；后续引入稳定数据服务契约后再移除 CrewApp.cron_store 兼容字段。
  • 挂载准备按 Store 串行；外部进程长期持有 cron.db 写锁时，Cron 读取和工具调用仍等待 SQLite busy 超时。注销会中止后续写重试，Gateway 关闭收尾最多等待当前一次 BEGIN IMMEDIATE 的 busy 超时，不再累计 15 次重试。跨进程写锁的超时策略仍待评估。

6. 扩展点

  • 新增触发轮上下文在 Cron Contributor 中扩展，不向 Agent Runtime 添加渠道判断。
  • 新增 Scheduler 资源必须能被 Scope drain/cancel，持久任务数据不随 disable 删除。
