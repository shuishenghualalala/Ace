Ace「灵感」统一 App 库 —— 技术拆解

「灵感」是 Ace Desktop 里用户可创建、使用和继续设计的本地 App 集合。本文不按目录罗列文件，而是把它当作一个跨前后端的运行系统来拆解：它要解决什么问题、Agent 用哪些工具与 skill 把一句话需求变成可运行 App、运行时如何用统一协议把构建产物和声明式组件收纳进同一个图库，以及预览、批注、分享、固定、删除这条生命周期在代码里如何落地。

实现范围：统一图库与真实预览、原对话修改、离线 ZIP 分享、置顶便利贴、受控删除、对话 Surface 与元素批注。源码与原对话始终保留；不含导入、在线公开分享、跨设备同步或重启恢复悬浮窗。

1. 定位与全景

「灵感」对外是一个统一 App 库：用户在侧栏点「灵感」即看到当前账号所有 App，按更新时间倒序排列，卡片是懒加载的真实内容缩略预览。它对内仍然复用 sites 模块，并保留两种运行时——site 构建产物型与 canvas 声明式组件型——但图库、详情、对话 Surface、批注和四操作都不向用户暴露这一区别，只靠资源 ID 前缀在内部分发。

整个系统的核心动力线是：Agent 在灵感会话里调用工具产出 App，工具返回一个稳定的 InspirationSurface 协议；这个协议既是聊天里的生成物卡片，也是右侧 Inspector 预览的锚点，还是图库列表项的来源。一条数据从需求到可使用 App 的全景如下：

用户「描述你想创建的 App」
   │  新建 builtin Session（inspiration_creation=true，标题「灵感」）
   ▼
Agent 加载 skill（webapp-building / blueprint 域）生成 App 源码或 Widget 声明
   │  调用工具：publish_site  /  Canvas.show / Widget.show
   ▼
后端 sites 模块分发（ID 前缀 site_/canvas_/widget_）
   │  site：构建 release → copy_release → finish_release(ready)
   │  canvas/widget：校验 index.html → bump resourceRevision
   ▼
工具返回 InspirationSurface（kind=inspiration, mode=site|canvas|widget）
   │  持久化进工具结果 → 聊天历史生成物卡片（刷新/回放可恢复）
   ▼
右侧 Inspector 用 ace-site:// 协议加载预览（默认查看，按需指出要修改的位置）
   │  批注按原 Session 聚合为 Composer 草稿 → 发送回 Agent 修改
   ▼
图库列表（list_inspirations：site+canvas 合并，按 updatedAt 倒序）
   ▼
详情四操作：修改（回原 sessionId）/ 分享（ZIP）/ 固定（sticky 便利贴）/ 删除（级联清理）

理解这条主线就抓住了灵感功能的骨架：工具产出 Surface，Surface 是图库、预览、历史回放的单一事实来源，所有用户操作都是围绕 Surface 背后资源的生命周期管理。

2. 核心抽象

2.1 双运行时：site 与 canvas

灵感内部承载 App 的方式有两种，决定了一整套差异化的构建、预览、分享与删除行为：

维度site 构建产物型canvas 声明式组件型
本质Workspace 内一个完整 webapp 项目经 npm run build 产出的静态站点若干 Widget（每个一个 index.html）按 12 列网格 placement 组合成的 App
存储sites + site_releases 表；release 目录在 owner_home/sites/site_*/releases/rel_*/siteBlueprint 表（canvas/widget/placement/binding/automation）；Widget 源码在 .ace/blueprint/widgets/widget_*
预览release 目录的 index.html + 静态资源，注入批注 bridge运行时拼装 Canvas HTML，每个 Widget 在独立 iframe 内运行
更新重新 publish_site 生成新 release，active_release_id 切换Widget.validate 升 resourceRevision，Surface 按指纹刷新
分享ZIP = release 静态文件，根路径改相对ZIP = 离线 Canvas HTML + manifest + Widget 静态文件 + 最近成功数据快照
删除删 DB 记录 + release/export 目录 + 批注；源码与原 Session 保留删 placement → 删不再共享的 Widget → 删无 Binding 的 Automation；共享资产保留

两条运行时通过资源 ID 前缀（site_ / canvas_ / widget_）在 SiteManager 的 get_inspiration / export_inspiration / delete_inspiration 里统一分发，对上层只暴露「灵感」一个概念。

2.2 InspirationSurface：单一事实来源协议

所有发布/展示工具都返回 kind=inspiration 的 Surface。它是工具结果、流式展示、历史回放共用的最小协议——聊天渲染器从持久化的工具结果里提取 Surface 元数据，所以刷新页面、重新进入 Session 后生成物卡片仍然在。

字段取值说明
kind"inspiration"固定，标识灵感类 Surface
modesite / canvas / widget决定 Inspector 渲染哪种预览
inspirationId资源 ID图库与详情统一锚点
siteId/canvasId/widgetId对应 mode 的内部 ID按 mode 填充
sessionId原会话 ID「修改」跳回原对话的依据
title展示名卡片标题
statuspreparing / readyWidget 未通过 validate 时为 preparing
revisionIdsite=release_id，canvas=updatedAtsite/canvas 版本锚
resourceRevisionWidget 专属validate 通过后 bump，驱动 Surface 刷新

2.3 统一资源契约

类型关键字段角色
InspirationItemid, kind, title, description, workspaceId, sessionId, createdAt, updatedAt图库列表项；kind 仅内部分发，不渲染类型标签
InspirationDetailItem 字段 + site?/canvas?/widgets?/annotations详情与运行时操作所需的完整资源

InspirationSurface见 2.2工具结果/历史回放共用协议

2.4 ace-site:// 私有协议

预览不直连后端 HTTP 端口，而是走 Electron 私有 scheme ace-site://{resource_id}/。主进程 protocol.handle 把 hostname 当作 assetId，按前缀定 kind 并映射到当前认证 Gateway：site → /api/sites/{id}/preview/{path}、canvas → /api/sites/canvases/{id}/render、widget → /api/sites/widgets/{id}/render/{path}。ID 必须匹配 /^(?:site|canvas|widget)_[0-9a-f]{12}$/i，不接受任意 URL。这样预览鉴权由主进程统一注入，资源 ID 是唯一入口，后端再对 release/widget 根目录做二次边界校验。

3. 工具（Agent Tools）

Agent 不直接写文件入库，而是通过工具产出 App 并返回 Surface。灵感相关工具分两组：sites toolset 的 publish_site，以及 blueprint toolset 的四个 Blueprint 工具。所有工具 always_load=True，即开箱可用，无需额外注册。

3.1 publish_site —— 构建产物型发布

属性值
toolset / namesites / publish_site
触发仅当用户明确要求部署或发布灵感 App 时
必填参数source_path（Workspace 内目录）、name
可选参数description、build_command（默认读 package.json 的 build script）、output_directory（默认 dist）、site_id（更新既有灵感时传入）
副作用校验源码在 Workspace 内 → 构建 → copy_release → 生成 release 记录（building→ready）
返回 Surfacemode=site，revisionId=release_id，status=ready

3.2 Blueprint 四工具 action 矩阵

四个工具共享同一种 schema 形态：一个 action 枚举 + 一组可选资源字段，action 是唯一必填。这把「资源 CRUD」压成单一工具入口，避免工具数量爆炸。

工具toolsetaction 集合是否产出 Surface
Canvasblueprintlist / create / read / update / placeWidget / updatePlacement / removePlacement / show / deleteshow → mode=canvas
Widgetblueprintlist / create / read / update / validate / show / deleteshow → mode=widget（resourceRevision + validate 状态决定 status）
Automationblueprint（async）list / create / read / update / run / readRun / readRunArtifact / readRunLogs / listRuns / delete否（产出 JSON artifact 投递给 Widget）
Bindingblueprintlist / create / read / validate / delete否（连接 Automation↔Widget 的持久边）

关键约束：工具结果里的 ID（automationId/widgetId/bindingId/canvasId/mountId）必须原样回用，不得臆造。需用 list 解析具名资产、read 读详情。Automation.run 是异步工具，运行后用 readRun 拿终态、readRunArtifact 拿产物。Widget.validate 通过才会 bump resourceRevision，挂载的预览随之刷新。

3.3 工具 → Surface 映射

publish_sitesiterevisionId=release.id固定 ready（构建失败则工具抛错，无 Surface）

Widget.showwidgetresourceRevisionvalidate 通过 ready，否则 preparing

4. Skill 体系

工具是「手」，skill 是「脑」。灵感会话里 Agent 加载哪些 skill，决定了它用什么方式把需求变成 App。灵感相关的 skill 分两层：Blueprint 域（组件型 App）和 webapp-building（构建产物型 App）。

4.1 blueprint —— 路由分发 skill

blueprint 本身不产出 App，它是 Blueprint 四资产的调度入口，告诉 Agent 该加载哪个子 skill。它定义了四资产的所有权边界：

资产拥有
Automation执行与结果（artifact）
Widget展示与交互
BindingAutomation ↔ Widget 的持久连接边
Canvas仅 placement（布局、z 序、placement 局部 view state）

它的 Routing 规则把请求导向子 skill：执行/调度/条件 → automation；HTML UI/数据渲染 → widget（再读 runtime-api.md）；数据投递/submit 路由 → binding；placement 布局 → canvas。它还给出了若干 Standard Chains（标准调用链），见第 5 节。

4.2 子 skill 分工

skill职责关键产出
widgetWidget 的创建/展示/校验/更新/删除；定义响应式尺寸契约与 runtime 状态机一个 index.html + slots.main/events.submit 契约
canvasCanvas 与 placement 的增删改查；12 列网格尺寸模型；共享 vs placement 局部状态placement（mountId + layout{x,y,w,h}）
widgetdesignWidget 设计规范权威；一个 job + 一个 archetype + Kimi tokens + 语义重组（Compact/Regular/Expanded）视觉与排版决策（不碰 API）
bindingAutomation artifact → Widget.slots.main 的投递与 events.submit 回路验证经验证的 Binding 边
automationAutomation 的执行/调度/触发（manual/one-shot/scheduled/interval/condition/widget-event）与 run 记录JSON artifact + run 状态
webapp-building本地脚手架 React+TS+Vite+Tailwind+shadcn/ui 项目，npm run build 产出 dist/可被 publish_site 发布的 webapp 源码

4.3 Widget Runtime 边界

Widget 的 index.html 运行在沙箱 iframe 里，只能用宿主注入的全局 window.DaimonWidget / window.DaimonCanvas（数据订阅、状态、主题、文件、placement 局部 view state）。iframe 内代码永远不直接调 agent 侧的 Canvas/Widget/Automation/Binding 工具——submit 事件经 Binding 路由到 Automation，由宿主运行后把数据回投到 data.main。这是组件型 App 的安全基石：不可信的渲染内容拿不到 agent 权限。

必读约束：创建任何 Widget 前必须先读 widgetdesign；写 iframe JS 前必须读 widget/references/runtime-api.md。widgetdesign 是唯一的 Widget 设计权威，不为同一工作加载第二个设计 skill。

5. 工作流程：三条执行路径

不同的需求落到不同的工具链。Blueprint skill 给出了若干 Standard Chains，落到灵感功能里有三条主干路径。

5.1 构建产物型（site）

适合「做一个完整网站/应用」——需要复杂 UI 组件、状态管理、构建流水线。

1. 加载 webapp-building skill
2. bash init-webapp.sh <project-dir> "<title>"   # 脚手架 React+TS+Tailwind+shadcn/ui
3. 编辑 src/，npm run build → dist/
4. publish_site(source_path=<project-dir>, name=..., description=...)
   # 后端：_resolve_source 校验源码在 Workspace 内
   #       _defaults 限定 build 命令首段 ∈ {npm,pnpm,yarn,bun}
   #       精确审核实际 argv/cwd → 解析受信 Node/包管理器入口 → Native Runtime
   #       _copy_release（拒符号链接、输出必在源码内）
   #       finish_release(ready) → 更新 active_release_id
5. 返回 Surface(mode=site, revisionId=release_id, status=ready)
   # 聊天卡片 + 图库列表（list_inspirations 合并 site+canvas）

5.2 声明式组件型（静态 widget / canvas）

适合「做一个卡片/看板/小工具」——单页响应式 UI，无需构建。

1. 加载 blueprint → widget skill（先读 widgetdesign 设计规范）
2. Widget.create(title, description)            # 拿到 widgetId + workspaceRoot
3. Widget.show(widgetId)                        # 立即挂占位预览（status 可能 preparing）
4. 写完整 index.html 到 workspaceRoot/index.html
5. Widget.validate(widgetId)                    # 校验通过则 bump resourceRevision，预览刷新
6. （可选）Canvas.placeWidget(canvasId, widgetId, layout{x,y,w,h})
7. Canvas.show(canvasId)                        # 返回 Surface(mode=canvas)
   # Canvas 单组件时铺满；多组件按 12 列网格 grid 排版

Standard Chain 里强调：Widget.show 要在创作开始时尽早调用以挂占位；Widget.validate 是唯一的 revision 推进器；Canvas.show 在整个看板需要常驻对话时调用。纯 Canvas 展示用 placeWidget 即可，Widget.show 只在还需要对话/侧栏展示时才用。

5.3 数据驱动型（automation-backed widget）

适合「做一个会自动刷新数据的仪表盘」——Widget 展示 Automation 产出的 JSON。

1. 定义匹配的 schema：Automation.result ↔ Widget.slots.main ↔ events.submit ↔ Automation.input
2. Automation.create(...) + Widget.create(...)   # 拿到 automationId / widgetId
3. 写 index.html + Widget.validate               # 准备渲染
4. Binding.create(automationId, widgetId)        # 建边，初始 pending_run
5. Binding.validate / Automation.run             # 审核初始目标及跨域重定向，再投递 artifact
6. Canvas.placeWidget + Canvas.show              # Surface(mode=canvas)
7. （可选）启用 interval / schedule 触发器周期刷新

验证要点：pending_run 只表示 Binding 已配置，不代表数据已投递。要确认 run 达到 succeeded 且 Widget.read 的 latestData.main 符合预期，才算数据真的到位。

6. 生命周期与状态

6.1 灵感资源生命周期

新建（inspiration_creation=true builtin Session）
  → 对话生成（工具产出 Surface）
  → 对话成果卡（点击后打开 Inspector 预览）
  → 指出要修改的位置（按需进入批注）
  → 部署到图库（list_inspirations 可见）
  → 使用 / 分享(ZIP) / 固定(sticky) / 删除(级联)
  → 修改：回原 sessionId 继续对话 → 重新发布/validate → 新 revision

6.2 release 生命周期（site）

create_release 写入 status=building → 构建成功 finish_release(ready) 并更新 active_release_id，失败 finish_release(failed) 记 error；若是新建站点失败则回滚删除 site 记录，不留半成品。

6.3 Widget revision 生命周期（canvas）

Widget.create 生成初始 resourceRevision → 写 index.html → Widget.validate 通过则 bump_widget_revision。前端 blueprint-surface 用 surfaceSignature()（widget id+revision+validation.status / canvas placements+widgets 指纹）判断是否重渲染，schedulePoll 每秒轮询，签名不变就跳过——避免轮询抖动。

6.4 批注生命周期与迁移

批注状态 open → resolved/rejected。统一存 inspiration_annotations 表，targetKind 区分 site_dom（网站 DOM 元素）/ canvas（看板级）/ widget（组件级）/ widget_dom（组件内 DOM），context JSON 存 canvasId/widgetId/mountId。Store 初始化时用 INSERT OR IGNORE 把旧 site_annotations 无损迁移到统一表（inspiration_kind='site'）；前端旧草稿 localStorage key ace.siteAnnotationDrafts.v1 转存到 ace.inspirationAnnotationDrafts.v1，升级后不丢未发送批注。

6.5 批注 → Composer 回写

批注按原 Session 聚合成 Composer 草稿 chip（chat-site-annotation-preview / chat-blueprint-annotation-preview 容器）。发送内容含源码路径、内部资源 ID、route、selector、当前文本、revision 与修改要求。site 修改后等用户明确重新部署；widget 修改后调 Widget.validate 直接刷新 Surface——这一差异由 Agent 工作流处理，不要求用户选类型。

6.6 用户体验收敛（2026-08-10）

灵感对用户只保留「成果」这一概念，site/canvas/widget、HTML、revision 等继续作为内部协议字段，不出现在成果卡和预览操作中。聊天内网站、看板和静态 HTML 统一渲染为一张可点击的灵感成果卡：整卡是单一入口，右侧使用箭头表达“查看”，不再同时展示“在 Crew 打开”或打开方式菜单。生成结果到达时不自动抢占 Inspector，用户点击卡片后才打开对应的网站或看板预览；历史回放仍可从同一 Surface 恢复。

预览面板默认只展示成果内容；网站和看板的批注入口统一为「指出要修改的位置」，进入后通过点击元素产生 Composer 批注草稿。刷新、revision、整体批注/元素批注等运行时概念不作为普通用户操作暴露。低频的分享、固定和删除继续保留在图库详情的次级操作中，避免干扰查看与修改主路径。

7. 设计取舍

双运行时统一为「灵感」，不向用户暴露 site/canvas

朴素方案是只用一套承载——但 React 构建产物是单体 index.html，硬塞进 widget 网格不合理；反之把一个静态小卡片走完整构建流水线又过重。保留双运行时、用 ID 前缀在 SiteManager 内分发，让「完整 webapp」和「组合式组件看板」各得其所，而上层图库/详情/操作只认一个「灵感」。代价是 get/export/delete_inspiration 三个方法都要写前缀分支。

Surface 作为单一事实来源

替代方案是每种类型独立协议。但历史回放、批注、图库都需要统一锚点，独立协议意味着每个消费方都要 if/else 分发。把 publish_site/Canvas.show/Widget.show 全部统一成 kind=inspiration + mode，工具结果持久化后任何消费方都能从最小元数据重建卡片，刷新不丢。

ace-site:// 私有协议 + ID 前缀，而非直连后端端口

直接用 http://localhost:port 会暴露端口、需要鉴权头、还有路径穿越风险。私有 scheme 让主进程成为唯一转发点：ID 正则校验 + 认证注入 + 后端二次根目录边界校验，三道独立校验。代价是 Electron 侧要维护 protocol.handle 与 scheme 特权声明。

批注统一表 + targetKind，而非每种类型一张表

site/canvas/widget/widget_dom 四种 target 若各建一表，跨类型聚合到 Composer 草稿和按 Session 聚合会很难。统一 inspiration_annotations 表 + context JSON 扩展字段，配合一次性迁移，让批注链路只有一套读写路径。

sticky 便利贴 frame:false + preload 注入 chrome

用系统标题栏会占空间且三端不统一；自绘标题栏需要 frame:false。inspiration-sticky-preload 注入拖拽条 + 关闭键，保证三端一致的无标题栏体验。透明圆角在 macOS 稳定（transparent:true + floating 层级 + 全工作区可见），Win/Linux 透明不稳定改用 resolveWindowBackgroundColor() 实色——这是显式的平台兼容性取舍，而非 bug。

删除采用引用计数式级联，保留共享资产

删 Canvas 时朴素方案是级联全删 constituent widget/automation。但一个 Widget 可能被多个 Canvas 引用，全删会误伤。改为：删 placement → 删不再被任何 Canvas 引用的 Widget → 删没有其他 Binding 的 Automation 并停调度。共享资产保留，源码与原 Session 也保留。

8. 安全边界

边界约束
构建命令_defaults 限定首段 ∈ {npm,pnpm,yarn,bun}；Agent 发布前以实际 Node/包管理器 argv 与源码 cwd 进入统一 exec 审核，请求批准模式会等待用户决定；npm/pnpm/yarn 解析为绝对 Node 与脚本入口，Native Runtime 仅增加已解析运行时依赖根的只读权限，工作区仍是唯一构建写入根；Desktop 手动重发本身就是认证用户动作，不重复弹审批，但仍执行持久 deny 规则检查、写入 desktop_user_gesture 审计并使用同一 Native Runtime；_copy_release 拒符号链接、要求输出在源码内
Automation 联网http_json 只接受无内嵌凭据的公开 HTTP/HTTPS GET/POST；连接固定到已校验的公共 DNS 地址，拒绝 localhost、私网、链路本地、保留地址、敏感查询参数与鉴权请求头；Agent 手动运行按精确 host/port/protocol 审核，每个跨域重定向都重新授权；响应上限 5 MiB。已启用的定时 Automation 以用户保存的公开目标配置作为持续执行授权，但仍经过相同 SSRF/DNS 固定边界
预览协议ace-site:// ID 正则 /^(?:site|canvas|widget)_[0-9a-f]{12}$/i；release_file 强制 requested 路径在 release root 内；widget 资源路径在 widget root 内；主进程为所有预览响应注入 CSP，connect-src 'none'、form-action 'none'，生成页面不能绕过 Ace 审核自行联网或提交外部表单
sticky 窗口仅接受规范 site_*/canvas_* ID，不传 URL；单例 Map；contextIsolation+sandbox+webSecurity，禁 Node/webview/新窗口/外导航；will-navigate 钳制同 ID ace-site:，windowOpenHandler deny
ZIP 保存通道 dialog:saveLocalExport；schema 要求绝对路径 + 无分隔符文件名 + .zip；主进程再校验相对 sites/{site|canvas}_*/exports/*.zip 三段、stat(isFile+nlink==1)+realpath canonical，最后 showSaveDialog + copyFile
隔离所有 API 查询/写入以 owner_account_id 隔离；Widget iframe 只能用 window.DaimonWidget/DaimonCanvas，不直调 agent 工具
文件传递资产间传文件只走 FileResourceRef；浏览器 File、原始字节、大 base64、本地路径、file: URL 不得进持久化 JSON 与通知

11. 小结

把灵感功能当成一个系统看，它有三层稳定契约：底层是双运行时（site 构建产物 / canvas 声明式组件），靠 ID 前缀分发；中层是InspirationSurface 协议，把工具产出统一成图库、预览、历史回放的单一事实来源；上层是四操作生命周期（修改/分享/固定/删除），围绕 Surface 背后资源做受控管理。Agent 侧通过 publish_site + Blueprint 四工具产出 Surface，由 webapp-building 与 Blueprint 域 skill 决定走哪条执行路径。安全上靠 ace-site:// 私有协议、sticky 沙箱窗口、ZIP canonical 校验、owner 隔离四道独立边界纵深防御。理解了「工具产出 Surface、Surface 驱动一切」这条主线，就理解了灵感功能的全部设计意图。
