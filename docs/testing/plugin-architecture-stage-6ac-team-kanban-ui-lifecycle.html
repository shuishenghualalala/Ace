阶段 6AC · Team/Kanban UI 能力驱动装卸

2026-09-14。ADR-0040 交付了按 Feature ID 索引的运行时能力状态源（feature_capabilities），但双端 Team/Kanban 处理器仍随 App 无条件安装。本片让 Desktop/Web 消费统一状态源，按 product.team / product.dynamic-kanban 独立推导可用性做动态装卸——reducer、board hooks 与页面随能力开/关独立启停；设计与决策见 ADR-0041。

处置

  • Desktop 能力接线：新建 desktop/src/ui/features/board-capability.ts 单一模块持有两个 Feature ID 的可用性推导（config 未加载 / 旧后端无 feature_capabilities 字段按 legacy-safe 视为可用，字段存在时项缺席或 available ≠ true 即不可用）、team-kanban:config-change 窗口事件与 installTeamKanbanBoards() 安装单元——能力开则 init 对应 board、关则 dispose，两板独立、幂等；app 引导不再无条件 init，中心文件不经由新导入认识具体 board 模块。
  • Desktop 会话内一致性：defaultInspectorTabForSession 在 team/kanban 能力下线时对对应模式会话回退 context；loadConfig() 成功/失败分支均广播能力事件，能力变化在引导、网关重连与模型 CRUD 后拉取式反映。
  • Web 宿主门控：web/src/lib/featureFlags.ts 新增 teamFeatureAvailable/kanbanFeatureAvailable（同一 legacy-safe 规则，与 Desktop 推导逐字同构）；App 宿主按能力分别条件安装 team/kanban feature-event handler，TaskBoard 挂载增加能力门，能力关闭时收起已开看板。

主 agent 审查修正：Web featureFlags.ts 两处 JSDoc 中「条目缺席按可用处理」的歧义表述改为精确规则（映射存在而条目缺席是不可用；可用兜底仅指 config 未加载 / 字段缺席）。另记录一项观察：既有 App.wiki-lifecycle.test.tsx 首宿主断言疑似依赖 StrictMode 丢弃渲染的空 registry「侥幸通过」（潜在假阳性），本片未动该文件，留待独立小切片核实。
