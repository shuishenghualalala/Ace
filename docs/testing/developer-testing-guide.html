Ace 自动化测试指南

这篇文档面向提交 Ace 代码的开发者与 Agent。目标不是“把测试跑绿”，而是让测试能够在功能真正交付的路径上失败。命令以仓库当前脚本和 CI 为准；新增测试前先选层级，再决定改哪里。

Python / pytest Gateway Electron / Vitest React / Vitest 真实模型 E2E 三平台 CI

1. 四条核心原则

  1. 测真实入口路径。后端至少从 CrewApp.handle(Envelope)、build_app 或真实 Gateway/WebSocket 进入；桌面从 Electron main/preload/renderer 的真实边界进入；Web 从真实组件树进入。不要用手工拼出的对象替代装配根，否则测试看不到 Loader、路由、权限或生命周期差异。
  2. 只 mock 昂贵或不确定的边界。模型、时钟、外部网络可以替换；SQLite、工具注册表、执行器、提示词拼装、会话持久化和安全判定保持真实。只证明桥接层搬了字节的测试，不足以证明产品可用。
  3. 断言外部世界，不断言自我报告。重新读取文件、查询 SQLite、检查 HTTP/WS 响应或桌面 DOM；不要只搜 Agent 自己回复里的关键词。未修改的文件应逐字节一致。
  4. 每个 bug fix 固定一条回归。在能复现它的最快层级加断言；只做一次临时验证、不留下测试，不算完成。
  5. 不要锁源码文本。只检查类名、属性顺序、JSX 字符串或“函数被调用过”的测试，不能证明渲染、布局或交互；这类断言会阻碍重构。触发真实行为，断言外部可观察结果。

2. 层级与命令

先选能捕获该回归的最窄层级；上层测试不重复下层已经证明的协议细节。完整后端 E2E 的字段与报告结构见 后端 E2E 批量测试指南。

2.1 静态检查

pytest 默认由 pyproject.toml 的 addopts = -m 'not e2e' 跳过真实模型用例；单跑 E2E 用 -m e2e，确实需要全量时显式 -m ""。

uv run ruff check .
uv run lint-imports
cd desktop && npm run typecheck && npm run lint
cd web && npm run typecheck

静态检查通过不等于行为正确；它只负责挡住类型、导入方向和风格回归。行为改动仍要落到对应层级。

目录用途
tests/test_*.py后端模块、状态机、工具、模型配置、Cron、MCP 等单元/集成测试
tests/gateway/Gateway 路由、认证、WebSocket、Owner 隔离、健康检查
tests/security/原生安全运行时与命令准入；按平台构建后执行
tests/e2e/真实产品入口的批量场景：scenarios.yaml、_run_case.py
tests/fixtures/可复用的 MCP、工作区、HTTP/SSE 等夹具
desktop/tests/unit/Electron main/preload/renderer 单元与集成测试
desktop/tests/visual/Playwright 视觉/交互回归
web/src/**/*.test.tsxReact 组件与前端控制器测试，与被测代码就近放置

新增文件时优先沿用既有文件名与夹具；不要把共享 harness 放进另一个 *.test.ts/test_*.py，导入测试文件会重复注册用例或产生额外副作用。

4. 真实模型 E2E 的写法

后端 E2E 场景写在 tests/e2e/scenarios.yaml，每个 case 在独立临时目录和子进程中运行，报告包含 result.json、transcript.jsonl、llm.jsonl、crew.log 和工作区前后快照。新增 case 的最小结构：

complex_tasks:
  my_feature:
    title: 新功能的用户可见行为
    mode: agent
    workspace:
      files:
        "toy/input.txt": "hello\n"
    prompt: |
      读取 toy/input.txt，写入 toy/output.txt。
    expected_tools: [file_read, file_write]
    expected_files:
      - path: "toy/output.txt"
        contains: ["hello"]
    expected_final_keywords: ["output.txt"]
    timeout_seconds: 240
  • 先只跑新 case：python scripts/run_e2e_batch.py --case my_feature；通过后再跑同类别。
  • 断言工具名、文件产物和有限关键词；不要写死模型全文。模型行为波动时先看 llm.jsonl，判断是提示词、产品还是断言问题，不要直接放宽断言。
  • 凭据只从隔离环境的 config/.env/CREW_MODEL_API_KEY 解析；不要把 key 写进日志、报告或测试文件，也不要混用不同仓库的 CREW_* 环境变量。
  • 缺少外部 CLI（Codex/Claude/Kimi 等）时用例应标记 skipped；--fail-on-skip 只用于明确要求“跳过也算失败”的验收。

4.1 无密钥回放（组装态）

tests/e2e/replay_server.py 用录制的 JSONL 响应替代模型 HTTP 边界；应用仍走真实 build_app、Provider、工具、SQLite 和会话入口，不需要 API Key。当前样例覆盖并行 file_read 的部分失败、file_read → file_write 的写入流程，以及 tool_search → cron_create 的持久化任务；响应耗尽时服务器返回失败，不会静默重复最后一条。fixture 从真实 trace 提取后必须人工审查是否含本地路径、用户数据或密钥。

# 从一次真实 E2E 的 llm.jsonl 提取回放响应
python scripts/record_replay_fixture.py \
  --trace build/e2e/<run>/<category>/<case>/llm.jsonl \
  --output tests/e2e/fixtures/replay/my_case.jsonl

# 只提取一个会话，或明确覆盖旧 fixture
python scripts/record_replay_fixture.py --trace ... --output ... --session-id e2e_my_case
python scripts/record_replay_fixture.py --trace ... --output ... --force

脚本不会自动清洗业务路径或密钥，输出需要人工审查后再提交；响应序列必须覆盖该 case 的所有模型请求，不足时回放会以 500 失败。

5. 稳定性与防 flake

  • 不要用固定 sleep 等待。用 asyncio.Event、wait_for、持久化完成信号、DOM/WS 事件或真实进程退出信号；只有时间本身是被测对象时才用假时钟。
  • 把 flake 当 bug。失败若与调度有关，先定位竞态或资源泄漏；不要用重试把它变成通过。需要时对最可疑套件做重复/打乱顺序运行。
  • 自己创建的资源自己释放。端口、临时目录、子进程、MCP 连接、Electron 窗口和 Gateway 都要在 teardown 中关闭，即使断言失败或超时。
  • 跨平台语义不要按本机字面量写。路径用 Path/pathlib，URL 用解析 API，换行/编码显式指定；平台差异用相邻断言覆盖，而不是静默跳过整个文件。
  • 并发/取消测试要断言副作用边界。取消后是否还有写入、是否重复执行、是否留下运行中状态，都要从外部状态验证。
  • 覆盖率只是删除检测器。未覆盖的行往往说明死代码或漏测；不要为了凑数字补空洞用例。

6. 提交前检查

按改动面选择命令，不要默认跑全量；在 PR 描述中写清实际运行的命令和结果。

6.1 PR 检查清单

  • [ ] 我选了能捕获这次回归的最窄层级，并在改动前确认它失败、改动后确认它通过。
  • [ ] 用户可见或模型可见的改动，有从真实入口执行的测试；不是只测了手工拼装的对象。
  • [ ] bug fix 在 owning suite 中留下了回归断言。
  • [ ] 断言检查了文件、SQLite、HTTP/WS 或 DOM 的真实状态，而不是只搜 Agent 回复。
  • [ ] 没有用固定 sleep、单次 DOM 采样或重试来掩盖竞态。
  • [ ] 临时资源在成功、失败和超时路径都释放。
  • [ ] 受影响模块的 HTML 文档已更新；行为变化写清边界与已知缺口。
  • [ ] PR 中报告了实际执行的命令与结果；未执行或环境受限的地方如实说明。

7. 当前缺口与后续方向

下面这些是尚未落地的能力，不应在 PR 中声称已有；需要时先单独设计，不要用临时脚本冒充：

  • 回放场景覆盖。已有三个无密钥组装态样例；更多模型可见流程、录制工具、fixture 审查流程和 CI 矩阵仍需补齐，不能因为有三个样例就宣称所有模型行为都已覆盖。
  • 覆盖率门禁。当前只有 test:coverage 命令，没有按文件强制阈值；覆盖率只应作为“死代码/漏测”的删除检测器，不能替代行为断言。
  • 受影响测试选择。前端可用 Vitest 的 related/changed 机制；后端需要稳定的测试映射或依赖分析后再接入 pre-push，避免“猜一个子集”造成假绿。
  • 桌面视觉与打包 E2E 的 CI 化。目前视觉测试和部分真实安装包场景仍以本地/专项为主，nightly 只构建产物。
快速判断：这次改动如果坏了，哪一个现有测试会变红？如果答不上来，先补测试，不要先改实现。若只能靠人工点一遍才能发现，考虑把它变成真实入口的 E2E 或视觉用例。
