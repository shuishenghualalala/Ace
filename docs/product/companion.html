1. 背景与现状问题

同伴功能的技术链路已经走通：蓝牙发现、单聊、群聊、群文件、群内 Agent 触发、Agent 回复桥接到本机 Gateway。当前的问题不在技术，在产品：

#问题现状优先级
1 造了第二套聊天界面 nearby-chat.ts 自实现了消息流、气泡、输入框、@ 弹层，与主对话页组件重复且质量参差不齐，维护两份。 P0
2 「连接」这个技术概念被直接暴露给了用户 同伴卡片上有 4 个按钮：连接 / 发消息 / 邀请进群 / 断开。用户的目标只有一个——「跟旁边这个人说话」，却要先理解并完成一次「连接」。 P0
3 Agent 的触达规则不清，且私聊可直达 Agent 存在安全风险 现状直聊可 @ 对方 Agent（agent.request），陌生人无需任何上下文就能支使你的 Agent；人和 Agent、Agent 和 Agent 的边界没有产品规则。 P0
4 UI 风格偏离设计系统 nearby.css 是少数带「个性」的页面：蓝色径向渐变、毛玻璃胶囊、#34c759 绿点，直接违反 DS 3.1 与状态色条款。 P1
5 连接状态机直接透传给用户 五种技术状态原样展示，用户只需要知道「能不能说话」。 P1
6 auto 模式存在 Agent 互相触发死循环的风险 现状 auto 模式下「每条非本机消息都触发本机 Agent」，A 的 Agent 发言会触发 B 的 Agent，反之亦然。 P1

2. 产品定位与设计原则

一句话定位：同伴 = 蓝牙可达范围内的人机协同空间。两台开着 Ace 的电脑靠近，两"个人"（人 + 各自的 Agent）就能拉群一起干活。不依赖局域网、不经过云端。

产品目标：让 人↔人、人↔Agent、Agent↔Agent 三种对话在统一的对话界面里自然发生，且用户不需要学习任何新概念。

六条设计原则

原则 1 · 一个同伴 = 一个人 + 一个 Agent。发现的每一台 Ace 设备呈现为一个「同伴」，同伴自带一个 Agent 副驾。Agent 不是独立联系人，没有单独的 Agent 列表、没有单独加 Agent 的操作。
原则 2 · 发现即认识，没有「连接」。连接是技术动作，不是用户意图。用户看到同伴就能发消息，连接在发消息的瞬间自动完成。界面上不出现「连接」按钮。
原则 3 · 一个输入框，@ 决定对象。群里默认说给所有人听；@谁，就触发谁——@人 或 @Agent 都一样。与主流 IM 心智一致。
原则 4 · Agent 随人走。建群、邀请都以「同伴」为单位：同伴进群，他的 Agent 自动在群里；同伴退群，Agent 一起离开。由此自动保证「任何 Agent 在场的群里，它的主人一定在场」。
原则 5 · 私聊无 Agent。直聊是人和人的私密空间，Agent 不进入、不可被 @。人与 Agent、Agent 与 Agent 的交互只发生在群里——群有主人、有成员可见性，是 Agent 行为的天然监督场。
原则 6 · 每个视图最多一个主按钮。次要操作一律收进「···」菜单或弹层。

3. 产品架构：管理中心 + 对话界面

产品由两个界面组成，职责严格分开：

界面职责类比
同伴页（侧边栏一级入口） 协同关系的管理中心：发现附近的同伴、管理我的名片（身份 + Agent 名片）、管理群（建群 / 邀请 / 成员 / 触发模式 / 解散）。这里不说话。 通讯录 + 群管理
主对话页 唯一的对话界面。同伴的直聊和群聊作为主对话侧栏里的「同伴」渠道分组出现，点击即在主对话区打开，完整复用主对话的消息流与 Composer 组件。 所有聊天只在这里发生

跳转关系：同伴页同伴卡片点「发消息」→ 跳到主对话的对应直聊会话；同伴页群卡片点「进入群聊」→ 跳到主对话的对应群会话；主对话同伴会话头部点「群信息」→ 跳回同伴页的群详情。

技术路线（已定）

主对话的消息流与 Composer 渲染层只消费 state.messages 与 chunk 流，对会话类型无感（外援 ACP 会话即是证明：UI 零分叉复用）。因此 nearby 不在前端造第二种数据源，而是以「新渠道平台」身份接入 gateway 既有的渠道会话管道：

  • 入站：desktop 主进程把 nearby IPC 事件（peer_message_received / room.message / Agent 回复等）转发给本机 gateway，写入派生会话 agent:main:nearby:{dm|room}:<hash> 的历史并广播 WS chunk——复用 prepare_inbound_channel_envelope 注入管道。
  • 出站：用户在这些会话里发消息，gateway 经 deliver_channel_session_reply 同型钩子转给 nearby runtime 发出（BLE）。
  • 侧栏：渠道分组（channel-sessions.ts）新增 nearby 平台，直聊/群聊按平台分组渲染。
  • 每台机器的 gateway 只写本机副本：房间消息由 Rust nearby 服务同步到全体成员，各端各自注入本机会话，会话 id 由 room_id/peer_id 哈希派生，各端一致。

对比方案（已否决）：在前端给 nearby:* 会话写一个与 BackendChatSocket 同形的 driver、在读写边缘按前缀分叉——侵入 openSession/sendMessage/stop/busy 同步等多处，回归风险大。

4. 核心概念模型

概念定义用户感知
同伴（Peer）一台运行 Ace 并开启「允许被发现」的电脑，= 主人 + 本机 Agent。对外字段：名字、Agent 名、能力标识。同伴页「附近的同伴」里的一张卡片。
会话直聊（dm）或群聊（room），以渠道会话形式存在于主对话页。群聊成员以同伴为单位。主对话侧栏「同伴」分组里的一项，带未读角标。
身份每条消息都有发送者身份：人 或 Agent。Agent 消息带中性身份徽章（identity 不靠颜色区分，DS 身份条款）。气泡样式一眼区分「人说的」和「Agent 回的」。
可见性「允许被发现」开关，控制本机是否被别的 Ace 扫到。同伴页我的名片卡上的一个开关。
群主建群的人，拥有邀请 / 改名 / 切模式 / 解散权限。群永远由人创建，Agent 不能建群。群详情里的管理操作区。

5. 核心逻辑：消息发给谁

用户在输入框里写一句话，系统按下面这张表决定它去哪：

场景用户的输入消息去向谁会响应
直聊任何消息对方的人（peer.message）只有对方的人。直聊无 @、无 Agent、无文件，就是纯对话。
群聊
（按群的触发模式）		mention（默认）广播给全体成员（room.message）所有人都能看；被 @ 的 Agent 响应（@ 可来自人或 Agent，见 §6 防循环）。
auto同上每条人发的消息触发所有成员的 Agent 依次响应；Agent 的消息不触发任何 Agent。
quiet同上只有人在群里说话，Agent 全部沉默（输入框禁用 @Agent）。

6. 安全模型

四条铁律，全部可由结构与裁决逻辑保证，不依赖用户自觉：

铁律 1 · Agent 不进私聊。直聊没有 @ 能力，agent.request 通道不在 UI 暴露。想支使任何人的 Agent（包括自己的），必须在群里。
铁律 2 · Agent 只在主人在场的群里响应。由原则 4（Agent 随人走）结构性保证：Agent 不可能出现在没有它主人的群里。主人能看到自己的 Agent 被问了什么、答了什么。
铁律 3 · 群永远有主人，Agent 永不管理群。群只能由人创建；邀请、改名、切模式、解散只有群主（人）能操作。Agent 不能建群、不能拉人、不能改任何设置。
铁律 4 · Agent 对话必须有刹车。mention 模式下 Agent 可以 @ 另一个 Agent 形成接力，但同一条触发链上 Agent 连续互聊最多 3 跳，到达上限后系统条提示「Agent 接力已达上限，请由人继续」；auto 模式下 Agent 只响应人的消息（Agent 消息永不触发 Agent），从规则上杜绝全员互触发的死循环。

能力边界（沿用现状，不变）

  • 同伴 Agent 默认纯文本问答：工具白名单为空、Skills 全禁、executor 固定 builtin、nearby_text_only。别人支使你的 Agent，它只能说话，不能动你的电脑。
  • 主人在「编辑名片」里可显式放行工具白名单（只收窄不放宽）、或关闭自动回复彻底拒绝。
  • BLE 链路未加密（仅 peer_token 握手校验），编辑名片弹层持续提示「不要通过同伴传输敏感信息」。

8. UI 设计规范（对齐设计系统）

三条硬约束（DS 原文）：

  • DS 3.1：「Do not use gradients, neon glow, glassmorphism, decorative color bars, or marketing-page composition in product views.」
  • 「Status colors are semantic and cannot be repurposed as page decoration.」
  • 「Theme selectors override semantic tokens, not individual page selectors.」同伴相关 CSS 不允许出现任何 [data-theme="dark"] 页面级覆写；原始色值只能出现在 tokens.css primitive 层（审计为阻断性门禁）。

9. 关键场景走查

S1 · 跟旁边的同事说句话（人→人）

  1. 打开「同伴」页 → 自动扫描 → 出现「小明」卡片。
  2. 点「发消息」→「连接中…」→ 自动跳到主对话的「小明」直聊会话。
  3. 输入「文档发我一份」→ Enter → 小明电脑的主对话侧栏「同伴」分组出现未读。小明的 Agent 全程无感知——直聊里没有 Agent。

S2 · 支使同事的 Agent 干活（人→Agent，必须在群里）

  1. 在同伴页点「+ 建群」（或用小明的卡片「··· → 邀请进群」进已有群），群里有小明——他的 Agent 自动在场。
  2. 在主对话打开该群，输入「@小明的Agent 把昨天的会议纪要总结成 5 点」。
  3. 小明的 Agent 在隔离会话生成，回复出现在群里并 @回我；小明（主人）在群里全程可见自己 Agent 被问了什么、答了什么。
  4. 若小明关闭了自动回复：我立即收到错误提示「对方已关闭 Agent 自动回复」，不静默失败。

S3 · 建群拉人拉 Agent 一起协同（核心场景）

  1. 建群「发布会筹备」，勾选小明、阿华，模式默认 mention。
  2. 两人电脑的主对话出现群会话；同伴页群详情显示：小明 └ 小明的 Agent、阿华 └ 阿华的 Agent。
  3. 我发：「@小明的Agent 出一版邀请函文案；@阿华的Agent 核对预算表」→ 两个 Agent 各自在本机生成，回复依次出现在群里并 @回我。
  4. 小明的 Agent 的回复里 @阿华的Agent 请求预算数据 → 阿华的 Agent 接力回答（第 2 跳）→ 若接力继续到第 3 跳后系统条提示「Agent 接力已达上限，请由人继续」，由人接管。

S4 · 群内发文件

  1. 群聊 Composer 点 📎 → 选文件（≤4MiB）→ 全员收到文件卡片 → 点「保存」落本地。

S5 · 纯人讨论

  1. 群主把模式切到 quiet → 全员收到系统条；Composer 的 @ 弹层中 Agent 组禁用——群里只剩人说话。

10. 状态与异常

10.1 连接状态的用户化映射

技术状态（内部）用户看到可执行操作
discovered「在附近」（灰点）发消息（点击后自动建链）
connecting「连接中…」（脉冲点 + loading）等待
connected「在线」（绿点 --mw-status-success）全部
disconnected / unavailable「已离线」（空心点）发消息（点击尝试重建链）；输入框置灰

10.2 异常态

异常界面表现
蓝牙关闭 / 无权限同伴页顶部 .notice 横幅，按 macOS / Windows / Linux 给出系统设置指引，带「重试」。
对端未配置模型群里 @Agent 后收到 503 → 错误提示「对方的 Agent 尚未配置模型」，不死等。
文件 > 4MiB选择时即拦截 toast，不发出去。
消息 > 8000 字输入框计数超限红字，禁止发送。
Agent 接力超 3 跳系统条「Agent 接力已达上限，请由人继续」，后续 Agent 间 @ 不再触发，人 @ 不受影响。
Linux 平台只能主动连别人、不能被发现连入：名片开关旁常驻说明，不报错。
断线重连会话历史保留，回到蓝牙范围自动重连，系统条提示「已重新连接」。

11. 本期边界（明确不做）

  • 直聊无任何 Agent 能力：无 @、无 agent.request、无文件——这是安全模型的一部分，不是功能缺失。
  • 不加好友 / 不审批：蓝牙范围内 + 双方「允许被发现」即可互发，物理 proximity 即信任边界。
  • Agent 不做独立联系人：无 Agent 目录、无单独与 Agent 的会话、Agent 不能建群。
  • BLE 链路加密 / 配对鉴权（仅 peer_token 校验，风险如实标注）。
  • 已读回执、reaction、消息引用 UI、消息搜索。
  • 手机端、跨网络协同。
