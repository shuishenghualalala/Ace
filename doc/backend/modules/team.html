Ccrew/team

多智能体协同：Leader + Teammate + 异构成员 + Team Bus · Crew 的扩展重点

1. 职责

  • 组建团队：按 session 创建 Team，包含一个 Leader 和多个 Teammate，每个正式成员拥有 member_session_id = team_session_id::member_id。
  • 统一成员配置：成员通过 TeamMemberSpec 描述，可配置 executor=builtin|external|client；旧 acp/cli 只作为配置兼容别名，外部成员使用 external_agent_id 绑定现有 runtime/agent。
  • 复用 Agent 内核：Leader/Teammate 都是 SingleAgent，执行层复用现有 AgentExecutor；不新增 AgentAdapter 抽象。
  • 强制工作流：Team 模式默认启用 required_workflow，由 Runtime 创建 TeamPlan、按依赖派活、更新节点状态；不再只依赖 Leader 大模型自行理解并调用工具。
  • 委派子任务：Team Runtime 或内部 Leader 调用受控派活能力，按成员执行队友任务；同批多个 delegate 目标成员互不相同时可并行。
  • Team Bus 通信：成员间消息通过 TeamBus / mailbox 流转，提供 team_read_messages、team_add_artifact 工具；发送侧统一通过 team_mention。
  • 并发与观测：team.max_concurrent_children 默认 3；TeamManager 维护 active child registry，Gateway 可展示活跃 teammate。
  • 中断传播：显式 stop/interrupt 会传播到 leader 和当前活跃 teammate；普通 busy interrupt 在有活跃子 agent 时由 Gateway 降级为 queue。
  • 记录任务流转：委派过程写入 crew/tasks，并向 Team Bus 写入 assign / task_notification 消息，支撑任务看板。

3. 数据模型与接口

实现 TeamManager.interact(envelope) / destroy(session_id)；delegate_to_teammate 通过函数式 handler 消费 TaskManager、Agent 与 TeamBus。Team Bus 使用 member_id 寻址，外部 Runtime 的原生 session/thread id 仅保留在 ExternalExecutor/Adapter 内。
概念说明
team_session_id团队级会话；承载用户目标、任务看板、Team Bus 事件、产物索引。
member_session_id正式成员在团队会话下的独立上下文，格式为 {team_session_id}::{member_id}。新建 Team Session 时，每个成员都会拥有新的 member session。
external_session_id外部 Runtime 的原生 session/thread id，不进入 Team Bus 消息，只由 ExternalExecutor / adapter 维护。

3.1 Owner 与 Session 契约

  • 沿用 Crew owner 分区：Team 不新增身份体系，所有父 session、::turn:: sidechain、Leader/成员子 session、TeamPlan、runtime task 与 ACP binding 都继承 Envelope.user_id / owner_account_id。
  • 内存态隔离：TeamManager 的 Team、TeamPlan、active child registry 按 (owner_account_id, session_id) 建 key；stop、steer、interrupt 只命中同 owner 的父会话与 ::turn:: 子会话。
  • ACP 绑定隔离：external_acp_session_binding 新增 owner_account_id，主键包含 owner；单 Agent 和 Team 外部成员都按 owner 读写 resume 绑定，旧绑定可根据唯一 session owner 自动回填。
  • 标识边界：crew::builtin 永远只作为内置 Crew 的 agent_id，不作为 session_id；:: 保留给 ::turn::、::leader、::crew、::{member} 这类内部会话层级。

5. 和 Hermes 的对照

Hermes 提供通用 Agent 平台能力。Crew 在 Hermes 骨架基础上增加更显式的多智能体 Team 模块，用 Leader-worker 的方式演示任务拆解、委派、执行和汇总。

6. 前端派活与 Crew 内部 Agent 入队

  • 团队派活：前端团队卡片的「派活」会创建新 session，写入 session_agent_config.executor=team 与 team.external_team_id，随后切换到 mode=team。
  • Team id 透传：WebSocket 消息携带 external_team_id；后端也会从 session agent config 兜底读取，避免刷新后丢失绑定。
  • Crew 内置智能体：创建团队时 UI 在 Leader 下拉和成员区都提供 Crew 内置智能体 卡片，统一存储标识为 crew::builtin；它不是 external runtime，不写入 external_agent，但可以作为逻辑 Leader 或普通 builtin teammate 加入 Team。
  • 外部成员：团队成员仍来自 external_agent，执行时按 runtime protocol 复用 ACP/CLI/client executor。

7. delegate 边界与外部协作入口

  • 内部 delegate：delegate_to_teammate 只允许 Crew Team 内部 Leader 使用。运行期通过 current_agent_id=leader 校验；非 Leader 或非 Team 上下文调用会返回明确错误。
  • 外部 agent：外部 Runtime 不直接获得 delegate_to_teammate，避免绕过 Crew 治理、权限、任务看板和成员校验。
  • 统一受控入口：ACP/Claude 使用 Crew Interaction MCP，Codex app-server 使用原生 dynamic tools；二者都进入可信 Binding 下的 team_mention 与 TeamPlan 工具。
  • TeamPlan 工具：外部 Leader 可创建、读取和更新计划；Member 只能读计划并更新自己的节点。Runtime 主循环根据合法 DAG 派发，不允许成员自报身份或越权改派。
  • 审计路径：合法 mention、计划更新和实际派发继续写入 TaskManager、TeamBus 与 Dynamic Kanban，前端不区分底层 MCP 或 dynamic tool 传输。

8. 任务看板 UX

  • 用户视图优先：前端 TaskBoard 不再默认展示底层 agent_turn/shell/subagent 日志列表，而是按模式展示更贴近用户理解的视图。
  • 单 Agent 大纲：单 Agent 模式显示"执行看板 / Execution Flow"，内容为极简聊天大纲：顶部只显示整个 session 的聊天总结，下面只展示用户消息概括版；用户可点击每条消息展开原文。不再显示"任务正在推进""下一节点""主责 Leader"等团队/流程口径。
  • 单 Agent 标识：单 Agent 大纲 logo 复用 session badge 样式；如果是 Crew 内部 session 或没有外部 logo，则显示 Crew。
  • Team 流程：Team 模式显示"协作看板 / Team Flow"，顶部展示总进度、当前/下一节点、运行成员；左侧使用和 sidebar 同款黑白双 agent Team logo。
  • Prompt 分层：Team Flow 第一层按每次用户 prompt 分组，组内再按 TeamPlan DAG 展示任务节点；直答型父 agent_turn 使用独立 direct turn id，复杂 TeamPlan 使用 ::turn::{request_id}，同一个团队被连续调用多次时不会混在同一层级。
  • Prompt 折叠：每个 prompt 分组头支持展开/收起，组内节点仍保持独立详情折叠。
  • 团队成员：仅 Team 模式展示团队成员名称和高度概括职责，例如 Leader 负责拆解/派活/汇总，hh 负责编码实现，kk 负责架构评审；当前由任务节点推导，后续可接真实 Team Session 成员元数据。
  • 折叠时间线：Team 时间线节点默认折叠，只显示主责、状态、标题和展开提示；用户点击节点后再展示执行关系、节点小结、产物和取消操作。
  • 触发关系：不再把每个节点都渲染成"互相交互"。单 agent 节点显示"执行：agent"；Team 委派节点显示"派发：Leader → member"；只有确实出现多个参与者时才显示协作网络。
  • 错误提示：底部提示改为"错误待处理"，并且只在 Team 节点存在真实 error 字段时显示；普通阻塞、等待或成功状态不展示该提示。
  • 固定成员视觉：每个成员在看板中使用固定 logo 颜色，便于用户沿时间线追踪同一 agent。
  • 视觉风格：采用像素可爱 + keycap-block 风格，使用暖米白、灰绿、柔粉和像素徽章，保证简约但不冰冷。
  • 调试信息收纳：运行态仍保留在底部小卡片，供开发排查并发/队列/活跃子任务，但不抢占主视觉；shell 这类工具 runtime 只作为节点日志/执行记录，不作为 Team 主责 agent 节点展示。
  • 会话识别：团队 session 的 agent_label.provider=team，左侧栏使用黑白双小 agent logo 标注；普通智能体 session icon 背景保持透明；点击 session 会立即切回聊天页并加载历史记录。
  • 历史聚合：Team 父 session 通常只保存 meta 唤醒消息，真实对话存放在 {team_session_id}::turn::*::{leader/member} 子 session；GET /api/session/{id} 对 executor=team 会聚合子 session 历史，避免右侧回到欢迎态。

9. 扩展点

  • Team Bus 持久化：当前为 in-process 内存实现，后续可替换为 SQLite/PostgreSQL queue，接口保持不变。
  • 动态工作流：在现有 Team Bus + Tasks 上增加 plan/run/checkpoint/retry/reassign primitives。
  • 纯外部团队增强：当前已支持外部成员配置、会话隔离与执行复用；外部 Leader 自动拆任务可接入动态工作流规划层。
  • 工作区隔离：后续将 workspace_policy 落到 agent_workspace_path 或 worktree。
  • 为 active child 增加运行耗时、最近事件、取消原因等更细粒度观测。

11. 当前看板细则

  • 单 Agent 聊天大纲：仅展示纯文本用户消息摘要；过滤 markdown 表格、代码围栏和链接格式；点击摘要节点直接定位到对应历史消息并短暂高亮，不在看板内展开。
  • Team 父会话历史：父 session 右侧聊天记录优先由父 agent_turn runtime task 重建真实用户输入与面向用户的 Leader/最终回复；is_meta 唤醒消息不会作为用户 prompt 展示。
  • 内部通信视图：成员子会话 assistant 输出与 Team delegate 结果会映射为 team_internal 轻量消息，并从当前 external_team_id 读取成员画像，携带 agent_id、agent_name、agent_role、is_leader、agent_tone；前端按协作看板成员卡片的头像规则展示，例如 hh leader、kk 测试，不再追加"Agent"后缀，颜色也与看板成员卡片一致。运行时派发节点、成员正文 delta、成员完成和成员失败摘要会实时推送 team_internal chunk；成员 tool/status 过程事件留在看板节点详情与调试链路，不进入聊天气泡。连续 delta 使用 append=true 合并到同一气泡，历史回放则从成员子会话与 runtime task 聚合重建。若旧历史只返回 leader 等内部后缀，前端会用当前看板团队成员映射兜底成真实成员名与 tone。Crew 内部智能体统一输出 agent_id=crew::builtin、agent_name=Crew，聊天区和看板都复用原 Crew logo，正文样式与普通 Crew session 消息一致；外部成员才使用低饱和透明气泡。这些内部通信不计入真实用户消息，也不参与看板 prompt 分层。
  • 继续上下文：Team direct leader 路径会把父 session 的用户请求与最近 Team 节点状态注入为模型上下文；用户说"继续"时，Leader 应承接最近未完成、失败或终止的团队任务，而不是当作新会话。
  • Team 进度：进度条使用稳定纯色填充，同一 Team session 内保持最大进度，避免任务轮询刷新时从 2/4 回落到 0/4。
  • Team 成员：成员区优先读取当前 external team 配置，展示 Leader + 全部团队成员；缺少配置时才从任务节点推导。
  • 看板降噪：节点内主责 chip 和执行关系头像采用中性低彩度样式，成员身份颜色主要保留在成员区与 session 内部通信里。
  • 窄聊天区适配：当协作看板展开后，聊天输入区先把 Agents/选择文件夹收纳到 + 菜单，模式切换立即显示为 A/T；看板宽度达到约 420px 后，再把 Model 收纳进 +；看板宽度达到约 520px 后，Craft/Skills 也收纳进 +，工具条只保留 + 与发送/停止按钮；看板未展开时保持原来的"单 Agent / Team"字样和独立工具按钮。

12. Leader 选择与追问边界

  • 按用户选择装配 Leader：创建团队时如果选择 crew::builtin，Team Runtime 使用 Crew 内置 Leader；如果选择外部 agent（例如 kk）为 leader_agent_id，Runtime 会把该外部 agent 装配为逻辑 Leader，并从 teammate 列表移除，避免 UI 标注和后端执行不一致。
  • Leader 会话：无论 Leader 来自 Crew 还是外部 agent，逻辑 Leader 的成员会话统一为 {team_session_id}::leader，便于权限、看板和 Team Bus 治理归一。
  • Crew 普通成员：当 crew::builtin 作为成员而不是 Leader 时，TeamManager 会创建 builtin teammate（member_id=crew::builtin），可承接拆解补位、验收、文档整理等任务。
  • 追问边界：开发、实现、继续开发等可默认推进的任务，不应因"基础版/完整版"等可默认选择停工；Leader 应采用合理默认范围委派成员持续推进，直到有可交付产物和验收结果。只有不可逆风险、权限问题或必须用户结构化决策时，才调用 ask_followup_question。

13. Team Flow 稳定展示与 Todo 节点方案

  • 状态闪动修复：Team 看板会缓存同一 Team session 的上一轮非空流程节点；当任务轮询短暂返回空数组时，Hero 区和流程区继续展示上一轮节点，不再在"等待执行任务"和"任务正在推进"之间来回闪动。
  • 空态图标："还没有流程节点"空态使用 Team 黑白 logo 中的黑色 agent 单体，保持与 Team logo 同源；黑白双 agent logo 去掉嘴巴，只保留细长竖眼。
  • Todo 现状：项目已有 Hermes 风格 TodoStore，当前挂在 PlanModeManager 下，属于按 session 保存的内存计划清单；它尚未作为 Team 看板的权威节点源，也未与 delegate_to_teammate 状态同步。
  • 推荐方案：Team Leader 接到用户目标后，应先创建 Team-scoped todo/plan nodes，字段至少包含标题、主责成员、状态、依赖、节点小结和产物引用；看板优先展示这些 todo 节点，delegate 任务作为节点执行记录挂到对应 todo 下。
  • 状态同步：Leader 创建 todo 后状态为 pending；派活创建 runtime task 后变为 in_progress；成员交付后变为 completed；失败、限流或需要用户输入时标记为 failed/blocked 并在节点详情中展示原因。
  • 复用边界：可复用现有 TodoStore 的 schema、校验和注入思路，但不建议直接把 PlanModeManager 的内存 todo 当 Team 看板源；Team 需要可恢复、可观测、可与 TaskManager 同步的 TeamPlan/Todo 投影。

14. 单 Agent 会话总结卡片

  • 命名：单 Agent 顶部卡片标题调整为 会话总结，避免和下方用户消息大纲混淆。
  • 溢出处理：会话总结保留纵向滚动能力，长摘要可上下滑动查看，不再横向溢出卡片。
  • 视觉处理：背景与 Team Flow 顶部卡片保持同款暖米色像素网格；内容直接落在卡片底色上，仅保留轻量滚动条。

15. Team 成员职责与执行身份展示

  • 职责滚动：Team 成员职责说明保留透明背景和纵向滚动能力；职责摘要不再提前压缩成省略号，长职责由卡片内滚动区域承载，不撑破成员卡片。
  • Leader 显示映射：看板内部仍可使用 Leader 表示逻辑角色，但 UI 展示时会映射为真实 Leader 成员名称；例如 Kimi 被选为 Leader 时，节点详情展示 执行：Kimi，头像字母为 K，不再显示 L。

16. Runtime 强制工作流

  • 默认开启：team_config.required_workflow 默认为 true。Team 有可委派成员时，interact() 先走 Runtime workflow；Leader 不再决定"是否派活"。
  • 自动 TeamPlan：若当前 session 没有 TeamPlan，Runtime 根据成员职责生成最小 DAG；默认 researcher 负责"拆解任务与确认方案"，coder 负责"执行任务并产出结果"，二者存在依赖边。
  • 强制派活：Runtime 只执行依赖已完成的 pending/failed 节点，通过 request_delegate(wait_for_result=True) 派给 assignee，并把 task_id 绑定回节点。
  • 失败防空转：节点记录 attempt_count 与 last_error；连续失败达到上限后转为 blocked，依赖无法满足时也会阻塞，避免循环重试。
  • 需要信息：成员通过 Team Bus 向 Leader 发送 question/decision_request/permission_request/blocked 且绑定 task 后，Runtime 可将节点标记为 needs_info，后续再接 Leader/用户追问处理。
  • 看板数据：TaskManager 负责任务列表，TeamPlan 负责流程节点，Team Bus 负责 assign/task_notification 审计；前端 Team Flow 可直接展示"Leader → member"的分配工作流。

17. 智能角色与职责生成

  • 标准角色：roles.py 维护技术负责人、项目经理、产品经理、UX/UI、前端/后端/服务端/桌面端/移动端/全栈、测试、DevOps、安全、技术文档等常用角色。
  • 快速组队：/api/external-teams/suggest 默认走本地规则，先把 Crew 内置智能体 作为稳定 Leader，再按用户需求识别前端、后端、测试、文档等角色；当用户明确说"让 Kimi 做开发""Hermes 写文档"时优先服从指定，未指定时再按 provider/name/model/system_prompt 给 Kimi、Hermes、Codex、Claude 等候选成员做默认偏好打分。
  • 硬排除：当用户明确说"不让 Codex 加入团队""不要用某成员"时，该 agent 会从 Leader/成员候选集中移除，排除优先级高于默认偏好和推荐打分。

  • 持久化：external_team_member 增加角色 key、标签、能力 JSON 与工作流泳道列；老库启动时自动迁移。
  • 运行时复用：TeamMemberSpec.metadata 携带结构化角色，Runtime 自动 TeamPlan 生成时优先使用能力和泳道识别开发/测试等节点。

18. Claude 动态工作流实现

  • 强制规划：Team 模式先创建 TeamPlan，不依赖 Leader 大模型"想起来"调用工具；leader_plan 是 Runtime 控制节点，用于表达拆分任务与确定验收标准。
  • 角色泳道 DAG：按 workflow_lane 生成规划、设计、开发、测试设计、验证、交付整理和 Leader 汇总节点；节点通过依赖边形成 DAG，前端看板可直接展示流程。
  • 测试类任务：当用户目标是测试/验证/验收，且团队没有明确 build 成员时，Runtime 不再把 verify 成员兜底改派为"实现"节点，而是生成测试设计、验证和汇总节点，避免测试团队误执行开发。
  • 并发 Worker：同一轮 ready 且 assignee 不同的成员节点会通过 asyncio.gather 并发派发；例如设计节点与测试设计节点可同时启动。
  • 失败重排：节点失败会保留 attempt_count 与 last_error，下一轮继续按依赖重试；超过上限后转为 blocked，避免死循环。
  • 信息不足：成员通过 Team Bus 提出 question/decision_request/permission_request/blocked 时，对应节点转为 needs_info，等待 Leader/用户补充信息。
  • 审计路径：所有成员节点仍通过 request_delegate 写入 TaskManager 与 Team Bus，保留看板任务、成员消息和 TeamPlan 状态同步。

19. 看板权威流程投影

  • 持久化 TeamPlan 优先：/api/tasks 在 Team 父 session 下读取 kanban_workflows 中 context.source=team 的 workflow，再把 kanban_tasks / kanban_dependencies / kanban_events 还原成前端 Task 形状；plans_for_session() 内存投影不再作为看板数据源。
  • DAG 原样展示：投影节点会携带 parent_node_ids / child_node_ids；前端 TaskBoard 根据真实 edges 计算深度分层，阶段从上到下，同层并行节点横向排列，不再把 DAG 压成单列时间线。
  • Prompt 元数据：Gateway 给 TeamPlan 投影节点补充 progress.turn_session_id 与 progress.turn_title；前端先用它聚合每次用户输入，再在组内展示 DAG。
  • 执行状态高亮：看板把 DAG 作为任务跟踪图：pending 节点弱化，running 阶段和节点高亮，completed 节点显示完成态，blocked/failed/cancelled 显示终止态；用户展开节点后查看该节点的具体执行日志。
  • 停止级联：对话框停止按钮会从父 session 级联到 ::turn:: sidechain，TeamManager 同步中断 Leader、活跃成员、TeamPlan 未完成节点和当前 task；Gateway 还会取消匹配 session 前缀的 runtime task，shell task 会尝试 kill process group，避免父会话 stopped 后子会话继续执行。
  • 阶段可读性：用户应看到 Leader 承接/拆分、规划/设计/开发/测试设计/验证/交付整理、Leader 汇总等 DAG 阶段；简单寒暄、感谢、确认类消息不进入强制 TeamPlan，由无 delegate 工具的 Leader 直接回复。
  • Leader 验收：当团队有开发节点但没有独立测试成员时，Runtime 会插入 leader_review 节点，并真实调用 Leader 的 executor 在 {team_session}::leader 会话中输出验收报告；结果写回 TeamPlan，节点日志可展示 Leader 的测试/检查过程。
  • 控制节点关系：Leader 控制节点（leader_plan / leader_summary）仍由 Runtime 自动完成；leader_review 是真实执行节点。前端显示为承接/验收/汇总，不再渲染成 Leader → Leader，避免外部 Leader 映射后出现"kk 给 kk"。成员执行节点只显示执行者，例如 执行：hh；汇总节点按上游依赖显示 汇总：hh → kk。
  • 执行记录收纳：delegate task 创建时写入 plan_node_id、requester_member_id、member 进度字段；看板主流程已有 TeamPlan 节点时，不再把同一 plan_node_id 的底层 delegate task 重复展示为独立节点。
  • 不兼容旧 fallback：本阶段不再为历史内存态 TeamPlan 或仅剩 delegate task 的旧会话合成 Leader 起止节点；直答类消息只展示父 session 的真实 agent_turn，复杂 TeamPlan 必须来自持久化 Kanban workflow。
  • 历史聚合兜底：Team 父 session 的历史接口不仅检查 executor=team，也会识别 ::turn:: 子 session；同时把相关 runtime task 的 result/error 合并为 assistant 历史，避免外部成员没有写 assistant message 时右侧历史为空。
  • 节点日志关联：前端展开 TeamPlan 节点时，仅按成员子会话、task_id 或 delegate_task_id 匹配日志，不再用 title/summary 宽匹配，避免父级汇总输出混进成员节点造成两个"执行输出"。

20. TeamPlan / TeamEvent 持久化

  • 复用专家模式产物：Team Runtime 不复用 Dynamic Kanban 的 expert planner/worker，但复用 SQLiteKanbanStore 的 kanban_workflows、kanban_tasks、kanban_dependencies、kanban_events 表作为 TeamPlan DAG 与 TeamEvent 的持久化底座。
  • 写入时机：创建 TeamPlan 后同步创建 kanban_workflows，并把每个 TeamPlan node 写成 kanban_tasks，TeamPlan edge 写成 kanban_dependencies；workflow context 标记 source=team、team_plan_id、team_session_id、parent_session_id、owner_account_id 和 external_team_id。
  • 专家隔离：Dynamic Kanban 专家看板读取最新 workflow 和复用 active workflow 时会排除 source=team；Team 看板读取时只消费 source=team，两边共享表但不共享查询结果。
  • 状态同步：TeamPlan 节点状态变更时同步更新对应 kanban task：in_progress 映射为 running，completed 映射为 done，blocked/needs_info 映射为 blocked，cancelled 保留为 cancelled。
  • 协作事件：Leader 派发、成员最终回复、成员失败等关键通信写入 kanban_events，并由 GET /api/session/{id} 投影回 team_internal 历史消息；实时 token delta 只推送前端，不逐 token 入库，避免事件表膨胀。
  • 读取路径：TeamManager 提供 task_projection_for_session()，按父 session + ::turn:: 前缀读取 source=team workflow，并按 owner_account_id 过滤；Gateway 只消费这个持久化投影。
  • 群聊降噪：Team Bus 与普通工具的 tool/status 运行时事件不再渲染为聊天气泡；成员 thinking 不进入群聊，只展示面向团队的正文 delta、Leader 派发和成员最终产出，避免把内部 JSON、推理草稿或 external_tool 状态暴露给用户。
  • UI 影响：用户看到的仍是 Team 聊天 + 协作看板；底层事件源增强后，刷新历史时更容易恢复"Leader 派发、成员回复、结果汇总"的群聊式协作流。

21. ExternalTaskPayload 与 ACP Prompt 瘦身

  • 定位：ExternalTaskPayload 不是新的入口协议，也不替代 crew.core.envelope.Envelope；它是 AgentContext/ExecutionContext 到 ACP session/prompt 文本的结构化投影。
  • 双维度语义：payload 使用 mode=single_agent|team_chat|team_relay|team_execute 表示本轮交互形态，使用 team_role=none|leader|member 表示当前 ACP agent 在 Team 中的身份；避免把"团队聊天/轻协作/执行模式"和"Leader/Member"揉成大量枚举。
  • 单 Agent 外部智能体：普通外部 ACP 会话使用 mode=single_agent、team_role=none，只保留用户本轮请求、必要输出约束和单智能体边界；不注入 TeamPlan、团队节点或成员协作字段。
  • Team 聊天：Team 会话中的普通问答使用 mode=team_chat；Leader 场景为 team_role=leader，代表团队直接回答，不派活、不创建 TeamPlan；未来用户在团队里 @member 可复用 team_role=member，仍保留团队上下文与群聊语境。
  • Team 轻协作：预留 mode=team_relay，用于 Leader 征询一个成员的短意见；Leader 负责汇总，Member 只短答，不扩展为完整计划。
  • Team 执行模式：正式 TeamPlan 执行使用 mode=team_execute；成员节点为 team_role=member，payload 携带 team_goal、member_id、team_plan_node_id、节点标题/详情、必要上游摘要、协作模式和输出契约；Leader 执行态为 team_role=leader，涉及派活或计划状态时必须落到 Crew 控制面。
  • 系统提示瘦身：ACP system prompt 从原先包含单 Agent、追问、TeamPlan、delegate 边界的大段说明，改为按 mode + team_role 生成 compact system；只有 team_execute 明确提示"派活/计划状态必须通过控制面真实执行，不得伪造"。
  • unsafe reset 记忆：当 ACP binding 标记为 unsafe_failed 后，新建 ACP session 时仍会把 Crew 侧连续上下文摘要注入 compact system prompt，保证 Kimi/外部 agent 不因新原生 session 丢失任务记忆。
  • Team 派发元数据：Team Runtime 派发节点时通过 task_payload_meta 把用户原始目标、节点信息和上游摘要传入子会话；delegate_to_teammate 仍只负责派活与任务状态，不承担 prompt 拼接。
  • 预期收益：减少 TeamPlan/角色模板/历史上下文在 ACP prompt 中的重复堆叠，降低长输出、工具循环、单 chunk 过大与 session/prompt 超时概率；同时保持单 Agent 外部调用的上下文连续性。
