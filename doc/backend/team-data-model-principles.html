2. 权威定义

对象回答的问题包含不包含生命周期
TeamSpec本次用户目标需要什么？对显式字段或 PlanningDecision 结果做规范化：必需能力、工作泳道、交付物、验收标准、复杂度、风险、不确定性、任务约束。具体 Agent、成员名单、职责文案、组队置信度、工作流，也不从业务关键词推断这些字段。结构化输入规范化生成；创建 Team 时保存输入快照。
AgentProfile这个 Agent 能做什么，判断依据是什么？能力分、能力置信度、逐能力 evidence、Runtime 条件、所选模型绑定、可用性。本次任务分配、用户指定职责、某个 Team 中的角色。Agent 创建时生成 V3；配置、Runtime、模型目录或足量历史变化时刷新。
FormationConstraints这次组队必须遵守什么？Leader、确认槽位、指定/排除 Agent、锁定项、是否允许系统补员。Agent 固有能力；用户指定不得作为能力证据。随本次组队请求生成，不独立沉淀为 Agent 数据。
FormationPlan这次具体如何组队？成员、角色、常驻职责、分配能力、选择来源、锁定状态、覆盖、置信度、原因、警告。本轮任务 DAG、节点级指令、长期团队表现。点击智能组队时生成候选；创建/保存 Team 时持久化确认版本。
WorkflowPlanTeam Session 的本轮任务准备怎么完成？任务目标、规划决策、语义工作单元、节点、依赖、负责人、本轮验收、预算快照、revision。节点实时状态、执行结果、工具过程、完整 AgentProfile、长期团队职责。每个实质性用户任务生成；结构性重规划时 revision 递增并保存当前快照。
WorkflowRun这次计划总体执行到哪里？Team/session/turn 关联、总体状态、节点运行投影、当前 plan revision。任务语义分析规则、长期能力画像。与本轮 WorkflowPlan 一起创建，执行结束后保留历史。
WorkflowEvent执行过程中按时间发生了什么？计划创建/修订、节点状态变化、成员提交、Leader 决策、用户确认和最终汇总。可变的当前状态、完整模型思考原文。执行时追加写入，作为审计、历史和恢复时间线长期保留。
TeamPortrait这个已有团队实际上表现如何？历史能力表现、协作效率、返工/阻塞、并行能力、适合任务类型。组队时的原始需求与一次性选择理由。先保留设计；达到使用样本阈值后成为有效推荐画像。

2.1 External Runtime 接入对象边界（冻结）

外部单 Agent 与外部 Team 成员共用同一套 Runtime 接入链路。该链路属于 crew/agent/external，不是新的顶层模块；Team 只消费已经创建好的 Agent 与 AgentProfile，不感知底层 ACP、Claude stream-json 或 Codex app-server 协议细节。

对象唯一职责包含禁止包含
RuntimeDescriptor静态声明"寻找什么 Runtime，并交给哪个协议驱动"。与安装路径无关的 descriptor_id、稳定 provider/runtime 标识、展示名、display_badge、环境变量覆盖、命令及安全别名、固定启动参数、adapter_id。本机实际路径、在线状态、探测结果、模型目录、业务 Agent 画像，以及探测/执行代码。
RuntimeAdapter协议驱动，负责"怎么探测和怎么执行"。probe、execute、可选 resume/cancel，参数构造、协议握手、输入输出解析、事件归一和进程清理；若上游没有模型枚举接口，可在 Adapter 内维护有来源、短小且可测试的版本化模型目录。跨 Runtime 发现目录、数据库记录、Team 分工、Agent 能力评分，以及散落到调用方的 provider 判断。
RuntimeProfile本机探测后的动态能力快照。真实可执行路径、版本、协议、可用性、结构化模型目录、默认模型、能力与诊断；metadata 记录实际 adapter_id，必要时记录 Adapter 声明的旧模型 ID 对账表。探测算法、执行代码、用户提示词、Team 角色或本轮任务状态。
external_runtime持久化 RuntimeProfile 当前快照。Runtime 标识、路径、版本、协议和 metadata。RuntimeAdapter 实例、运行进程、完整 AgentProfile 或 Team 成员职责。
AgentProfile描述用户创建的 Agent 能做什么及其证据。所选 Runtime/模型绑定、Skills、Tools、system prompt 形成的能力分、置信度与 evidence。CLI argv、ACP JSON-RPC、Runtime 搜索路径和本次 Team 分配。
命名冻结：不建立独立领域对象 AdapterProfile。静态选择由 RuntimeDescriptor.adapter_id 表达，协议行为由对应 RuntimeAdapter 实现，探测结果由 RuntimeProfile 表达。若某 Adapter 内部需要不可变参数模板，它只是 Adapter 的私有实现配置，不进入 API、数据库或 Team 数据模型，也不得演变为与 Descriptor 重复的公共模型。
展示标识契约：RuntimeDescriptor.display_badge 是 Runtime 的唯一权威短标识，当前冻结 Kimi=K、Codex=X、Hermes=H、Claude Code=C，其他内置 Runtime 使用显式且不冲突的 1–2 字符。Detector 将它写入 RuntimeProfile metadata，Gateway 再投影到 Runtime、external Agent、external Team Member 与 Session agent_label。旧 external_runtime 行不迁移数据库，由服务端按 descriptor_id（兼容 provider）实时对账；未知 Runtime 的中性首字母也只允许服务端生成。Desktop/Web 禁止根据 provider 或 Agent 名称二次推断，字段缺失仅显示 ? 作为契约错误。
Runtime 身份与路径迁移：descriptor_id 表示 Runtime 种类（如 builtin:hermes），runtime_id 表示由 provider + 规范化可执行路径确定的本机安装实例。扫描发现同 Descriptor 的唯一新 ready 实例、而旧实例路径已消失时，Store 在事务中保持 external_agent.id 不变并迁移其 runtime_id；Team 因引用 Agent ID 无需改写。旧原生 session binding 删除，旧 Runtime 记录标记 lifecycle_status=replaced 与 replaced_by_runtime_id 后退出默认 UI。存在多个候选时禁止猜测，不自动迁移。
实现状态（2026-07-24）：对象边界、协议流式核心和协作能力对齐已经落地；当前注册 acp-stdio、claude-stream-json、codex-app-server 三个协议驱动，并以 external_runtime_session_binding 统一保存原生会话指针。ACP 与 Claude 通过统一 RuntimeMcpServer 转换为各自原生 MCP 配置；Codex app-server 使用原生 dynamicTools + item/tool/call 回调，但仍进入同一个 InteractionBridge.invoke_tool() 做 Binding 鉴权和业务处理。外部单 Agent、外部 Team 成员和临时委派均进入 ExternalExecutor。跨系统实机验收仍列在本页 TODO；完成前不得宣称所有目标操作系统均已实机验证。后续接入不得退回 provider 分支或重新引入 AdapterProfile。

Claude Code 模型数据原则：Claude Code 当前没有公开的 models list 命令，因此 claude-stream-json Adapter 参考 Multica，在 Adapter 内维护精简、版本化并按 Anthropic 官方 ID 校准的模型目录；RuntimeProfile 保存这份结构化快照。创建 Agent 时必须从目录选择，Session 覆盖仍是会话级，执行时明确传入 --model，气泡按同一绑定映射 label。模型回答正文永远不是数据源；协议 system/init.model 只可用于诊断请求与实际运行是否一致，不反向改写 AgentProfile 或 Session。

通用 ACP Runtime 采用同样关系：Kimi、Hermes、Gemini、Qwen 等 Descriptor 可以共享 adapter_id="acp-stdio" 和一个通用 ACP RuntimeAdapter，只在 Descriptor 中声明各自命令与固定启动参数，不为每个 provider 新建 Adapter。Claude Agent ACP 与原生 Claude Code 是两个 Descriptor：前者选择 ACP Adapter，后者选择 Claude stream-json Adapter。

  • 禁止按 provider 分派协议行为：Resolver、Executor、Gateway 和 TeamManager 不写 provider == "claude" 或 provider == "codex" 来决定参数和解析方式；统一根据 adapter_id 取得 RuntimeAdapter。
  • 允许 Adapter 内实现协议差异：Claude stream-json、Codex app-server、ACP 的握手与事件格式天然不同，应由各自 Adapter 封装，不把协议细节塞进 Descriptor。
  • 未知 Runtime 边界：标准 ACP Runtime 可通过受控 generic ACP 接入；未知私有 CLI 必须增加经过审查的 RuntimeAdapter，不允许用户配置任意 shell 字符串。
  • 影响边界：该模型只影响外部单 Agent 和由外部 Agent 组成的 Team；MobileWork 内置 Agent、专家、专家团继续使用原有执行路径。
  • 旧 Profile 驱动补齐：持久化 RuntimeProfile 缺少 adapter_id 时，由 Descriptor 注册表按 descriptor_id（旧数据兼容 provider）补齐，不在 Executor 中写 Codex/Hermes provider 分支。这样旧 Codex 会话可直接升级到 app-server。
  • 思考事件边界：RuntimeAdapter 只归一 Runtime 主动返回的可展示 reasoning summary；Executor 将其保存为 Message.thinking，Desktop 复用过程时间线。Codex 当前采用 medium effort + concise summary 的平衡默认值；不保存、不推断也不伪造原始思维链。
  • 终态事件边界：协议权威终态由 Adapter 识别：Claude 为 type=result，Codex 为 turn/completed，ACP 为对应 RPC/流结束。收到权威终态后统一关闭协议输入并回收短进程；不得以正文静默、特定文本或 provider 名称推断任务完成。
  • 模型 ID 对账边界：Adapter 可在 RuntimeProfile metadata 声明窄范围 model_migrations。Store 只迁移该 Runtime 下精确命中的旧 Agent 模型；Session 读取与 ExternalExecutor 共用同一规范化函数兜住旧覆盖。不得按 provider 写数据库迁移，也不得修改已选择的其他具体模型。

2.2 Runtime 识别到组队与执行的稳定链路

Runtime 发现、Agent 能力画像、Formation、DAG 编译和运行时执行是连续但职责独立的五段链路。Formation 与 Runtime staffing 使用解析后的标准 AgentProfile；DAG admission 使用 Formation 已确认的成员能力快照；三者共用同一个能力覆盖计算入口，只在需求范围、候选池和触发时机上不同。不允许 Team Formation 根据 provider 名称猜测协议，也不允许 RuntimeAdapter 参与团队选人。

2.4 两类 Binding 与 Interaction 生命周期

项目中的两类 Binding 解决不同问题，不得复用同一对象或混淆生命周期。

对象用途存储生命周期
ExternalInteractionBinding把外部进程的 MCP 回调映射到可信 Owner、Crew session、Team session、member 和 role，并据此鉴权。Gateway 内存，使用高熵临时 token 索引。单次外部执行；超时、执行结束或 Owner 退出立即撤销。
external_runtime_session_binding把 Crew session 映射到 Claude session、Codex thread 或 ACP session，支持跨轮 resume；session_profile 记录影响原生会话能力面的协议版本。数据库。跨多轮会话；直到失效、能力面版本变化、重建或显式清理。

3. TeamSpec

10. 不变量与开发纪律

  • 需求与供给分离：TeamSpec 只写任务需要；AgentProfile 只写 Agent 能力供给。
  • 能力与分配分离：用户指定和 Team 分配不修改 AgentProfile 能力分。
  • 职责与任务分离：FormationPlan 保存团队常驻职责；WorkflowPlan 保存本轮任务职责。
  • 候选与确认分离：智能组队先返回候选 FormationPlan，用户创建/保存后才持久化。
  • 画像与事实分离：TeamPortrait 只能基于足量运行事实生效，不能把 FormationPlan 直接包装成"历史表现"。
  • 能力单源：通用能力 key、label、signals、aliases 和受控包含关系统一来自 capabilities.py。
  • 角色单源：role key、稳定工作原则和能力组合统一来自 roles.py；角色能力必须使用 CapabilityCatalog 的规范键。
  • 计划与运行分离：WorkflowPlan 保存相对静态的计划定义；节点状态、结果和重试只写 WorkflowRun 投影与 NodeAttempt。
  • 当前与历史分离：kanban_workflows.context.workflow_plan 保存当前生效快照；WorkflowEvent 追加保存产生、修订与回退历史。
  • 不提前造层：当前不引入 TeamManifest，不为 TeamPortrait 创建空表；WorkflowPlan V1 优先复用现有 Dynamic Kanban 存储。

层次回答的问题数据库职责

WorkflowRun总体和节点做到哪里？运行头、总体状态、节点状态投影。

14. PlanningDecision：一次受约束的 LLM 语义分析

默认 Auto 模式下，新的实质性任务调用一次轻量 LLM。第一阶段输入只包含本轮 Prompt、TeamSpec 必备摘要、成员能力摘要和用户模式偏好；不传完整 AgentProfile、完整 FormationPlan、成员职责全文或历史事件。后续运行中重规划再追加当前会话状态与工具可用性摘要。输出必须符合小型 JSON Schema。

  "goal_clarity": "high",
  "critical_missing_info": [],
  "dependency_pattern": "parallel_merge",
  "quality_policy": "independent_review",
  "dynamic_discovery": false,
  "conditional_branching": false,
  "iteration_until_convergence": false,
  "risk_level": "medium",
  "semantic_uncertainty": "low",
  "work_units": [{
    "id": "research_hermes",
    "objective": "调研 Hermes 的核心架构和模块",
    "required_capabilities": ["research", "analysis"],
    "depends_on": [],
    "expected_output": "Hermes 调研摘要",
    "needs_independent_review": false
  }]
}
  • LLM 负责理解目标、工作单元、依赖形态、质量要求和未知项，不生成 DAG nodes/edges，不直接决定最终 Agent、权限和预算。
  • 系统校验 work unit ID、依赖引用、环、目标/输出完整性、CapabilityCatalog 规范键和用户约束；LLM 不得指定不存在的 Agent 或修改 FormationPlan。
  • PlanningDecision 不作为新的长期数据层；其必要结论进入 WorkflowPlan 的 planning、nodes、edges、warnings。
  • 用户明确选择 Fast、当前只是进度查询/确认/追问补充，或命中相同 Prompt 与上下文指纹缓存时，可以跳过新的语义分析。
  • 输出无效时允许一次受限修复；仍失败则回退 Standard。缺少关键用户事实时应追问用户，不得用 AI Planner 猜测事实。

15. Auto / Fast / Standard / AI Planner

产品公开模式统一为 auto | fast | standard | ai；不再接受旧模式别名，公开模式只保留四种产品概念。默认使用 Auto，手动模式保留为高级覆盖，并同时保存 requested_mode 与 selected_mode。

模式规划方式边界
Fast跳过规划 LLM，本地生成 Leader、至多一个主要执行者和必要汇总/核验的极简路径。目标单一、依赖少、低风险；用户明确选择 Fast 时优先控制成本和延迟。
Standard一次轻量 PlanningDecision 产出语义 work units，再由确定性 Topology Compiler 分配成员、生成 DAG 并校验。工作单元和依赖可明确映射到受支持的通用拓扑；不得退化成开发领域固定流水线。
AI PlannerLLM 生成任务定制 DAG，随后执行成员白名单、能力、预算、依赖和 PlanGraph 严格校验。子任务不可预知、条件分支、动态发现、需要循环收敛或通用拓扑无法表达时使用；失败回退 Standard。
AutoPlanningDecision + 确定性 PlannerPolicy 选择 Fast、Standard 或 AI。默认入口；不使用法律、开发、调研等领域关键词决定模式。

Auto 使用按顺序执行的结构门控，不使用不可解释的单一"复杂度魔法分数"：

  1. 用户明确覆盖模式时尊重用户选择。
  2. critical_missing_info 非空时先追问用户。
  3. 存在 dynamic discovery、conditional branching 或 iteration until convergence 时选择 AI Planner。
  4. 只有一个工作单元、风险低且不需要独立核验时选择 Fast。
  5. 工作单元可映射受支持拓扑且未超过 Standard 可配置资源上限时选择 Standard。
  6. 其他情况选择 AI Planner；Planner 调用失败时回退 Standard。

16. Standard 通用拓扑与质量策略

Standard 将"依赖形态"和"质量策略"拆为两个正交维度，避免把所有模式都写成互斥图类型：

{
  "dependency_pattern": "sequential | parallel_merge | staged",
  "quality_policy": "none | leader_review | independent_review | evaluator_optimizer"
}
概念语义说明
Sequential后一个工作单元依赖前一个结果。最基础的单向依赖，不默认包含正式阶段或反馈循环。
Parallel Merge多个独立工作单元并行就绪，结果汇总后继续。逻辑并行不等于必须拥有同等数量 Agent；Runtime 受并行预算和成员可用性限制。
Staged Pipeline带进入条件、阶段交付物和阶段门禁的顺序结构。是具有治理语义的 Sequential；阶段内部仍可包含并行节点。
Evaluator Optimizer执行者产出后由评估者按标准判断，不通过则修订再评估。逻辑上是反馈循环；V1 每次具体 WorkflowPlan 保持无环，通过追加修订/再评估节点展开循环。

Standard Compiler 只负责把已校验 work units 编译为节点与依赖、按 FormationPlan 和 AgentProfile 证据分配成员、添加必要的 Leader 汇总/审阅，并通过 PlanGraph 校验无环、无孤立节点和负责人有效。它不会重新理解业务领域。

17. 置信度与预算快照

PlanningDecision 不应让 LLM 直接决定一个看似精确的总分。系统分别计算需求清晰度、拓扑清晰度和能力证据置信度，V1 使用保守最小值：

overall_confidence = min(
  requirement_confidence,
  topology_confidence,
  capability_confidence
)
  • requirement_confidence：目标、交付物和验收条件的关键字段明确比例。
  • topology_confidence：work units 中目标、输出和依赖关系可校验的比例。
  • capability_confidence：FormationPlan 的必需能力覆盖与 AgentProfile evidence confidence。
  • 初始建议：>= 0.80 可自动执行；0.55–0.80 增加 Leader 审阅或提示；< 0.55 按缺口来源选择追问、AI Planner 或补员建议。阈值必须集中配置，并在积累真实结果后校准。

budget_snapshot 保存 ResourcePolicy 最终解析出的执行限制，不负责推导预算。它服务成本控制、重启恢复、并发限制、重试与工具上限、动态提额/用户确认、决策解释，以及后续 TeamPortrait 和 AgentProfile 的效果分析。V1 只保存 Runtime 真正执行的限制，不提前建设复杂预算模型。

18. Workflow 不变量

  • 每个实质性用户 turn 对应一次 WorkflowRun；一个 WorkflowRun 可拥有多个 WorkflowPlan revision。
  • WorkflowPlan revision 只因结构、依赖、负责人或本轮契约变化而递增；普通状态更新和同节点重试不递增。
  • DAG 逻辑并行与实际 Agent 数量分离；Runtime 根据预算、成员可用性和工具限制调度。
  • AI Planner 不能绕过 FormationPlan、用户成员约束、权限策略、CapabilityCatalog 和 ResourcePolicy。
  • 高风险不必然意味着 AI Planner；风险主要增加审批、独立核验和权限门禁。是否选择 AI 由任务结构是否可预知决定。
  • Evaluator Optimizer 的逻辑循环不得直接写成有环 DAG；通过 revision 或追加节点保持每份具体计划可拓扑执行。
  • 看板恢复以数据库中的当前计划快照、节点/依赖投影、NodeAttempt 和 WorkflowEvent 为准，不依赖进程内 TeamPlan。

18.1 Fast Formation 基线整合

2026-07-27 完成的 Fast 基线整合没有改变冻结数据模型。角色目录仍是已有 AgentProfile 与 FormationPlan 之间的确定性编译知识，不是新的持久化对象；确认后的职责仍保存为 FormationPlan 成员既有的 responsibility 与 responsibility_markdown。

  • Fast 只根据 TeamSpec 硬约束、AgentProfile evidence、角色目录和能力覆盖生成候选 FormationPlan；不调用 LLM，不直接创建 Team，也不绕过用户确认。
  • 职责结构固定为既有 mission / boundaries / deliverables / collaboration，内部 scope、节点标签和去重签名不进入持久化模型。
  • 用户确认后，TeamManager 通过既有成员 metadata 把 FormationPlan 职责投影给本轮 Runtime；这只是运行时投影，不新增数据库字段。
  • Standard Role DAG 仅对 FormationPlan-backed 外部团队按已确认职责生成节点；完全相同的责任范围做确定性精确去重，但不删除长期团队成员。
  • PlanningDecision 将 Formation 职责视为成员分配边界，而不是必须给每位成员制造工作单元的配额；任务拆解仍以本轮目标和依赖为准。
  • FormationPlan 与 WorkflowPlan 版本均保持不变；专家团队、配置团队、MobileWork 和单 Agent 不进入此投影路径。

20. Formation、DAG 与 Runtime 能力准入（2026-08-13）

能力来源统一但生命周期不同：Formation 使用 TeamSpec 的长期团队要求；DAG 编译使用 Formation 已确认并落到 TeamMemberSpec.capabilities 的能力分配快照校验负责人；Runtime 只检查当前节点在计划生成后是否发生能力/Runtime 变化。Formation 与 Runtime 消费 Resolver 返回的标准 AgentProfile，DAG 不重新访问外部 Agent Store，而是消费由 Formation 形成的能力契约；三者共用同一个覆盖计算入口，不建立 EffectiveAgentProfile 或第二套能力评分。Runtime 的能力契约与可执行性是两个维度：已确认能力可以抵抗低置信先验，但不能绕过外部 AgentProfile 的不可用或未知状态。

  • 统一入口：evaluate_capability_coverage() 只做本地确定性计算，返回 required、covered、missing、unavailable、unknown 和 covered_by；不访问 Store、不调用 LLM。DAG 仅传入能力契约；Runtime 同时传入已解析画像并开启可用性门控。
  • DAG 硬准入：节点生成后必须检查 assignee 是否完整覆盖节点能力。若现有其他成员完整覆盖，编译器只做本轮确定性改派并记录 previous_assignee、assignment_source=existing_member_reassignment；若无人覆盖，记录计划内能力缺口，不能伪装成已覆盖。
  • Runtime 兜底：节点执行前只检查当前 assignee，不把整个团队能力并集当作当前节点能力。无真实缺口不创建 RuntimeStaffingRequest、不发送补员确认。
  • 解析边界：TeamManager 通过单一成员画像解析入口读取当前 External Agent/model 绑定；Team 初始化和 Runtime readiness 不各自拼装 Store 数据。DAG 只消费已解析的 member_profiles 与确认能力契约，不反向触发 I/O。
  • 性能边界：Runtime 按 owner、Agent、模型、画像修订/内容指纹和 Runtime/model 执行指纹缓存已解析 AgentProfile；普通调度轮询不重新读取和解析全部成员，画像、Runtime 状态或模型事实变化时自然换 key，不复用旧画像。

22. Runtime 补员拒绝与 Workflow 可行性（2026-08-13）

  • 已有成员可承担：Runtime 不弹补员确认，直接创建本轮确定性改派，保存原负责人和改派原因，并重置节点为 pending。
  • 没有可承担成员：只阻塞当前节点；沿 DAG 依赖链的后续节点保持等待并记录 blocked_by_nodes；没有依赖的并行节点仍可继续。
  • Workflow 结论：关键节点无法执行时 Workflow 状态为 blocked，不能返回“已完成”；只有节点恢复、明确允许降级/跳过，或用户调整任务后才能重新形成可完成路径。
  • 持久化：runtime_blocking 保存拒绝/无候选原因、补员请求、能力要求和可行性快照；Kanban task 的 assignee 同步为空，避免内存态与看板态分裂。
